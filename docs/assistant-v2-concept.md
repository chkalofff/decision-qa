# Ассистент v2 — концепция модернизации

Статус: проект на ревью пользователя (прошёл раунд внутренней критики,
фатальные замечания учтены). Основание: аудит текущей реализации
(backend/assistant, frontend/static/assistant.js) + исследование лучших
практик (Label Studio Prompts, Argilla, Prodigy, Cursor, Hex, Promptfoo,
Hamel Husain evals FAQ, NN/g). Дата: окт 2026.

## 1. Рамка: кто пользователь и что он делает

Аналитик отлаживает decision-пайплайн перед автопилотом: подбирает контекст,
формулирует вопросы, задаёт правила решений с порогами, прогоняет модели,
размечает результаты (✓/✗/? + комментарии). Цель — минимум ложных
срабатываний обоих типов при стабильном качестве. Ассистент — второй
участник этой петли, а не «чат-бот сбоку».

Ключевой инсайт исследования (Label Studio Prompts, Husain): **разметка
пользователя — это ground truth, и ценность ассистента измеряется тем,
насколько его предложения уменьшают ошибки на размеченных данных**. Всё
проектирование ниже — вокруг этой петли.

### 1.1. Два равновероятных сценария (уточнение по ревью пользователя)

- **С ground truth:** пользователь размечает результаты (или верифицирует
  предразметку), ассистент ищет проблемы и предлагает исправления с дельтой
  на размеченных.
- **Без разметки (холодный старт):** ассистент помогает проанализировать
  прогон без единой метки и **сам предлагает разметку** (см. 4.3) —
  пользователь только подтверждает/отклоняет.

Оба сценария — first-class; интерфейс не должен «наказывать» отсутствие
разметки.

### 1.2. Известное будущее: мультипользовательский режим — горизонт недель

Продукт уходит в веб-серверный многопользовательский режим (инхаус-модели,
модели на Mac пользователя) уже в ближайшие версии. v2 ассистента мультиюзер
**не реализует**, но не должен блокировать переход:

- persist-форматы версионируются (см. 3.6) — миграция на серверные сессии
  не сломает данные;
- API ассистента остаётся stateless (снапшот приходит от клиента);
- никаких решений «один пользователь = одна машина» в новых механиках
  (единственное исключение — start/stop моделей, §6.1, уже POSIX-only и
  честно отказывает).

**Целевой тир chat-модели ассистента:** умные модели с режимом рассуждений,
готовые к длительной многошаговой агентной работе (класс qwen3-flash-next /
deepseek-flash и выше, инхаус или облачные). Слабые локальные (2bit) —
деградационный режим (§5.1), а не основа проектирования. Следствие: лимиты
агентного цикла (MAX_STEPS=6, TOTAL_TIMEOUT=900с) в волне 3 пересматриваются
вверх для «длинных» задач с явным прогрессом в чате.

## 2. Что уже есть и переиспользуем (не трогаем транспорт)

- SSE-чат с tool calling (hermes-локальный / нативный облачный), лимиты
  шагов и таймаутов, стоп-кнопка, стриминг токенов.
- Proposal-конвейер «карточка → принять/отклонить → клиентское применение»
  — универсален, новые виды предложений добавляются без переделки.
- run_trial — действующий механизм what-if: ≤5 вопросов × ≤3 модели,
  только запущенные decision-модели, умеет один batch-файл (`batchFile`) и
  картинки (`useImages`), карточка отличий ≠/↑/↓.
- reviewMarks в снапшоте — разметка всех 8 уровней доходит до модели,
  **с лимитами 30 пунктов / 1500 симв. и молчаливым отбрасыванием
  сирот** (assistant.js:577-591) — «вся разметка видна» неверно, это
  допущение учтено ниже.
- Undo на карточках вопросов/контекста/правил (один снимок на карточку).
- Управление моделями уже есть как HTTP API: `POST /api/models/{key}/start|
  stop` поверх `mm.start_model/stop_model` (app.py:166-178,
  model_manager.py:390-477) — идемпотентность, бюджет RAM, adoption чужих
  процессов, **только POSIX** (Windows-релиз обделён).

## 3. Слепые зоны — закрыть в первую очередь (фундамент)

Ассистент сегодня советует «вслепую» в самых важных местах. Дополнения
снапшота/инструментов с непропорционально большим эффектом:

1. **Trace решений** в снапшот: по каждому исходу — какие условия
   сработали/провалились и с каким запасом. Данные уже есть на фронте:
   `evaluateDecision().trace` (decision.js:85-116), из него строятся
   hover-объяснения `describeDecision` (decision.js:200-243) — сериализуем
   тем же текстовым генератором, почти бесплатно. Без этого тюнинг порогов —
   гадание.
2. **Полные распределения вероятностей и label_mass** для размеченных
   (✗/?) ячеек вместо top-ответа — точность нужна именно там.
3. **Метрики прогонов** (длительность, токены) одной строкой на прогон —
   данные уже рендерятся (results.js:520,732); нужны для cost-awareness (§6).
4. **Инструмент детализации single-результатов** (аналог get_file_result
   для одиночного режима) — сейчас есть только для batch
   (tools.py:98-107).
5. **Превалидация карточек**: фронт вызывает существующий, но неиспользуемый
   `/api/assistant/propose/validate` при показе карточки. «Битое» =
   невалидно по схеме ИЛИ семантически конфликтует (дубль текста вопроса,
   ссылка на несуществующий №, пустой diff). Битая карточка помечается до
   клика «Принять». Валидация обязана понимать и пакеты (§5.1), иначе
   волна 2 обесценивает волну 1.
6. **История чата в persist** (dq-workspace): перезагрузка сегодня стирает
   разговор вместе с trial-карточками — теряется работа. Хранить ленту
   (сообщения + карточки со статусами), лимит 20 сообщений как сейчас.
   **Версионирование формата** (`v:`-поле, как в снапшотах) и политика
   усечения: trial-карточки хранятся без `fullAnswers` (тяжёлые) — при
   восстановлении таблица сворачивается в сводку «прогон от <время>,
   N вопросов × M моделей». localStorage ~5 МБ — бюджет ленты ≤300 КБ.
7. **Vision у chat-модели ассистента** как конфигурационная опция.
   Честная оговорка: chat+vision сегодня одна модель (bonsai2-27b, 2bit) —
   ценность ограничена, пункт отложен за волну 3. Если у ассистента vision —
   он сам анализирует картинки; если нет — делегирует через run_trial
   useImages (уже работает).

### 3.8. Бюджет снапшота (обязательный расчёт до реализации)

Потолки 6000/12000 симв. (prompts.py:124-125) уже тесные: контекст до 4000 +
сводка до 3000 + разметка 1500, а серверная serialize_snapshot режет хвост.
Новые поля (trace, распределения, метрики) добавляют ~1–2К симв.
Распределение приоритетов жертв (от первого к последнему): тексты
batch-файлов → context.text → resultsSummary → метрики → распределения
не-размеченных ячеек → reviewMarks с хвоста. **Trace и разметка не режутся
никогда** — ради них всё затеяно. Для 32k-контекста локальных моделей
(model_manager.py:412-415 уже поднимает CONTEXT_LENGTH ради ассистента)
потолок поднимаем до 8000 симв. с тестом на реальной локальной модели.

## 4. Анализ прогонов: от «сводки» к «диагностике»

### 4.1. Карточка «Разбор прогона» (error analysis как фича)

По запросу («разбери прогон») или кнопке в шапке результатов ассистент
выдаёт **карточку-таксономию**, а не простыню текста.

**Разделение труда (важно): частоты и группировку считает код, не модель.**
Расхождения моделей, близость score к порогу, концентрация ✗ по типам
вопросов, провалы условий из trace — всё это детерминированные метрики,
считаются на фронте/сервере и отдаются модели готовой таблицей. Модель делает
только то, что не умеет код: **называет категории и формулирует причину**
(«порог режет пограничные score», «модель игнорирует изображение»),
опираясь на комментарии пользователя к ✗/?. Это снимает зависимость от
качества локальных chat-моделей — 2bit bonsai справится с именованием,
а «сам нашёл аномалии» = код нашёл + модель объяснила.

Карточка: категории с частотами; каждая категория кликабельна — подсвечивает
строки/ячейки в результатах (инфраструктура есть: `flash()` review.js:369,
help-highlight). Это цикл Husain: open coding (комментарии пользователя) →
axial coding (код группирует, модель называет) → чиним самую частую причину.

### 4.2. Очередь «Что разметить дальше» (active learning)

Карточка-кандидаты на разметку, отсортированные по ценности метки
(всё считает код):

- расхождение моделей между собой (⚡);
- score/choice вблизи порога срабатывания (из trace + распределений);
- низкая уверенность top-ответа;
- override-сигнал: ячейки, где пользователь ранее правил похожие.

Клик по кандидату → скролл и подсветка ячейки. **Холодный старт:** пока
разметки нет, дельта (§5.2) недоступна — ассистент обязан замыкать петлю:
«разметки нет → вот 10 самых информативных кандидатов, разметь их».
Quick-chips при пустой разметке предлагают «Что разметить», а не «Разобрать
прогон».

### 4.3. Предразметка от ассистента (suggestions как first-class, Argilla)

Для сценария «размечать некогда / корпус большой» (анализ интервью,
продуктовых исследований): ассистент **предлагает разметку** — вердикты с
однострочным обоснованием по кандидатам из 4.2 — а пользователь
подтверждает/отклоняет. Предложенные метки визуально отличимы от ручных
(пунктирная кромка + значок ✨) и в экспорте/saveas помечены `source:
"assistant"` — снимок ассистента считает их отдельно от ground truth
(в дельте §5.2 они имеют пониженный вес, пока пользователь их не
подтвердил). Применение — через тот же review.js (одна механика пометок,
два источника). Это смена задачи с «разметить с нуля» на «accept/reject
кандидата» — главный ускоритель разметки по всему исследованию.

## 5. Предложения: пакеты, дельта, пороги

### 5.1. Пакет-решение (bundle)

Сегодня propose_* атомарны. Вводим **пакет**: одна карточка «План
исправления» с секциями (вопросы / правила / контекст), у каждой секции
свой diff и **per-section accept/reject** (гранулярный accept — паттерн,
за который пользователи выбирают Cursor; бинарный accept-all — анти-паттерн).
Undo формулируется точно: **одна кнопка «Отменить» откатывает все принятые
секции пакета** (композитный снимок до применения первой секции пакета);
per-section undo не делаем.

**Деградация на слабых моделях:** bundle — это большой составной JSON;
риск hermes-парсинга на 2bit-моделях реален (парсер уже несёт три формата
и ретрай, agent.py:43-49,229). Правило: пакеты генерируют только модели из
allowlist («сильные»: облачные + qwen-локали); слабая chat-модель получает
промпт-инструкцию выдавать пакет как последовательность обычных propose_* —
фронт склеивает их в одну карточку. Решение по allowlist — после замера на
реальных моделях в волне 2.

### 5.2. Дельта на размеченных (Label Studio Prompts-петля)

Любое предложение правки вопроса/порога перед показом пользователю
**проверяется на размеченных данных**, и карточка показывает дельту:
«на 12 размеченных ячейках: было 4 ошибки → стало 2; ✗→✓: 3, ✓→✗: 1
(показать)». Пользователь решает по измеренному эффекту, а не по
убедительности текста.

**Два механизма дельты — по стоимости:**

- **Правка правил/порогов — без прогона моделей вообще.** Сервер исходы
  не вычисляет: их считает фронт из `fullAnswers` через evaluateDecision
  (trial.py:6-7). Значит, новая редакция правил применяется к **уже
  полученным** полным ответам прогона локально и мгновенно — дельта
  «было/стало» по размеченным ячейкам бесплатна. Это самая дешёвая и
  самая частая операция тюнинга → делается в ранней волне, никаких гейтов.
- **Правка вопросов — нужен what-if прогон** (текст вопроса меняет ответ
  модели): расширение run_trial — прогон только по размеченным целям,
  затем дельта как выше. Гейтится по §6.

Размеченных данных мало (<5 целей) — честный дисклеймер «выборка маленькая,
эффект ±шум» вместо ложной точности.

### 5.3. Сопоставление разметки с what-if ячейками (краеугольный камень)

Пометки ключуются `targetKey` = id вопроса из снапшота прогона + ключ
модели + id файла (review.js:52-66). Проблемы, которые надо закрыть явно:

1. **Снапшот ассистента не отдаёт id вопросов** — только номер `n`
   (assistant.js:717); run_trial генерирует синтетические `q1..qN`.
   Решение: прокинуть стабильный id вопроса в снапшот (скрытое поле
   рядом с `n`) и в what-if прогон передавать вопросы **с исходными id**,
   а не синтетическими. Изменённая формулировка сохраняет id — именно это
   позволяет дельте работать на отредактированных вопросах.
2. **Уровни выше ячейки** (прогон, модель, файл, вопрос целиком) на ячейки
   не мапятся: они участвуют в дельте только как агрегаты («✗ прогона»
   = конфликт, если дельта ухудшает >N ячеек) и как контекст для модели.
   Дельта считается строго по ячеечным пометкам (single: ответ на вопрос;
   batch: ячейка вопрос×модель×файл); остальные уровни — в сводку причин.
3. **runMode "both"** добавляет mode-суффиксы к ключам — учесть в
   сопоставлении (тестом).
4. **resultsStale** (результаты старше текущих вопросов): дельта на stale-
   разметке запрещена — карточка честно говорит «разметка от старой
   редакции вопросов, сначала перепрогон».
5. Сироты (пометки без живой цели) уже отбрасываются снапшотом — для дельты
   это корректное поведение.

### 5.4. Тюнинг порогов на trace

Предложение по правилам опирается на trace (§3.1): «исход „спам"
проваливается на условии score≥70: в 4 размеченных ✗-случаях score 62–68»
→ propose_decision с новым порогом + **мгновенная локальная дельта** по
механизму §5.2 (без прогона). Это главный быстрый выигрыш этапа.

### 5.5. Генерация сбалансированной системы вопросов — отложено

Матрица покрытия «аспекты × типы» генерируется моделью — сама по себе
источник нейрослопа, ценность ниже остального. Вместо неё в ранних волнах —
усиление промпта propose_questions: обязательное поле `aspect` у каждого
вопроса (что закрывает) и правило «не плодить вопросы об одном аспекте».
Полноценная матрица — после обкатки, отдельным решением.

## 6. What-if под капотом: cost-awareness и стратификация рисков

Принцип (Cursor auto-review, agent-patterns): **апрув-гейт только на
длинных/необратимых действиях, дешёвые — без вопросов**, иначе approval
fatigue и пользователь штампует апрувы не читая. Правила гейтов — жёсткие,
в коде; никакого «LLM решает, спрашивать ли».

**Единица «дороговизны» — не стоимость токенов, а сложность и длительность
задачи** (уточнение по ревью): в целевом режиме модели локальные (Mac
пользователя) или инхаус — денежная стоимость не играет; внешние модели
(Jev и подобные) — только для внутренних экспериментов, не для работы
пользователей. Ассистент оценивает «стоит ли запускать и уходить в
длительное решение» по объёму (ячеек × моделей) и прогнозу времени.

- **Дешёвые (без апрува):** run_trial на локальных запущенных моделях,
  ≤5 вопросов × ≤3 модели, один вход — как сейчас. Локальный пересчёт
  правил (§5.2) — бесплатен всегда.
- **Средние (карточка-план с оценкой):** what-if по нескольким файлам
  пакета, всё облачное (тестовое). Карточка: «План: прогнать 8 файлов ×
  2 модели ≈ 3–6 мин. [Запустить] [Только размеченные] [Отмена]». Оценка —
  диапазоном (ложная точность хуже отсутствия), из метрик прошлых прогонов
  (§3.3). Кнопка «только размеченные» — scope chip, удешевляет прогон.
- **Длинные/необратимые (явный апрув):** полный прогон пакета (уже есть —
  propose_run), сохранение пресета, запуск/остановка моделей, многошаговые
  агентные серии (§1.2: запуск >~5 мин или >3 шагов прогонов подряд — с
  карточкой-планом и возможностью прервать).

### 6.1. Запуск моделей ассистентом

Инструмент `start_model`/`stop_model` — **тонкая обёртка над существующим
`mm.start_model/stop_model`** (не над run_*.sh напрямую): бюджет RAM,
идемпотентность и adoption уже реализованы там. Всегда через
proposal-карточку («Запустить Qwen3.5? ~9 ГБ RAM, свободно 22 ГБ»).

Две оговорки: (1) запуск работает **только на macOS/Linux** — на Windows
инструмент честно отвечает «запустите модель вручную» (релиз для Windows
существует, молчать нельзя); (2) запуск модели — минуты, синхронный
tool-вызов не подходит: инструмент возвращает «запускается», агентный цикл
ждёт статуса поллингом `list_models` (probe уже есть) с прогресс-строкой в
чате. Закрывает сценарий пользователя «модели не влезают в RAM — гоняю по
очереди»: ассистент сам строит серию «прогнал → остановил → запустил
следующую → сравнил».

### 6.2. Batch what-if

run_trial умеет один файл пакета (`batchFile`). Шаг — серверная обёртка
«прогнать N файлов пакета» (N вызовов decide под капотом, прогресс в
карточке поллингом). Стоимость контролируется гейтом выше; дефолтный
scope — «только размеченные файлы».

## 7. UX чата: против нейрослопа, за наглядность

Принципы (NN/g, generative UI, трёхслойная раскрываемость):

1. **Карточки вместо прозы.** Ответ по делу — карточка действия; текст —
   1–3 строки вывода. «Почему» — сворачиваемый блок (Layer 2), полный
   трейс инструментов — Layer 3 (к «Рассуждению» добавить сворачиваемый
   «Шаги»).
2. **Кликабельные quick-chips** после ответа ассистента (не только статичный
   welcome): «Разобрать прогон», «Что разметить дальше», «Предложи правку
   вопроса №3», «Сравни модели». Контекстные: пустой проект / есть
   результаты без разметки / есть разметка — три разных набора (§4.2).
3. **Page-awareness на виду**: чип в шапке панели — «Страница: Пакет ·
   8 файлов · 2 модели · разметка 14». Снимает недоверие «бот не знает,
   что я смотрю».
4. **Ссылки-подсветки**: упоминания «вопрос №3», «файл resume.pdf»,
   «прогон Qwen» — кликабельны, скроллят и подсвечивают элемент в основном
   UI (`flash()`/help-highlight уже есть).
5. **Diff везде одинаковый**: контекст получает настоящий построчный diff
   (сейчас два текста ≤500 симв. рядом, CONTEXT_PREVIEW=500 — нечитаемо).
6. **Не автоскроллить** ленту при длинном стриминге, если пользователь
   проскроллил вверх (сейчас безусловный scrollTop=scrollHeight,
   assistant.js:219). Правило: автоскролл только если пользователь «внизу»
   (порог ~40px) или нажал отправить сам.
7. **Без новых шкал**: вердикты остаются бинарными ✓/✗/? (рекомендация
   evals FAQ); никаких композитных «скоров качества модели» — только
   счётчики ошибок по категориям с drill-down.
8. **Мультиязычность**: промпт и карточки на русском, материалы любые —
   таксономия (4.1) именует категории на языке материалов, если их >50%
   не на русском (инструкция в промпте, не отдельный механизм).

## 8. Чего сознательно НЕ делаем

- **LLM-as-judge для выводов без ground truth**: ассистент не выносит
  вердиктов «прогон хороший/плохой» по неразмеченному на основании только
  собственного мнения модели — такой судья наследует слабости модели и
  требует валидации 100+ ручными метками (EvalGen, FAQ). Вместо этого:
  кандидаты на разметку (4.2), предразметка-suggestions с подтверждением
  человеком (4.3) и дельта на размеченных (5.2). **Предразметка как
  продуктовый сценарий (корпуса, интервью, исследования) — поддерживается
  (§4.3, §1.1)**: это верифицируемая человеком петля, а не автономный судья.
- **Автооптимизация промптов по типу DSPy/MIPRO** — длительные циклы без
  человека: против философии продукта и взрывает время. What-if —
  только с выводом и гейтами.
- **Версионирование веток диалога** (Hex-style) — overkill; достаточно
  persist истории (3.6) и undo на карточках.
- **Классификатор-гейт действий** — LLM-фильтр «спрашивать ли апрув» —
  best-effort, не граница; гейты жёсткие, в коде (§6).
- **Расширение разметки шкалами** — см. 7.7.
- **Vision chat-модели (3.7) и матрица покрытия (5.5)** — отложены, не
  отменены.

## 9. Технический план (волны)

**Волна 1 — фундамент (S–M):**
- снапшот: trace решений (3.1), распределения размеченных (3.2), метрики
  (3.3), стабильные id вопросов (5.3.1), бюджет 8000 для 32k (3.8);
- инструмент детализации single (3.4);
- превалидация карточек (3.5);
- persist чата с версионированием и усечением (3.6);
- **локальная дельта правок правил на размеченных (5.2-дешёвая + 5.4)** —
  без прогонов, главный быстрый выигрыш;
- quick-chips (7.2), чип page-awareness (7.3), построчный diff контекста
  (7.5), стоп автоскролла (7.6).
Тесты: поля снапшота и бюджет обрезки, валидация карточек, persist ленты
(миграция формата), дельта-пересчёт правил на фикстурах.

**Волна 2 — анализ и пакеты (M):**
- карточка «Разбор прогона» (4.1): детерминированные метрики кодом +
  именование моделью, связка чат↔UI-подсветкой (7.4);
- очередь кандидатов (4.2) + холодный старт;
- предразметка-suggestions (4.3): `source: "assistant"` в review.js,
  визуальное отличие, подтверждение/отклонение;
- пакеты с per-section accept и композитным undo (5.1) + деградация на
  слабых моделях (замер на реальных, потом allowlist);
- обновление тура: шаги про разбор прогона и пакеты (обязательно по
  конвенции проекта).

**Волна 3 — агентность (M–L):**
- what-if по размеченным целям с дельтой (5.2-дорогая) — после обкатки
  дешёвой дельты;
- гейты стоимости + карточка-план (6);
- start/stop_model с асинхронным ожиданием (6.1);
- batch what-if (6.2);
- vision-конфигурация (3.7) — если появится сильная chat+vision модель.

Каждая волна — самостоятельная ценность и отдельный релиз. ARCHITECTURE.md
обновляется в каждой волне (новые поля снапшота, инструменты, SSE-события).

**Принцип реализации карточек:** визуальный дизайн каждой новой карточки
(разбор прогона, план, дельта, suggestions) перед массовым написанием кода
показывается пользователю на живом экране/скриншоте для апрува — наглядность
виджетов исторически главный источник переделок, ловим это на макете, а не
после реализации.

## 10. Метрики успеха

- Доля предложений ассистента, принятых пользователем (accept/reject
  карточек логируются в persist, локально — механизм: счётчики по kind,
  без содержимого).
- Доля принятых без правок предразметок-suggestions (4.3) — качество
  предразметки как продуктового сценария.
- Доля ответов, где вывод дан карточкой, а не прозой (эвристика: наличие
  SSE-событий proposal/trial/analysis в ответе).
- Число апрув-диалогов на сессию — не выше 2–3 (стратификация §6).
- Субъективно: «ассистент предложил правку, которую я принял без правок».
