# Decision-QA CLI — вариант A: «человеческий» конвейер

Концепция командной утилиты `dqa` — тонкого клиента поверх HTTP API сервера
Decision-QA. Оптика проектирования: человек в терминале (ручные запуски и
shell-скрипты); AI-агенты обслуживаются через SKILL.md и машинные форматы
вывода, но не диктуют командную модель.

Дано (не перепроектируется): CLI ходит только по HTTP на сервер приложения;
креды к моделям живут на сервере; серверный `POST /api/run` даёт job +
события прогресса + отмену + частичные результаты; конфиг-пакет —
версионируемый JSON (вопросы + правила + настройки + version + hash),
экспортируемый из веба.

## 0. Имя и общий принцип

Бинарь/команда — `dqa`. Полное имя `decision-qa` слишком длинное для набора
руками (`decision-qa run ...` — 12 символов до первого пробела); `dqa` —
три. В документации и help утилита представляется как «Decision-QA CLI
(dqa)».

Главный принцип командной модели: **одна рабочая лошадка `dqa run`**, всё
остальное — служебные субкоманды. Нет отдельных `decide` / `batch` /
`moderate` — режим (одиночный/пакетный) определяется входом, а не глаголом.
Это снимает с пользователя решение «какой командой я это запускаю» и
гарантирует, что команда, отлаженная на одном файле, работает на тысяче
файлов без изменений — только больше позиционных аргументов.

## 1. Командная модель

```
dqa run [МАТЕРИАЛ ...] --config pack.json [флаги]   # основной прогон
dqa packs [--json]                                   # список конфиг-пакетов из реестра сервера (позже)
dqa pack show <id|файл>                              # сводка по пакету: вопросы, исходы, модели, hash
dqa models [--json]                                  # модели сервера и их статус (обёртка /api/health)
dqa config set|get|list|path                         # адрес сервера, токен
dqa doctor                                           # диагностика: сервер, пакет, модели
dqa version                                          # версия CLI и сервера, совместимость
```

Почему субкоманды, а не «всё флагами корневой команды»: discoverability —
`dqa --help` показывает карту возможностей, `dqa run --help` — полный список
флагов прогона. Это модель `gh`/`docker`, а не `curl`.

### `dqa run` — флаги

Позиционные аргументы — пути к материалам (файлы). Ноль позиционных
аргументов + нет флагов ввода ⇒ читаем stdin (или ошибка, если stdin — TTY,
с подсказкой).

| Флаг | Дефолт | Назначение |
|---|---|---|
| `--config PATH` | **обязателен** | конфиг-пакет (JSON из веба). `-` = из stdin |
| `--doc ID` | — | вместо `--config`: пакет из серверного реестра (позже) |
| `--mode decisions\|fast_batch\|both` | из пакета | режим прогона; `both` = два прохода |
| `--threads N` | серверный дефолт | параллелизм на сервере |
| `--glob PATTERN` | — | расширение позиционных директорий (см. §2) |
| `--recursive` / `-r` | off | рекурсивный обход директорий |
| `--files-from FILE` | — | список путей из файла; `-` = stdin, одна строка = один путь |
| `--image IMG` (повторяемый) | — | картинки материала (≤8, лимит API) |
| `--out FILE` / `-o` | stdout | куда писать результат |
| `--format table\|json\|jsonl\|csv` | auto | формат вывода (§3) |
| `--fields a,b,c` | все | фильтрация полей ответа |
| `--outcome-filter ID[,ID]` | — | показывать/писать только материалы с этими исходами |
| `--fail-on ID[,ID]` | — | exit 10, если хоть один материал получил исход (§4) |
| `--on-partial continue\|abort` | continue | поведение при ошибках отдельных материалов |
| `--dry-run` | off | разобрать вход, показать план (N материалов, M моделей, пакет), не гонять |
| `-q` / `--quiet` | off | только код выхода и (при ошибках) stderr |
| `-v` / `--verbose` | off | прогресс с деталями, трассировка HTTP при ошибках |
| `--no-progress` | auto | отключить индикатор прогресса (нужен для логов cron) |
| `--server URL`, `--token T` | из конфига/env | переопределение точки подключения |

Дефолт `--format auto`: stdout — TTY ⇒ `table`; stdout — пайп/файл ⇒
`jsonl`. Это конвенция gh/docker: человек видит таблицу, скрипт получает
поток JSON без лишнего флага. Прогресс и диагностика — всегда в stderr,
результат — всегда в stdout: `dqa run ... > out.jsonl` ничего не портит.

Одиночный режим — частный случай: один материал ⇒ в таблице одна строка, в
JSON — объект, а не массив из одного элемента (скрипту не нужно знать,
пакетный это был запуск или нет: `jsonl` всегда поток строк, `json` —
объект для 1 материала и массив для N).

## 2. Ввод материалов

Четыре вида входа, маппинг на варианты из пресетов (`backend/presets/`):

| Пресетный вариант | Как в CLI |
|---|---|
| Одиночный текст (`resume_screening.json`: поле `input`) | `dqa run resume.txt --config pack.json` или `cat resume.txt \| dqa run --config pack.json` |
| Картинки (`batch_photo_moderation.json`: `files[].image`, ≤8, base64/data URL) | `dqa run --image a.png --image b.jpg --config pack.json` |
| Пакет файлов (`batch_resume_screening.json`: 10 резюме) | `dqa run resumes/ --glob '*.txt' --config pack.json` |
| Текст + картинки (vision-материал с подписью) | `dqa run post.txt --image p1.png --image p2.png --config pack.json` |

Правила:

- **Пути как позиционные аргументы.** Директория среди аргументов
  разворачивается по `--glob` (дефолт `*` без `-r`, `**/*` с `-r`).
  Глоб разворачивает CLI, а не shell — на Windows шелл глобы не разворачивает,
  поэтому `--glob` обязателен как первоклассный механизм, а не костыль.
- **stdin**: `dqa run --config pack.json < interview.txt` или
  `... | dqa run - --config pack.json`. Явный `-` тоже принимается
  (конвенция tar/curl). Из stdin нельзя прочитать и материал, и пакет
  одновременно — `--config -` и материал из stdin несовместимы, CLI сообщает
  об этом явно.
- **`--files-from list.txt`**: один путь на строку, `#` — комментарий,
  пустые строки пропускаются. `--files-from -` читает список из stdin
  (тогда материалы из stdin брать нельзя). Нуль-терминированный ввод —
  `--files-from - --null` для связки с `find -print0`.
- **Картинки**: `--image` применяется к текущему материалу. Пакетный режим
  по картинкам: `dqa run photos/ --glob '*.png' --config pack.json` — каждый
  файл-картинка = один материал с одним изображением. Связка «текст + до 8
  картинок как один материал» доступна только в одиночном режиме (в пакетном
  нечем задать группировку — сознательное ограничение, не баг; кто хочет
  пакеты мульти-изображений — тот пишет манифест `--files-from` в формате
  JSON-строк, см. «Отвергнутые альтернативы»).
- **Смешение**: текстовые файлы и картинки в одном позиционном списке
  определяются по расширению/MIME (`.txt/.md/.json` → текст; `.png/.jpg/
  .jpeg/.webp/.gif` → изображение). Неизвестное расширение — ошибка с
  подсказкой про `--image` или переименование. HEIC сразу отвергается текстом
  ошибки, дословно повторяющим серверный («сконвертируйте в JPEG»).
- Дедупликация и сортировка путей — всегда (предсказуемый порядок вывода
  важнее порядка аргументов командной строки).
- `--dry-run` печатает итоговый список материалов до отправки — дешёвая
  страховка от «я прогнал не ту папку на 10k файлов».

Base64-кодирование, лимиты (8 изображений, ~20 МБ суммарно — из
`backend/schemas.py:11-12`) проверяются на клиенте до отправки: ошибка «у
вас 9 изображений» должна прийти мгновенно, а не после установления job'а.

## 3. Вывод

### Содержимое записи результата (на материал)

```json
{
  "file": "resumes/smirnov.txt",
  "outcome": {"id": "invite", "label": "Пригласить"},
  "answers": {"stack_fit": {"yes": 0.87, "no": 0.13}, "...": "..."},
  "models": {"clef-local": {"duration_s": 1.2, "label_mass_min": 0.71}},
  "error": null
}
```

Поле `outcome` — результат применения правил пакета к ответам; `answers` —
вероятности по вопросам (агрегат по моделям); `models` — помодельная
разбивка (совпадает по смыслу с `results` из `POST /api/decide`).

### Форматы

- `table` (дефолт в TTY): колонки `ФАЙЛ | ИСХОД | УВЕРЕННОСТЬ | МОДЕЛИ |
  ВРЕМЯ`. Исход подсвечен цветом из пакета (`color` в outcomes: green/red/
  yellow → ANSI). При `--verbose` после таблицы — блок ответов по вопросам
  с вероятностями. Таблица никогда не идёт в пайп (auto переключает на
  jsonl) — парсить таблицу скриптом должно быть невозможно по построению.
- `json`: один объект (один материал) или массив. Для ручного разбора и
  `jq`.
- `jsonl`: одна строка на материал, **пишется по мере готовности** (сервер
  стримит события `/api/run`) — скрипт видит первые результаты, не дожидаясь
  конца прогона. Дефолт в пайпах и рекомендованный для агентов.
- `csv`: плоская проекция `file,outcome_id,outcome_label,<по одной колонке
  на вопрос: top-ответ и его вероятность через «:»>`. Для Excel/аналитиков.
  Вопросы с типом score — числовое значение уровня.

`--fields file,outcome,answers.stack_fit` — точечная фильтрация (dot-path),
работает для json/jsonl/csv. `--outcome-filter reject,review` — отбрасывает
записи (удобно: «покажи только проблемные»).

`--out results.jsonl` пишет в файл; stdout остаётся свободен для прогресса…
нет — прогресс всегда stderr, поэтому `-o` нужен в основном для `table`
(красивый вывод в терминал + машинный файл одновременно:
`dqa run ... -o r.jsonl --format table` пишет таблицу в терминал и jsonl в
файл? **Нет** — один `--format`, один поток; для двух представлений —
`--tee FILE`, который дублирует запись в jsonl независимо от основного
формата. Это честнее, чем перегружать `-o`).

### Прогресс

В TTY — одна перерисовываемая строка stderr:
`[■■■□□□□□□□] 34/120 · clef-local ×4 потока · ETA 2м10с · ошибок: 1`.
В не-TTY прогресс молчит автоматически (`--no-progress` — для принудительной
тишины в логах cron; `-v` в не-TTY печатает построчный лог
`OK smirnov.txt → Пригласить (0.9с)` в stderr).

## 4. Встраивание в пайплайны

### Коды выхода

| Код | Значение |
|---|---|
| 0 | Всё обработано, `--fail-on` не сработал |
| 1 | Ошибка исполнения: сервер недоступен, модель не запущена, HTTP 5xx, таймаут |
| 2 | Ошибка использования: неизвестный флаг, нет входа, взаимоисключающие флаги (конвенция CLI, как у grep/git) |
| 3 | Частичный результат: часть материалов завершилась ошибкой (при `--on-partial continue`) |
| 4 | Конфиг-пакет невалиден: битый JSON, несовместимая version, hash не сошёлся |
| 10 | Сработал `--fail-on`: хотя бы один материал получил перечисленный исход |
| 130 | Прервано пользователем (Ctrl+C); job на сервере отменяется, частичные результаты всё равно пишутся |

### Реакция скрипта на решение: почему `--fail-on`, а не exit-код по исходу

Вариант «exit-код = исход» отвергнут: (а) исходов произвольное число и их id
— пользовательские строки из пакета, стабильного отображения «исход → код»
нет; (б) в пакетном прогоне у N материалов N исходов — один код не выразить;
(в) коды >2 в shell теряют смысл «ошибка/не ошибка», ломая `set -e`.

Выбрано: **`--fail-on <id[,id]>` → exit 10**. Семантика «прогон успешен, но
политика нарушена» отделена от «прогон сломался». Скрипт читает:

```bash
if dqa run new_posts/ --config mod.json --fail-on reject,needs_review -q; then
  echo "всё чисто"
elif [ $? -eq 10 ]; then
  notify-reviewers   # исходы reject/needs_review есть — это не сбой
else
  alert-oncall       # коды 1-4: сбой конвейера
fi
```

Для тонкой логики — `jsonl` + `jq`: исходы, вероятности, помодельная
разбивка доступны без парсинга текста. `--on-outcome <id>=<команда>`
(запуск произвольной команды на исход) отвергнут — CLI не должен быть
планировщиком, это работа shell по выводу jsonl.

### Частичные ошибки и идемпотентность

`--on-partial continue` (дефолт): материал с ошибкой получает запись с
`"error": "..."`, прогон доезжает, exit 3. `--on-partial abort`: первая
ошибка материала отменяет job (exit 1). Ошибка **запуска** (сервер лежит)
— всегда фатальна, exit 1, никакого continue.

Идемпотентность: прогон чисто вычислительный, побочек нет — повторный запуск
безопасен по построению. Для «догнать упавшее» — не resume-файлы состояния
(отвергнуто: CLI без состояния), а фильтрация входа снаружи:

```bash
dqa run batch/ --config p.json -o r1.jsonl || true   # часть упала
comm -23 <(ls batch/*) <(jq -r .file r1.jsonl | sort) > todo.txt
dqa run --files-from todo.txt --config p.json -o r2.jsonl
```

Это прозрачно и не требует от CLI понятия «сессия». Пакетный файл
результатов атомарен: пишется во временный файл и переименовывается, чтобы
cron не прочитал половину JSON.

## 5. Многопоточность

`--threads N` — проброс параметра в `POST /api/run`; потоки живут на
сервере, клиент лишь подписывается на события. Дефолт — **не зашит в CLI**:
пустое значение = «как настроено на сервере» (сервер знает свои модели и
RAM, клиент — нет). `--threads` без значения запрещён, диапазон 1–32
валидируется на клиенте.

В прогрессе: `×4 потока`. В jsonl-записи поле `models.<key>.duration_s`
уже отражает реальную скорость; агрегат `files/min` печатается в финальной
строке stderr: `Готово: 118/120 за 3м04с (38.4/мин), ошибок: 2 → exit 3`.

## 6. Конфигурация CLI

Приоритет (сверху вниз): флаг → env → конфиг-файл → дефолт.

- Флаги: `--server`, `--token`.
- Env: `DQA_SERVER_URL`, `DQA_TOKEN`.
- Файл: `~/.config/dqa/config.toml` (Linux/macOS),
  `%APPDATA%\dqa\config.toml` (Windows). Права 600 при создании через
  `dqa config set`. Формат TOML, секции-профили:

```toml
default_profile = "work"
[profile.work]
server = "http://qa.internal:8000"
token = "dqa_..."
[profile.local]
server = "http://localhost:8000"
```

Профиль выбирается `--profile work` / `DQA_PROFILE`. Дефолт без конфига:
`http://localhost:8000`, без токена.

Что хранится: **только адрес сервера и токен доступа к самому серверу**
(если у сервера включена авторизация). Креды к LLM остаются в
`backend/credentials.json` на сервере — локально секретов моделей нет и не
может появиться: CLI физически не имеет команд, которые бы их принимали.
`dqa config list` маскирует токен (`dqa_…f3a9`).

## 7. Установка и кроссплатформенность

Утилита едет **в том же релизном zip**, что и приложение
(`scripts/build_release.sh`, `dist/decision-qa-{mac-arm64,windows}.zip`):
каталог `cli/` с пакетом `dqa` (чистый Python ≥3.10, зависимости: `httpx`,
`tomllib` из stdlib — то есть одна внешняя зависимость) + шимы `dqa`
(shell) и `dqa.cmd` (Windows), вызывающие `python -m dqa`. Установка:
распаковать, добавить в PATH. Версия CLI = `VERSION` проекта, релизный
цикл общий.

Почему не отдельный PyInstaller-бинарь: серверная часть и так требует Python
на машине установки (приложение из того же zip), размер бинаря 20+ МБ против
~100 КБ кода, плюс две сборочные цепочки вместо нулевой. `pipx install
decision-qa-cli` из PyPI — задел на потом, когда пакет стабилизируется;
сейчас оверинжиниринг для внутреннего инструмента.

Требования: Windows 10+ (PowerShell 5+/cmd — шим на оба), macOS 13+ arm64,
Python 3.10+, сеть до сервера. `dqa doctor` проверяет всё это одной
командой.

## 8. Ошибки и диагностика

Принцип: текст ошибки = что случилось + что с этим делать. Примеры честных
текстов:

- Сервер недоступен: `Не удаётся подключиться к http://qa.internal:8000
  (connection refused). Проверьте, что сервер запущен, или смените адрес:
  dqa config set server <url>.` — exit 1.
- Модель не запущена (409 от сервера): `Модель clef-local не запущена на
  сервере. Запустите её в веб-интерфейсе или: curl -X POST
  .../api/models/clef-local/start` — exit 1.
- Битый пакет: `Конфиг-пакет mod.json: невалидный JSON (строка 42:
  ожидалась запятая). Переэкспортируйте пакет из веб-интерфейса.` — exit 4.
  Несовпадение `hash` пакета: отдельное сообщение «пакет изменён после
  экспорта» — exit 4 (а не молчаливый прогон: для продакшн-пайплайна
  целостность конфигурации важнее удобства).
- Несовместимость версий: `Пакет собран для версии сервера ≥0.9, сервер —
  0.7. Обновите сервер или переэкспортируйте пакет.` — exit 4.
- Нет входа: `Не указаны материалы и stdin пуст. Примеры: dqa run file.txt
  --config p.json | dqa run dir/ --glob '*.txt' --config p.json` — exit 2.

`-v` добавляет HTTP-трасса (метод, URL, статус, тело ошибки сервера) —
достаточно для баг-репорта без перепроса «а что там было». Traceback Python
пользователь не видит никогда, кроме как с `--debug` (скрытый флаг).

## 9. SKILL.md для AI-агентов

Файл `cli/skills/dqa/SKILL.md`, едет в zip рядом с CLI. Набросок:

```markdown
---
name: dqa
description: Прогон материалов через Decision-QA — вероятностные ответы на
  вопросы и детерминированное решение (исход) по каждому материалу.
  Применять, когда нужно классифицировать/отмодерировать файлы, тексты или
  изображения по готовому конфиг-пакету Decision-QA.
---

# dqa — Decision-QA CLI

## Когда применять
- Пользователь просит «прогнать/проверить/отмодерировать» файлы по пакету.
- В пайплайне нужен исход (Принят/Отклонён/Требует разбора) по материалу.

## Предусловия
- Доступен сервер Decision-QA: проверка `dqa doctor` (exit 0 = готов).
- Есть конфиг-пакет (pack.json) или id из реестра (`dqa packs`).

## Команды
- Один материал из stdin: `cat f.txt | dqa run --config pack.json --format json`
- Папка: `dqa run DIR --glob '*.txt' --config pack.json --format jsonl -o out.jsonl`
- Реакция на исход: `--fail-on reject,needs_review` → exit 10
- Только проблемные: `--outcome-filter needs_review`

## Коды выхода
0 ок · 1 сервер/модель недоступны · 2 ошибка вызова · 3 часть материалов
с ошибкой · 4 пакет невалиден · 10 сработал --fail-on

## Правила для агента
- Всегда `--format jsonl` (или json для одного файла) и `--no-progress`.
- Исход читать из поля `outcome.id`, не парсить label.
- Exit 3 ≠ сбой: разобрать записи с `"error"` и решить по контексту.
- Не повторять запрос в цикле при exit 1 — сначала `dqa doctor`.
```

## 10. Примеры сеансов

Разработчик отладил пакет в вебе, гоняет папку:

```bash
dqa run ~/interviews/ --glob '*.txt' --config packs/support-qa.json --threads 8
```

Проверка одного файла из stdin, машинный ответ:

```bash
cat appeal.txt | dqa run --config packs/support-qa.json --format json | jq .outcome.label
```

Ночной cron: результаты в файл, алерт при «Требует разбора», тишина в логе:

```bash
15 3 * * * dqa run /incoming --config /etc/dqa/moderation.json \
  --fail-on needs_review -q --no-progress -o /var/dqa/$(date +\%F).jsonl \
  || [ $? -eq 10 ] && /usr/local/bin/notify-review
```

Агент в пайплайне: по одному материалу, реакция по полю исхода:

```bash
dqa run post.txt --image photo1.jpg --config pack.json --format json --no-progress \
  | jq -e '.outcome.id == "accept"' >/dev/null && ./publish.sh post.txt
```

Картинки без текста (модерация фото):

```bash
dqa run photos_2026-10/ --glob '*.jpg' --config packs/photo-mod.json \
  --outcome-filter reject --format csv -o rejected.csv
```

Догон упавшего пакета:

```bash
dqa run batch/ --config p.json -o run.jsonl || true
dqa run --files-from <(comm -23 <(ls batch/* | sort) \
  <(jq -r 'select(.error == null) | .file' run.jsonl)) --config p.json >> run.jsonl
```

Диагностика перед внедрением в пайплайн:

```bash
dqa config set server http://qa.internal:8000 && dqa doctor && dqa pack show packs/mod.json
```

Сухой прогон перед большой папкой:

```bash
dqa run /data/ugc --recursive --glob '*.txt' --config p.json --dry-run
# План: 12 481 материал × 1 модель (clef-local), пакет «Модерация UGC» v3 (hash ok)
```

## Отвергнутые альтернативы

- **Отдельные команды `dqa decide` / `dqa batch`.** Режим определяется
  входом; две команды — двойной help, двойные тесты и переключение команды
  при росте объёма. Единый `run` масштабируется бесплатно.
- **Exit-код = исход решения.** Исходы — произвольные пользовательские id,
  пакет даёт N исходов на N материалов; семантика «ошибка процесса»
  смешивается с «политика сработала». Вместо этого `--fail-on` → exit 10
  (§4).
- **`--on-outcome id=команда` (запуск произвольных команд).** CLI становится
  планировщиком с экранированием, состоянием и отладкой чужих скриптов.
  Та же задача решается jsonl + shell за три строки.
- **Resume-состояние прогонов в CLI (`~/.dqa/state`).** Клиент без состояния
  проще и честнее; «догон» делается фильтрацией входа снаружи (§4). Если
  появится серверный job-реестр с resume — пересмотреть.
- **Автоопределение «пакета материалов из нескольких картинок» по
  манифесту в первой версии.** Мульти-изображение — только одиночный режим;
  для пакетов мульти-изображений нужен манифест-формат (JSON-строки через
  `--files-from --manifest`), который стоит проектировать отдельно, когда
  появится реальный кейс.
- **PyInstaller-бинарь и PyPI-пакет на старте.** Двойная сборка и релизный
  цикл вне zip проекта; целевая машина и так имеет Python из того же
  релиза (§7).
- **Формат вывода YAML.** Третий зависимый пакет ради формата, который
  проигрывает json/jq в пайплайнах; человеку достаточно table.
- **Интерактивный wizard (`dqa run` без аргументов задаёт вопросы).**
  Конвейерный инструмент не должен иметь модальности; discoverability
  решается `--help`, `--dry-run` и текстами ошибок.
- **Конфиг-пакет по умолчанию (`~/.config/dqa/default.pack`).** Скрытый
  дефолт для главного входа прогона делает cron-пайплайны
  невоспроизводимыми: `--config` обязателен всегда, это осознанная цена.

## Открытые вопросы (к серверной части)

- Авторизация сервера: сейчас API без токена; `DQA_TOKEN` проектируется
  впрок, нужен серверный middleware до выкатки CLI в организации.
- `POST /api/run`: формат событий прогресса (SSE vs polling) влияет только
  на транспорт клиента, не на командную модель — документ совместим с обоими.
- `--doc <id>` и `dqa packs` ждут серверного реестра пакетов.
