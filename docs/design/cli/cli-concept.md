# Decision-QA CLI — единая концепция (синтез вариантов A и B)

> Финальный документ конкурса концепций. База — вариант B («машина в
> пайплайне»); из варианта A перенесены командная эргономика человека,
> `--glob`, неявный stdin, `dqa doctor`, тексты ошибок и фазированная
> дистрибуция. Оба критических разбора учтены; варианты A и B остаются в
> `docs/design/cli/` как история.
>
> Данности (не перепроектируются): CLI — тонкий HTTP-клиент поверх сервера
> Decision-QA; креды к моделям живут только на сервере (`backend/credentials.json`),
> автономного режима нет; серверный `POST /api/run` даёт job + события
> прогресса + отмену + частичные результаты; конфиг-пакет — версионируемый
> JSON (вопросы + правила + настройки + `version` + `hash`), экспорт из веба.
> Данности, которых на сервере пока **нет** (движок решений, формат пакета,
> сам `/api/run`, capabilities, auth), вынесены в раздел «Зависимости от
> сервера» — это блокеры, а не сноски.

---

## 1. Целевая аудитория и оптика

CLI `dqa` — конвейерный шаг: CI, cron, shell-скрипты, AI-агенты. Это
первичный пользователь, и он диктует контракты: версионируемая схема
вывода, разнесённые exit-коды, идемпотентность, наблюдаемость. Вторичный
пользователь — разработчик-аналитик, только что отладивший вопросы и
правила в веб-мастерской: он пришёл *взглянуть* на результат по 50
интервью глазами и получить честную подсказку при ошибке в 3 часа ночи.
Его обслуживают опциональная TTY-таблица, `dqa doctor`, `dqa pack show`
и тексты ошибок стиля «что случилось + что делать» — но ни один из этих
«человеческих» механизмов не просачивается в машинные контракты.

Инварианты, которые не нарушает ни одна фича:

1. stdout — только данные (JSON/NDJSON/CSV/table); stderr — только
   прогресс и диагностика. Потоки не смешиваются никогда.
2. Форма JSON-результата не зависит от числа материалов: один файл и
   сто тысяч файлов дают документ одной схемы с `files[]` (никакого
   shape-shifting «объект vs массив»).
3. Команда, отлаженная на одном файле, работает на тысяче без изменений.
4. Креды моделей физически не могут появиться на клиенте: нет ни одной
   команды, которая бы их принимала.

## 2. Командная модель

Одна рабочая лошадка — `dqa run`; режим (одиночный/пакетный) определяется
входом, а не глаголом. Остальное — служебные субкоманды (модель
`gh`/`docker`: `dqa --help` — карта возможностей).

```
dqa run [МАТЕРИАЛ ...] --config pack.json [флаги]   # основной прогон
dqa validate [МАТЕРИАЛ ...] --config pack.json      # проверка входа и пакета без прогона (dry-run)
dqa explain <path> --report r.json                  # почему материалу вынесено такое решение (локально, из отчёта)
dqa diff r1.json r2.json                            # сравнение двух прогонов (A/B пакетов, локально)
dqa pack show <pack.json>                           # сводка пакета: вопросы, id исходов, модели, hash
dqa config init|set|show                            # клиентская конфигурация (сервер, профили)
dqa doctor                                          # диагностика среды и сервера одной командой
dqa version                                         # версии CLI/схемы + совместимость с сервером
```

### 2.1 Флаги `dqa run`

| Флаг | Дефолт | Смысл |
|---|---|---|
| `--config pack.json` | **обязателен** | конфиг-пакет из веба (вопросы+правила+hash); `--config -` — пакет из stdin |
| `--mode decisions\|fast_batch\|both` | **из пакета** (fallback `decisions`) | режим прогона; пакет — источник истины о задаче |
| `--threads N` | **серверный дефолт** | желаемый параллелизм на сервере; без флага клиент не передаёт значение (§7) |
| `--glob PATTERN` | `*` (с `-r` — `**/*`) | разворачивание директорий самим CLI — первоклассный механизм ради Windows (§3) |
| `--recursive, -r` | off | рекурсивный обход директорий |
| `--files-from FILE [--null]` | — | список путей из файла (`-` = stdin), `--null` — NUL-терминированный (`find -print0`) |
| `--manifest FILE` | — | JSON-манифест: группировка «текст + до 8 картинок» в один материал (§3) |
| `--image IMG` (повторяемый) | — | картинки одиночного материала (с путём/stdin-входом) |
| `--stdin`, `-` | неявный при пустом входе | один текстовый материал из stdin; `--name STR` задаёт имя (дефолт `stdin`) |
| `--format json\|ndjson\|csv\|table` | `json` | формат вывода; `table` — только в TTY (§4) |
| `--output, -o FILE` | `-` (stdout) | файл результата, атомарная запись |
| `--report PATH` | — | полный JSON-отчёт на диск независимо от stdout (§6.4) |
| `--fields a,b,c` | все | dot-path проекция per-file (экономия контекста агента) |
| `--outcome-filter ID[,ID]` | — | оставить в выводе только файлы с перечисленными исходами |
| `--fail-on LIST` | `error` | исходы, дающие exit 10 (§5.2); id валидируются против пакета до прогона |
| `--skip-processed FILE` | — | идемпотентность между прогонами, ключ = content+config hash (§6.3) |
| `--no-dedup` | off | отключить дедуп по content-hash внутри прогона |
| `--timeout SEC` | `0` = без лимита | общий дедлайн клиента; истёк → exit 75 (§6.1) |
| `--retry N` | `2` | ретраи транспорта/5xx с backoff (§6.1) |
| `--encoding utf-8\|cp1251` | `utf-8` | детерминированная кодировка входных текстов (§3.3) |
| `--quiet` / `--verbose` | off | уровень stderr |
| `--profile NAME`, `--server URL` | конфиг/env | точка подключения (§8); **`--token` не существует** — токен только env/файл (§8.2) |
| `--dry-run` | off | алиас `dqa validate` для тех же аргументов |

### 2.2 Неинтерактивность и discoverability

CLI всегда неинтерактивен: ни одна команда не задаёт вопросов; ввод ждёт
только явный/неявный stdin. Интерактивный prompt в CI = зависший job.
Удобство первого запуска решается явно вызванными `dqa config init` и
`dqa doctor`, а не модальностью `run`. Недостающий обязательный параметр
→ exit 64 с именем флага и примером вызова.

### 2.3 Тексты ошибок: «что случилось + что делать»

Стиль, перенесённый из варианта A (его лучший раздел), — обязателен для
всех ошибок клиента. Примеры нормы:

- `Не удаётся подключиться к http://qa.internal:8000 (connection refused).
  Проверьте, что сервер запущен, или смените адрес: dqa config set …` — exit 69.
- `Модель clef-local не запущена на сервере. Запустите её в веб-интерфейсе
  (менеджер моделей) и повторите.` — exit 69 (серверный 409 mid-run → per-file error).
- `Конфиг-пакет mod.json изменён после экспорта: hash не сошёлся.
  Переэкспортируйте пакет из веб-интерфейса.` — exit 65.
- `Не указаны материалы и stdin пуст. Примеры: dqa run file.txt --config p.json ·
  dqa run dir/ --glob '*.txt' --config p.json` — exit 64.
- `--fail-on rewiew: в пакете нет исхода "rewiew". Исходы пакета: invite,
  reserve, reject (см. dqa pack show pack.json).` — exit 64.

Traceback Python пользователь не видит никогда, кроме скрытого `--debug`.
`-v` добавляет HTTP-трассу (метод, путь, статус, latency, тело ошибки
сервера) — достаточно для баг-репорта без перепроса.

### 2.4 Политика совместимости контрактов

Семвер раздельно для трёх контрактов: (а) флаги и exit-коды CLI,
(б) JSON-схема результата (`schema`), (в) минимальная версия сервера.
Внутри мажорной версии поля JSON **только добавляются** (потребитель
обязан игнорировать неизвестные поля — это правило зашито в SKILL.md);
удаление/переименование поля или смена семантики exit-кода = новая
мажорная `schema`. Перед прогоном клиент сверяет свою `schema` с
диапазоном сервера (capabilities, §12.4): вне диапазона → exit 69 до
старта с текстом «обновите CLI до ≥X / сервер до ≥Y». Устаревший флаг =
deprecation warning в stderr минимум один мажорный цикл, потом отказ с
подсказкой. Потребители никогда не парсят stderr и таблицу — парсинг
человеческих форматов исключён по построению.

## 3. Ввод

### 3.1 Источники входа

1. **Позиционные пути** — файлы и директории. Директория разворачивается
   по `--glob` (дефолт `*`, с `-r` — `**/*`). Глоб разворачивает **CLI, а
   не shell**: на Windows шелл глобы не разворачивает, поэтому `--glob` —
   первоклассный механизм, а не костыль. Поддерживаемые типы: тексты
   `.txt .md .json` (json = материал-объект, как `input: dict|list` в
   `DecideRequest`, `backend/schemas.py:71`), картинки
   `.png .jpg .jpeg .webp .gif`. Файл-картинка = один материал с одним
   изображением (как `files[].image` в пресете `batch_photo_moderation.json`).
   Неизвестное расширение → ошибка с подсказкой. HEIC отвергается текстом,
   дословно повторяющим серверный (`backend/schemas.py:111-114`).
2. **stdin**: `cat f.txt | dqa run --config p.json` — неявно (ноль
   позиционных аргументов + stdin не-TTY); явные формы `-` и `--stdin`
   принимаются равноправно (явный `--stdin` — самодокументируемая форма
   для агентов и SKILL.md). Имя материала — `--name`, дефолт `stdin`.
   Из stdin нельзя одновременно читать материал и пакет (`--config -`) —
   CLI сообщает об этом явно. Картинки через stdin не поддерживаются
   (бинарь в пайпе — источник порчи данных); для одиночного vision-материала
   — `--image`: `dqa run post.txt --image p1.png --image p2.png --config p.json`.
3. **`--files-from list.txt`** — один путь на строку, `#` — комментарии;
   `--files-from - --null` — NUL-терминированный список для связки с
   `find -print0` (пути с пробелами и кириллицей не ломаются).
4. **`--manifest m.json`** — JSON-массив `{"path": …, "name": …,
   "images": ["a.png", …]}`: точный набор входов от скрипта/агента и
   группировка «текст + до 8 картинок» в один материал пакетно (то, что
   `--image` умеет только в одиночном режиме).

Пресет-формат веба (`files[]` с `content`/`image`) в CLI-ввод не
принимается: пресеты — формат мастерской, CLI работает с реальной ФС;
конфиг-пакет (`--config`) и вход разделены жёстко.

### 3.2 Валидация до прогона — `dqa validate` / `--dry-run`

Локально, без обращений к моделям: пакет валиден, `version`
поддерживается, пересчитанный `hash` совпадает с записанным (каноникализация
— §12.2); пути существуют и читаемы; лимиты картинок (≤8, ≤20 МБ base64 —
приходят из capabilities, не зашиты, §12.4) соблюдены; id исходов в
`--fail-on` существуют в пакете. Вывод — JSON-сводка: `files_total`,
`files_ok`, `files_skipped` с причинами, оценка `n_files × n_models`
инференсов, ETA и порядок токенов из калибровки сервера с честной пометкой
`estimate: true` (точный бюджет до прогона невозможен — длина генерации
неизвестна; это sanity-gate «вы точно хотите 40 000 файлов?», не биллинг).
План свыше 50 материалов печатается усечённо (первые 50 + счётчики).
Exit 0/65. Правило для всех потребителей и зашито в SKILL.md: **большой
прогон всегда предваряется validate**.

### 3.3 Битые, пустые, дублирующиеся файлы; кодировки

- **Пустой текст** → `skipped` с `reason: "empty"` (сервер отвергает
  пустой `input` без изображений, `backend/schemas.py:83-89`; клиент
  дублирует проверку, чтобы не жечь прогон).
- **Нечитаемый/битый** (ошибка чтения, битый base64 картинки) →
  `skipped` + `reason: "unreadable"`, прогон остальных продолжается.
- **Кодировка текста**: детерминированно — UTF-8 с допуском BOM
  (`utf-8-sig`); невалидный UTF-8 → `skipped`, `reason: "encoding"`, с
  подсказкой `--encoding cp1251` (типовой случай файлов с Windows-машин).
  Эвристического угадывания кодировки нет: молчаливое перекодирование —
  скрытая порча материала, детерминированность решений важнее удобства.
- **Дубликаты**: дедупликация по sha256 содержимого; повторный файл не
  уходит на модели, в результате — `skipped`, `reason: "duplicate"`,
  `duplicates_of`. `--no-dedup` отключает.
- Один битый файл никогда не роняет прогон при наличии хотя бы одного
  валидного входа. Ноль валидных входов → exit 65.

### 3.4 Очень большие папки (10⁵ файлов)

Перечисление входа — потоковое (ленивый обход, без списка 100k путей в
памяти; дедуп-множество хэшей — ~3 МБ на 100k файлов, приемлемо).
Загрузка материалов в job — чанками (§12.3), клиент никогда не собирает
одно тело в 100 МБ. `--report` при `files_total` выше порога (10 000)
автоматически пишется в NDJSON-построчном виде (или принудительно —
`--report-format ndjson`): гигабайтный цельный JSON не собирается в
памяти и не «переименовывается атомарно» наполовину. Жёсткий потолок
`max_files_per_job` приходит из capabilities; превышение → exit 65 с
текстом «разбейте вход или поднимите лимит на сервере». Авто-разбиение
на несколько job'ов осознанно отложено (§15): оно ломает корреляцию
«один прогон = один run_id».

## 4. Вывод

### 4.1 JSON-схема результата — стабильный контракт (`--format json`)

Всегда конверт, независимо от числа материалов:

```json
{
  "schema": 1,
  "run_id": "run_01JEXAMPLE…",
  "cli_version": "1.0.0",
  "server": {"url": "http://127.0.0.1:8000", "version": "1.5.0"},
  "config": {"path": "pack.json", "version": 3, "hash": "sha256:…"},
  "mode": "decisions",
  "models": ["clef-27b", "qwen3-32b"],
  "threads_effective": 4,
  "started_at": "2026-10-23T10:15:00Z", "finished_at": "…", "duration_s": 222.4,
  "summary": {"files_total": 12, "files_ok": 10, "files_failed": 1,
              "files_skipped": 1,
              "decisions": {"invite": 7, "reserve": 2, "reject": 1}},
  "files": [
    {
      "path": "inbox/resume_01_petrov.txt", "name": "resume_01_petrov.txt",
      "content_sha256": "…", "status": "ok",
      "decision": {"outcome": "invite", "label": "Пригласить",
                   "rule": "q9>=3 && q3.yes>=0.6", "is_default": false},
      "answers": {
        "q9": {"type": "score", "score": 3.71,
               "by_model": {"clef-27b": 3.6, "qwen3-32b": 3.82}},
        "q3": {"type": "yes_no", "answer": "yes", "confidence": 0.96,
               "probabilities": {"yes": 0.96, "no": 0.04},
               "by_model": {"clef-27b": {"yes": 0.93, "no": 0.07}, "…": {}}}
      },
      "usage": {"prompt_tokens": 1840},
      "metrics": {"duration_s": 18.2, "label_mass_min": 0.87},
      "errors": []
    },
    {"path": "inbox/empty.txt", "status": "skipped", "reason": "empty",
     "decision": null, "errors": []},
    {"path": "inbox/huge.png", "status": "error", "decision": null,
     "errors": [{"stage": "server", "model": "clef-27b",
                 "message": "Суммарный объём изображений больше 20 МБ"}]}
  ]
}
```

Принципы схемы:

- `decision.outcome` — **id исхода** из пакета (машинный ключ; ветвление
  скриптов только по нему, `label` — человеческое имя), `rule` — текст
  сработавшего правила (ответ «почему», §4.5).
- `answers[q]` — агрегат, пошедший в правила, плюс разрез `by_model`:
  вероятности/скор каждой модели отдельно; зеркалит per-model `answers`
  ответа `/api/decide` и фронтовое представление
  (`frontend/static/results.js:41-58`: `yes_no` → `probabilities`,
  `choice` → топ-вариант + распределение, `score` → число).
- Ошибки — **per-file массив**, не единичное поле: файл может упасть на
  части моделей и всё равно получить решение по остальным — тогда
  `status: "ok"`, но `errors` непуст, модель перечислена.
- `status`: `ok | error | skipped`; `reason` у skipped:
  `empty | unreadable | encoding | duplicate | already_processed`.
- `run_id` — сквозной корреляционный ключ с серверным журналом (§10).
- stdout всегда UTF-8, `ensure_ascii=false` (кириллица читаема в логах и
  diff'ах; потребители обязаны читать UTF-8 — правило зашито в SKILL).

### 4.2 NDJSON-поток (`--format ndjson`)

Одна строка = одно событие, по мере готовности файлов:

```
{"schema":1,"type":"run_start","run_id":"…","files_total":120,"threads_effective":4}
{"type":"file","i":1,"path":"…","status":"ok","decision":{…},"answers":{…}}
{"type":"file","i":2,"path":"…","status":"error","errors":[…]}
{"type":"run_end","summary":{…},"duration_s":…,"cancelled":false}
```

Обоснование событийной обёртки (а не «голых» записей файлов): сервер
стримит per-file события (`/api/run`, §12.3) — NDJSON честно их
проксирует; `run_start` несёт `run_id` и `threads_effective`; `run_end`
с `summary` — бесплатный контроль целостности потока (обрыв отличим от
конца); CI стримит решения в следующий шаг, не дожидаясь всей пачки;
крах посередине не портит выданные строки. Цена — обязательная
фильтрация `select(.type=="file")` у потребителя; она зафиксирована как
shape-правило №2 в SKILL.md и показана в каждом NDJSON-рецепте. Порядок
событий — по готовности (`i` — порядковый номер входа), сортировка путей
в стриме не обещается; для предсказуемого порядка — цельный `json`
(файлы отсортированы по пути).

### 4.3 CSV (`--format csv`)

Одна строка на файл: `path,status,outcome,label,confidence,<по колонке
на вопрос — краткий агрегированный ответ>,errors`. Без `by_model` (для
per-model анализа — JSON). Порядок колонок стабилен и следует порядку
вопросов в пакете; новые вопросы — в конец. Кодировка — UTF-8 с BOM
(Excel на Windows открывает кириллицу корректно только так); это
осознанное исключение из «stdout = чистый UTF-8» именно для csv.

### 4.4 Таблица (`--format table`) — опциональный человеческий формат

Колонки `ФАЙЛ | ИСХОД | УВЕРЕННОСТЬ | ВРЕМЯ`, исход подсвечен цветом из
пакета (`color` в outcomes → ANSI). Только когда stdout — TTY: в пайпе
`--format table` → ошибка с подсказкой (парсинг таблицы скриптом
невозможен по построению). ANSI отключается, если терминал не объявляет
поддержку VT (Windows cmd без VT — читаемая монохромная таблица, а не
мусор из escape-кодов). Не дефолт: дефолт всегда `json`, потому что
TTY-зависимый auto-формат — второй контракт, который надо тестировать,
а машина — первичный пользователь. Человеку после веб-мастерской таблица
важна, поэтому она есть — но по явному флагу.

### 4.5 `dqa explain` и `dqa diff` — локальные команды разбора

- `dqa explain <path> --report r.json`: из отчёта (без сервера) печатает
  по материалу исход, сработавшее правило (`decision.rule`), ответы с
  вероятностями и разрез `by_model`, ошибки. Закрывает самый частый
  вопрос мастерской «почему этому материалу такое решение» — ответ уже
  лежит в отчёте (`answers` + `rule` + `config.hash`), сервер нужен
  только для сырых ответов моделей по `run_id`.
- `dqa diff r1.json r2.json`: рабочий цикл мастерской «стало ли лучше
  после правки вопроса/правила». Джойн двух отчётов по `content_sha256`:
  таблица/JSON переключений исходов (`outcome: invite → reject`) и
  дельт ответов сверх порога. Оба отчёта должны быть полными (json или
  ndjson — формат сниффится). Типовое употребление: один вход, два
  прогона с `--config old.json` / `--config new.json`, затем `dqa diff`.

## 5. Exit-коды

### 5.1 Единая таблица

| Код | Условие | Семантика |
|---|---|---|
| 0 | Все файлы ok, политика `--fail-on` не сработала | успех |
| 2 | Есть файлы `status=error` или `skipped` с reason ∈ {empty, unreadable, encoding}; политика НЕ сработала | degraded (частичный успех) |
| 10 | Сработала политика `--fail-on` (включая псевдо-исход `error`) | «проверка не пройдена», данные полные |
| 64 | Ошибка вызова: нет `--config`, неизвестный флаг, несовместимые флаги, опечатка в `--fail-on` | EX_USAGE |
| 65 | Валидация не пройдена: битый пакет (JSON/version/hash), 0 валидных файлов, превышен лимит входа | EX_DATAERR |
| 66 | Вход недоступен: пути не существуют | EX_NOINPUT |
| 69 | Сервер недоступен / несовместимы версии схем / обрыв стрима без восстановления | EX_UNAVAILABLE |
| 70 | Внутренняя ошибка клиента / job упал целиком / манифест `--skip-processed` занят другим процессом | EX_SOFTWARE |
| 75 | Истёк `--timeout` (ретрай уместен) | EX_TEMPFAIL |
| 77 | Сервер ответил 401/403 (когда auth появится на сервере, §12.5) | EX_NOPERM |
| 130 | Прервано пользователем (Ctrl-C) — `128+SIGINT` | отмена |

Разнесение: **0/2/10 — о данных** (смотрит логика пайплайна), **≥64 — о
запуске** (смотрит on-call). Ctrl-C — именно 130, а не 75: 130
распознают CI-системы и shell-идиомы, а 75 (EX_TEMPFAIL) означает
«ретрай уместен» — для ручной отмены это ложный сигнал; 75 остаётся
таймауту.

### 5.2 `--fail-on` и приоритеты кодов

`--fail-on reject` / `--fail-on reject,reserve` — id исходов из пакета.
Спец-значения: `error` (файлы со `status=error` считаются сработавшей
политикой — **дефолт**), `any` (любой не-default исход), `none`.
Дефолт `error` делает CLI из коробки честным шагом CI: падение материала
= падение шага; бизнес-решения (`reject`) шаг не роняют, пока явно не
попросили. Id валидируются против пакета до прогона (опечатка → exit 64).

При совпадении условий действует **явный приоритет** (сверху вниз;
применяется первый подходящий):

1. `64/65/66` — вызов и вход (до старта job);
2. `69/77` — сервер недоступен/несовместим/не пустил;
3. `70` — job упал целиком, внутренняя ошибка;
4. `130`, затем `75` — прерывания (отмена пользователем важнее таймаута);
5. `10` — политика `--fail-on` сработала;
6. `2` — degraded без сработавшей политики;
7. `0`.

Следствия, закрывающие прежнее противоречие «1 vs 2»:

- При дефолтном `--fail-on error` файл с ошибкой → exit **10** (ошибка —
  это и есть сработавшая политика), а exit 2 достижим только при
  `--fail-on` без `error` (или `none`) — тогда degraded сигналится
  отдельно. Коды 1 и 3 не используются вовсе (1 зарезервирован, чтобы не
  путаться с родовым failure CI).
- Политика важнее degraded (10 > 2): то, ради чего шаг стоит в CI, не
  должно маскироваться; детальный расклад всегда есть в финальной строке
  stderr (`итог: exit 10 · политика reject: 3 файла · ошибки: 1 файл ·
  пропущено: 2`) и в отчёте.
- `skipped` с reason `already_processed`/`duplicate` — рутинные, на exit
  не влияют (иначе каждый инкрементальный cron-прогон был бы «красным»).

## 6. Пайплайн-механика

### 6.1 Таймауты, ретраи, идемпотентность запросов

Connect-timeout 10 c (фикс.), read — без лимита (job живёт долго, события
идут стримом). `--timeout SEC` — общий дедлайн: истёк → клиент запрашивает
отмену job, частичные результаты пишутся (в `--report` всегда), exit 75.
`--retry N` (дефолт 2): только транспортные сбои и 5xx, backoff
1s→2s→4s + jitter. 4xx (422 валидация, 409 модель не запущена) не
ретраятся — они детерминированы. Создание job несёт client-supplied
`Idempotency-Key` (uuid на вызов): повтор после обрыва сети не плодит
второй прогон (серверная часть — §12.3). Сам прогон чисто
вычислительный, побочек нет — повторный вызов безопасен по построению;
при `--skip-processed` повтор просто догонит манифест.

### 6.2 Отмена и сигналы — best-effort, честные статусы

SIGINT/SIGTERM: клиент шлёт `POST /api/run/{run_id}/cancel`, ждёт
подтверждения до 5 c, сохраняет частичные результаты, exit 130. Второй
Ctrl-C — немедленный выход с `run_id` в stderr для ручной отмены.
Отмена — **best-effort, а не гарантия**: сервер помечает job
`cancel_requested`, гасит asyncio-таски (httpx-коннекты закрываются;
sglang обычно прерывает генерацию по дисконнекту — подлежит
верификации), но облачные API не отменяются — их токены уже сожжены.
Финальный статус job — `cancelled` или `completed_partial`; оба честно
отражаются в `run_end.cancelled` и stderr. На Windows семантика
Ctrl-C/Ctrl-Break в консоли эквивалентна (console control handler);
принцип «не оставлять сироту-прогон, жгущий GPU» — главная причина, что
отмена обязательна, пусть и best-effort.

### 6.3 Идемпотентность между прогонами — `--skip-processed FILE`

FILE — пополняемый NDJSON-манифест
`{"key": "sha256:…", "config_hash": "sha256:…", "outcome": …, "run_id": …}`.
**Ключ = sha256(content) + config.hash**: переименование файла не
провоцирует перепрогон, изменение содержимого — провоцирует, а смена
пакета (новый hash) автоматически инвалидирует старые записи — сценарий
«тот же вход, новые правила» работает без ручной смены манифеста. Файлы
с совпавшим ключом получают `status: "skipped", reason:
"already_processed"` и не уходят на сервер. **Single-writer**: клиент
берёт эксклюзивную advisory-блокировку манифеста (flock / LockFileEx) на
весь прогон; занят → до 5 c ожидания, затем exit 70 с текстом «манифест
занят другим процессом dqa; дождитесь его или используйте отдельный
манифест». Параллельные cron-инстансы обязаны иметь либо разные
манифесты, либо сериализоваться блокировкой — это задокументированное
правило, а не молчаливая гонка с порчей файла. Рост манифеста без GC —
принятая цена (append-only журнал — это и есть аудит); ротация —
внешняя (`--skip-processed` принимает несколько файлов через запятую,
пишет в первый).

### 6.4 `--report <path>` — артефакт аудита

Полный JSON-отчёт (схема §4.1, без `--fields`-проекции и
`--outcome-filter`) пишется на диск независимо от stdout-формата, атомарно
(временный файл + rename; для больших прогонов — NDJSON-режим §3.4).
Типовая схема: stdout кормит следующий шаг пайпа, `--report` — артефакт
для `dqa explain`, `dqa diff` и аудита. Отмена/таймаут/обрыв не теряют
частичный отчёт.

### 6.5 Обрыв стрима событий

Обрыв SSE/стрима посреди job ≠ отмена: job продолжает работать на
сервере. Клиент делает `--retry` попыток переподключения. В v1
переподключение начинает стрим заново (события с начала; клиент
дедуплицирует по `i`/`path` — записи идемпотентны). Целевое решение —
reattach по `run_id` с продолжением после последнего `seq`
(`GET /api/run/{run_id}/events?after=<seq>`) и `dqa run --attach
<run_id>` — отложено в v1.1 как зависящее от server-side ретеншена job
(§12.3, §15). Исчерпание ретраев → exit 69, в stderr — `run_id` и
подсказка «job жив на сервере, результаты не потеряны».

### 6.6 Прогресс и наблюдаемость

В stderr: строка прогресса `12/120 files · 2 err · eta 4m10s`
(перерисовка `\r` только на TTY; в пайп — построчно, пригодно для логов
CI), диагностика сервера, deprecation warnings. `--quiet` — только
фатальные ошибки (в cron тишина — by design: шаг, ждущий уведомления,
обязан ветвиться по exit-коду сам; это оговорено в SKILL и примерах).
`--verbose` — события job, ретраи, HTTP-трасса, `run_id`. Тела
материалов в логи клиента не попадают никогда (приватность по
умолчанию). Корреляция: `run_id` печатается в stderr при старте и лежит
в корне результата; серверный журнал индексируется по нему; «почему
такое решение» — через `dqa explain` из отчёта (§4.5), глубже — по
`run_id` на сервере.

## 7. Многопоточность

`--threads N` — **пожелание серверу**, не локальный пул. Параллелятся
материалы внутри job на сервере; внутри материала модели идут
параллельно (как `asyncio.gather` по `req.models` в `/api/decide`,
`backend/app.py:488`). Семантика:

- **Дефолт — серверный, не зашитый в клиенте**: без флага клиент не
  передаёт значение; сервер знает свои модели, RAM и очередь GPU,
  клиент — нет. Рекомендуемый серверный дефолт объявляется в
  capabilities (`default_threads`, §12.4).
- Сервер вправе зажать значение своим лимитом (`max_threads`); факт
  возвращается в `run_start.threads_effective` и stderr-прогрессе.
  Реальный ускоритель — внутренний батчинг/очередь модельного сервера,
  а не наши потоки; поэтому `threads_effective`, а не обещание.
- **Backpressure**: загрузка материалов чанками (§12.3); переполненная
  очередь сервера отвечает 429 + `Retry-After` — клиент ждёт и повторяет
  чанк (не расходует ретраи сбоев). В v1 серверного 429 может не быть —
  деградация до обычных 5xx-ретраев зафиксирована как допустимая (§12.4).
- **Частичные сбои моделей**: одна модель из `models[]` упала на файле →
  решение по оставшимся, `errors[]` фиксирует модель и причину (зеркало
  per-model `{ok:false,error}` из `/api/decide`); упали все →
  `status: "error"` файла, остальные продолжаются. Строгость реакции —
  через `--fail-on` (дефолт `error`).

## 8. Конфигурация клиента

### 8.1 Иерархия и профили

Приоритет (сверху вниз): **флаги → env → файл → дефолт**.

- Файл: `~/.config/dqa/config.toml` (macOS/Linux) /
  `%APPDATA%\dqa\config.toml` (Windows), права 600 при создании через
  `dqa config`. Формат:
  ```toml
  default_profile = "local"
  [profiles.local]   server = "http://127.0.0.1:8000"
  [profiles.staging] server = "https://dqa.staging.example.com"
  ```
- Env: `DQA_SERVER`, `DQA_TOKEN` (впрок, §12.5), `DQA_PROFILE`,
  `DQA_CONFIG_DIR`.
- Флаги: `--server`, `--profile`.
- Дефолт без конфига: `http://localhost:8000`, без токена.

`dqa config show` печатает эффективные значения **с источником каждого**
(`server = … # env DQA_SERVER`), токен маскируется (`dqa_…f3a9`) —
это ответ на «почему он ходит не на тот сервер». Агент в CI использует
только env (файл не нужен, секреты не седлаются в конфиги); человек —
профили.

### 8.2 Токен — никогда флагом

Флага `--token` **нет по построению**: значение флага видно в
`ps`/журналах CI. Токен доступа к серверу — только `DQA_TOKEN` или файл
конфига (600). В v1 серверной auth нет (§12.5): поле и env зарезервированы,
клиент шлёт заголовок, если токен задан, сервер его пока игнорирует;
401/403 клиент обрабатывает уже сейчас (exit 77 с текстом «проверьте
DQA_TOKEN»), чтобы включение auth на сервере не ломало CLI-контракт
задним числом. В SKILL.md токен помечен «заработает, когда появится auth
на сервере» — агенту не обещают несуществующее.

### 8.3 `dqa doctor`

Единая диагностика среды одной командой (первый запуск на новой машине):
версия Python/бинаря и платформа → доступность сервера →
`/api/version` и совместимость схем → capabilities (лимиты, threads) →
статусы моделей (`/api/health`) → auth-проба → при указании пакета — его
валидация и список исходов. Каждая проверка — строка `OK/FAIL + что
делать`. Exit 0, только если всё зелёное; первый FAIL → соответствующий
код (69/77/65). Для агентов — `--format json`.

## 9. Дистрибуция (Win/Mac)

### 9.1 v1: python-модуль в релизном zip со шимами

Утилита едет **в том же релизном zip**, что и приложение
(`scripts/build_release.sh`, `dist/decision-qa-{mac-arm64,windows}.zip`):
каталог `cli/` с пакетом `dqa` (Python ≥3.10; зависимости — только
`httpx`, остальное stdlib) + шимы `dqa` (shell) и `dqa.cmd` (Windows).
Шим обязан: предпочесть Python из venv проекта (co-located установка),
иначе найти системный (на Windows — лаунчер `py`, не только `python` на
PATH), проверить версию и наличие `httpx`, при нехватке — честный текст
«что делать» + отсылка к `dqa doctor`. Версия CLI = `VERSION` проекта,
релизный цикл общий. Требования: Windows 10+ (cmd/PowerShell), macOS 13+
arm64, сеть до сервера.

Обоснование фазы: нулевая новая сборочная цепочка, co-located сценарий
(та же машина, что и приложение) покрыт сразу. Признаваемая правда: цена
CLI — на других машинах (CI-раннер, ноутбук аналитика), где Python'а
может не быть.

### 9.2 Цель: single-binary — зафиксирована

Как только появится потребитель CLI вне серверной машины — сборка
`dqa-windows-x64.exe` / `dqa-macos-arm64` (PyInstaller `--onefile`,
~15–25 МБ) на существующих релизных раннерах обеих платформ. Контракт
CLI (флаги, exit-коды, схема) спроектирован так, что переезд трогает
только упаковку: stdlib + единственная внешняя зависимость `httpx`
переживают PyInstaller тривиально. Самообновления не будет никогда:
непиннутая версия убивает воспроизводимость конвейера; обновление —
осознанный шаг, при смене мажорной `schema` релиз несёт миграционную
заметку.

### 9.3 Кириллица и Windows-консоль

Заявленная поддержка Windows при русскоязычном продукте требует явных
решений (все — v1): stdout всегда UTF-8 (`ensure_ascii=false`); клиент
переключает консоль Windows на UTF-8 для своего вывода (и восстанавливает
по выходу); ANSI-цвета таблицы — только при объявленной VT-поддержке,
иначе монохром; stderr пишется в UTF-8 независимо от cp866/cp1251
консоли; входные тексты — `utf-8-sig` с флагом `--encoding cp1251`
(§3.3); пути с кириллицей и пробелами — через `--files-from --null` или
манифест (§3.1), никогда через построчный `ls`. CSV — UTF-8 с BOM (§4.3).

## 10. SKILL.md для AI-агентов (готовое содержимое)

Файл `cli/skills/decision-qa/SKILL.md`, едет в zip рядом с CLI:

```markdown
---
name: decision-qa
description: Массовый разбор материалов (тексты, изображения) через набор
  вопросов с вероятностными ответами и детерминированное решение по каждому
  материалу (принять/отклонить/на разбор) через сервер Decision-QA.
  Применять, когда нужно классифицировать/отмодерировать/отскринить файлы
  по заранее отлаженному конфиг-пакету правил.

# decision-qa (dqa)

## Когда применять
Есть конфиг-пакет pack.json (экспорт из веб-интерфейса Decision-QA) и файлы,
по которым нужны решения. НЕ применять, если правила ещё не отлажены —
это делается в веб-мастерской.

## Предусловия и эскалация
1. Сначала `dqa doctor` (или `dqa doctor --format json`). Не прошёл —
   ОСТАНОВИСЬ и сообщи человеку текст FAIL-строки; НЕ чини сервер сам,
   НЕ ретрай в цикле.
2. Не знаешь id исходов для --fail-on — `dqa pack show pack.json`, не гадай строками.
3. Большой прогон (сотни+ файлов) — всегда сначала `dqa validate`:
   она покажет files_ok, оценку времени и ошибки входа без расхода моделей.

## Контракт вызова
dqa run --config pack.json [файлы|директория [--glob '*.txt'] |
        --files-from list.txt [--null] | --manifest m.json | --stdin]
        [--format ndjson|json|csv] [-o out.json] [--report r.json]
        [--fail-on outcome1,outcome2|error|any|none] [--threads N]
        [--timeout SEC] [--skip-processed seen.ndjson] [--quiet]
Обязательно: --config и источник входа (для stdin — явный --stdin).
Сервер: env DQA_SERVER. Токен: ТОЛЬКО env DQA_TOKEN (флага токена нет;
auth появится на сервере позже — тогда DQA_TOKEN заработает; сейчас
сервер его не требует). Никогда не передавай секреты аргументами командной
строки — они видны в ps и логах.

## Коды выхода — проверяй ПЕРЕД разбором stdout
0  все ок, политика --fail-on не сработала
2  частичный успех: есть файлы status=error/skipped — разбери
   .files[] | select(.status != "ok"), это НЕ фатал
10 сработала политика --fail-on (по дефолту error): данные полные, решай
   по .summary и .files[] — это сигнал о ДАННЫХ, не о сбое конвейера
64/65/66  ошибка вызова/валидации/входа — чини аргументы, НЕ ретрай
69  сервер недоступен/несовместим или оборвался стрим — ретрай позже,
    при повторе — эскалация человеку (см. run_id в stderr)
70  внутренняя ошибка / job упал / манифест занят другим процессом
75  истёк --timeout — ретрай уместен (частичные данные в --report)
77  401/403 — проверь DQA_TOKEN (когда auth включена на сервере)
130 прервано пользователем (Ctrl-C), job на сервере отменяется

## Форма вывода (shape-правила — читай всегда)
1. stdout — ТОЛЬКО данные; stderr — прогресс и логи, оттуда данные НЕ читать.
2. json: ВСЕГДА конверт — результаты только в .files[] (даже для одного
   файла это .files[0]); счётчики в .summary; версия контракта — "schema": 1;
   неизвестные поля ИГНОРИРОВАТЬ (схема растёт только добавлением полей).
3. ndjson: строка = СОБЫТИЕ; записи файлов — только
   select(.type=="file"); run_start/run_end — обрамление (summary в конце
   потока — контроль его целостности). Никогда не разбирай ndjson без
   фильтра по .type.
4. Решение читай из .files[].decision.outcome (id исхода), НЕ парси label.
5. Файл может быть ok с непустым errors[] (упала часть моделей) — при
   важности per-model смотри .files[].answers.<q>.by_model.
6. stdout — UTF-8 с кириллицей без экранирования; читай как UTF-8.

## Лимиты входа (узнавай здесь, а не из ошибок)
≤8 изображений на материал; ≤20 МБ base64 суммарно; тексты >~200 КБ —
дорогой prefill, лучше резать; типы: .txt .md .json .png .jpg .jpeg .webp .gif;
HEIC не поддерживается (конвертируй в JPEG). Актуальные значения —
`dqa doctor` (capabilities сервера).

## Рецепты
1. Разобрать входящие интервью (инкрементально, идемпотентно):
   dqa run --config screening.json inbox/ --glob '*.txt' \
     --skip-processed seen.ndjson --report r.json --format json -o out.json

3. Один текст из переменной:

   …исход: jq -r '.files[0].decision.outcome' из вывода
4. Стрим с реакцией по мере готовности (БЕЗ перемещения файлов внутри цикла —
   сначала собери исходы, действуй после завершения прогона):
   dqa run --config pack.json inbox/ --format ndjson \
     | jq -rc 'select(.type=="file") | {path, outcome: .decision.outcome}'
5. Почему материалу такое решение:
   dqa explain inbox/ivanov.txt --report r.json
6. Сравнить две версии правил (A/B пакета):
   dqa run --config old.json inbox/ -o r1.json --fail-on none
   dqa run --config new.json inbox/ -o r2.json --fail-on none
   dqa diff r1.json r2.json
7. Проверка перед большим прогоном:
   dqa validate --config pack.json big_folder/ --format json \

- Повторный прогон «в лоб» после обрыва: безопасен (прогон вычислительный),
  а с --skip-processed ещё и догонит только необработанное.
```

## 12. Зависимости от сервера (блокеры, в честном порядке)

CLI не строится, пока не решены (1)–(3); (4)–(5) — до выкатки за пределы
одной машины. Порядок важен: это, а не форматы вывода, определяет сроки.

### 12.1 Блокер: серверный порт движка решений

Сегодня исход (outcome) вычисляет **только фронт** —
`evaluateDecision` в `frontend/static/decision.js:109`
(`backend/assistant/trial.py:6-8` говорит прямо: «Правила решения сервер
не вычисляет»). Нужен порт движка правил на Python (в сервер, чтобы
возвращал `/api/run`) с **parity-тестами бит-в-бит против JS-версии**:
`evalRules`, trace, default-исходы, пороги/операторы условий
(`gte`/`lt`, `threshold`/`score` — формат условий виден в пресетах,
`backend/presets/batch_resume_screening.json`). Без этого ни одна запись
результата с `decision.outcome` не может быть произведена, а рассинхрон
веба и конвейера — худший из возможных: ценность продукта —
детерминированность решения.

### 12.2 Блокер: формат конфиг-пакета

Пакета с `version` + `hash` не существует: пресеты
(`backend/presets/*.json`) их не содержат. Нужно: структура (questions +
decision + settings{mode, models, temperature?} + version + hash),
экспорт из веба, и **каноникализация JSON для hash** — сортировка ключей,
UTF-8 без экранирования не-ASCII, фиксированные разделители, без
плавающих неоднозначностей; иначе «hash не сошёлся» будет ложно
срабатывать на безобидные правки. Поле `settings.mode` обязательно:
дефолт `--mode` берётся из пакета (§2.1).

### 12.3 Блокер: контракт `/api/run` целиком

Эндпоинта нет (`backend/app.py` знает только `/api/decide`:454 и
`/api/version`:498); job-реестра нет (единственный образец —
`_ACTIVE_TRIALS` в `trial.py:36`, in-memory, один прогон на сессию).
Требуемый контракт:

- **Жизненный цикл job**: `POST /api/run` (config pack или его hash +
  mode + threads? + Idempotency-Key) → `run_id`; загрузка материалов;
  старт; события; финальный результат; ретеншен результатов (TTL) для
  reattach.
- **Загрузка payload — выбрано: чанковый upload-then-run.** `POST
  /api/run/{id}/files` принимает чанки (ориентир: ≤50 материалов или ≤16
  МБ на чанк, пороги — из capabilities), затем `POST /api/run/{id}/start`.
  Отвергнутые альтернативы: (а) один POST со всеми материалами — тело в
  сотни МБ (500 файлов × 200 КБ ≈ 100 МБ), нет гранулярности ретраев и
  backpressure, частичный приём невозможен; (б) полноценное файловое
  хранилище с upload-сессиями — избыточно для вычислительного
  stateless-конвейера. Чанки дают: ретрай на гранулярности чанка,
  серверный контроль очереди (429 + `Retry-After`), потоковую отправку
  100k-входа без сборки тела в памяти.
- **События**: SSE (`StreamingResponse`-инфраструктура есть,
  `router.py:218`, но trial-стрим привязан к session_id чата — нужен
  отдельный эндпоинт). События `run_start/file/run_end` (+`run_cancelled`),
  каждое с монотонным `seq` — задел под `?after=<seq>` для reattach (v1.1).
- **Отмена**: `POST /api/run/{id}/cancel` → статусы
  `cancel_requested → cancelled | completed_partial`; гашение
  asyncio-таск уже частично существует (`trial.py:391-395`); прерывание
  генерации sglang по дисконнекту — верифицировать; облачные API не
  отменяются (токены сожжены) — best-effort зафиксирован в §6.2.
- **Лимиты и таймаут job**: `max_files_per_job`, `max_concurrent_jobs`,
  серверный дедлайн job (сегодня 500 файлов × `REQUEST_TIMEOUT=600с`
  worst-case — 83 часа бессмертного job'а; `TRIAL_TIMEOUT_S=300` —
  антиспам ассистента, не лимит пакетов).
- **Дедуп по Idempotency-Key** при создании job — сервер хранит ключи в
  пределах ретеншена.

### 12.4 Capabilities-эндпоинт

`GET /api/run/capabilities` (или расширение `/api/version`): лимиты входа
(8 изображений, 20 МБ — сегодня зашиты в `backend/schemas.py:11-12`, у
фронта вообще `MAX_FILE_IMAGES=3` — клиент обязан получать их от сервера,
а не дублировать константы), `default_threads`/`max_threads`,
поддерживаемые режимы, диапазон схем (`min_schema`/`max_schema`), лимиты
job'ов, флаг `auth_required`. `dqa doctor` и `dqa validate` читают его;
клиент без capabilities работает по консервативным дефолтам с warning.

### 12.5 Задел под изоляцию v1.3 (мультитенантность)

Сервер сегодня однопользовательский: глобальный `mm.REGISTRY`, нет auth,
нет per-user квот; два прогона с `--threads 8` на одном GPU устроят
взаимный DoS. CLI-контракт обязан **уже сейчас** включить: `run_id`
сквозной (есть), токен в клиенте (есть, впрок, §8.2), обработку 401/403
(exit 77), поле владельца в job (серверная данность будущего). Тогда
изоляция v1.3 не сломает CLI задним числом.

### 12.6 Прочие серверные требования

ETA-калибровка для `validate` (агрегат `metrics.duration_s` из
`backend/app.py:437` по моделям; до его появления `validate` честно
отдаёт `estimate: null`); gzip-транспорт для base64-картинок (+33%
объёма: 20 МБ лимит ≈ 27 МБ на материал — приемлемо co-located, для
удалённого сервера нужен gzip и предупреждение в validate); реестр
пакетов и `--doc <id>` — позже, блок `config` в схеме результата устроен
так, чтобы добавить `doc_id` без смены мажорной версии.

## 13. Отвергнутые альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| Автономный режим (модели внутри CLI) | Данность: креды и модели на сервере; дубль движка = два контракта правил и рассинхрон решений между вебом и конвейером |
| Отдельные команды `dqa decide` / `dqa batch` | Режим определяется входом; две команды — двойной help, двойные тесты, переключение команды при росте объёма |
| Интерактивный визард по умолчанию | Зависший prompt в CI — классическая авария; удобство человека — явные `config init` / `doctor` |
| Shape-shifting JSON (объект для 1 файла, массив для N) | Скрипт «проверил один файл → поставил в пайплайн» ломается ровно на смене формы; всегда конверт с `files[]` (§4.1) |
| TTY-auto-формат (table в терминале, jsonl в пайпе) как дефолт | Два визуальных контракта; машина первична. Конвенция gh/docker признана, но table принят опциональным явным форматом (§4.4) |
| NDJSON из «голых» записей файлов | Без `run_start`/`run_end` обрыв потока неотличим от конца, `run_id` неоткуда взять (§4.2) |
| `--tee` (дублирующий вывод) | Мутная семантика при csv-основном-потоке; `--report` решает задачу честнее (полный артефакт независимо от stdout) |
| Exit-код = исход решения | Исходы — произвольные id из пакета, N исходов на N материалов; семантика «ошибка процесса» смешивается с «политика сработала». Вместо этого `--fail-on` → exit 10 |
| Exit 75 (EX_TEMPFAIL) для Ctrl-C | 75 означает «ретрай уместен» — ложный сигнал для ручной отмены; 130 (`128+SIGINT`) распознают CI и shell-идиомы |
| Хуки `--on-outcome cmd` / `--post-hook` | CLI не планировщик: скрытая точка отказа, shell-injection, смешение exit-семантики; «выход кормит следующий шаг» наблюдаемее. Агенту хук не нужен — он читает JSON |
| Догон упавшего через `comm`/`jq`/process-substitution | Ломается на путях с пробелами/кириллицей, требует jq/sort, на Windows не работает вовсе; `--skip-processed` по content+config hash решает это одной строкой (§6.3) |
| Resume-состояние прогонов в CLI (`~/.dqa/state`) | Клиент без состояния проще и честнее; догон — `--skip-processed`; серверный reattach по run_id — v1.1 (§6.5) |
| Гарантированная «подтверждённая» отмена job | Недостижима без кооперации модельного сервера; облачные API не отменяются. Честные статусы cancel_requested/cancelled (§6.2) |
| Токен флагом `--token` | Виден в ps и журналах CI; только env/файл (§8.2) |
| Эвристическое угадывание кодировки входа | Молчаливое перекодирование — скрытая порча материала; детерминированный `--encoding` (§3.3) |
| Server-side дедуп обработанных | Сервер — stateless-конвейер; состояние идемпотентности — у вызывающей стороны |
| Один POST со всеми материалами / файловое хранилище upload-сессий | См. §12.3: выбран чанковый upload-then-run |
| Точный бюджет токенов до прогона | Невозможен (длина генерации неизвестна); честная оценка с `estimate: true` |
| YAML-конфиг клиента / YAML-вывод | Лишний парсер и диалекты; TOML и json/jq достаточны |
| Конфиг-пакет по умолчанию (`~/.config/dqa/default.pack`) | Скрытый дефолт главного входа делает cron-пайплайны невоспроизводимыми; `--config` обязателен всегда |
| Картинки через stdin; пресет (`files[]`) как вход CLI | Бинарь в пайпе — порча данных; пресеты — формат мастерской, CLI работает с ФС (§3.1) |
| Авто-разбиение входа на несколько job'ов при превышении лимита | Ломает корреляцию «прогон = run_id»; v1 — отказ с подсказкой (§3.4) |
| Несколько пакетов на один вход за один прогон | Промпты разные — двойной расход неизбежен; батчинг пакетов — серверная оптимизация, не клиентская. Рецепт: два прогона + общий манифест с разными config.hash работает уже сейчас (§6.3) |

## 14. Открытые вопросы

- Parity-подход для движка решений (§12.1): общий golden-набор кейсов
  (вопросы+ответы→исход), прогоняемый и JS-, и Python-реализацией в CI —
  формат набора надо спроектировать первым делом.
- SSE vs long-poll для событий `/api/run`: CLI-контракт изолирован от
  транспорта (события те же), выбор — за серверной реализацией.
- Состав `by_model` для режима `fast_batch` (его метрики отличаются):
  уточнить при серверной агрегации, прежде чем фиксировать поля в
  `schema: 1`.
- Размеры чанков загрузки (§12.3) — калибруются на реальном сервере;
  в контракте — через capabilities, не константой.
- GC/ротация манифеста `--skip-processed` при годах работы — сейчас
  append-only журнал принят как аудит; если станет проблемой — отдельная
  утилита/флаг, не молчаливая обрезка.
