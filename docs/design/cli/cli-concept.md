# Decision-QA CLI — единая концепция (синтез вариантов A и B)

> Финальный документ конкурса концепций. База — вариант B («машина в
> пайплайне»); из варианта A перенесены командная эргономика человека,
> `--glob`, неявный stdin, `dqa doctor`, тексты ошибок и фазированная
> дистрибуция. Оба критических разбора учтены; варианты A и B остаются в
> `docs/design/cli/` как история.
>
> Данности (не перепроектируются): CLI — тонкий HTTP-клиент поверх сервера
> Decision-QA; креды к моделям живут только на сервере (`backend/credentials.json`),
> автономного режима нет; серверный `POST /api/run` даёт job + события
> прогресса + отмену + частичные результаты; конфиг-пакет — версионируемый
> JSON (вопросы + правила + настройки + `version:1` +
> `fingerprint_version:1` + `hash` + семантический `fingerprint`, §12.2),
> экспорт из веба. Python-порт решений и формат пакета уже реализованы в
> `dqa_common` с общими JS/Python golden-фикстурами. Данности, которых на
> сервере пока **нет** (подключение порта к run engine, сам `/api/run`,
> capabilities, auth), вынесены в раздел «Зависимости от сервера» — это
> блокеры, а не сноски.

---

## 1. Целевая аудитория и оптика

CLI `dqa` — конвейерный шаг: CI, cron, shell-скрипты, AI-агенты. Это
первичный пользователь, и он диктует контракты: версионируемая схема
вывода, разнесённые exit-коды, идемпотентность, наблюдаемость. Вторичный
пользователь — разработчик-аналитик, только что отладивший вопросы и
правила в веб-мастерской: он пришёл *взглянуть* на результат по 50
интервью глазами и получить честную подсказку при ошибке в 3 часа ночи.
Его обслуживают опциональная TTY-таблица, `dqa doctor`, `dqa pack show`
и тексты ошибок стиля «что случилось + что делать» — но ни один из этих
«человеческих» механизмов не просачивается в машинные контракты.

Инварианты, которые не нарушает ни одна фича:

1. stdout — только данные (JSON/NDJSON/CSV/table); stderr — только
   прогресс и диагностика. Потоки не смешиваются никогда.
2. Форма JSON-результата не зависит от числа материалов: один файл и
   сто тысяч файлов дают документ одной схемы с `files[]` (никакого
   shape-shifting «объект vs массив»).
3. Команда, отлаженная на одном файле, работает на тысяче без изменений.
4. Креды моделей физически не могут появиться на клиенте: нет ни одной
   команды, которая бы их принимала.

## 2. Командная модель

Одна рабочая лошадка — `dqa run`; режим (одиночный/пакетный) определяется
входом, а не глаголом. Остальное — служебные субкоманды (модель
`gh`/`docker`: `dqa --help` — карта возможностей).

```
dqa run [МАТЕРИАЛ ...] --config pack.json [флаги]   # основной прогон
dqa validate [МАТЕРИАЛ ...] --config pack.json      # проверка входа и пакета без прогона (dry-run)
dqa explain <path> --report r.json                  # почему материалу вынесено такое решение (локально, из отчёта)
dqa diff r1.json r2.json                            # сравнение двух прогонов (A/B пакетов, локально)
dqa pack show <pack.json>                           # сводка пакета: вопросы, id исходов, модели, hash
dqa config init|set|show                            # клиентская конфигурация (сервер, профили)
dqa doctor                                          # диагностика среды и сервера одной командой
dqa version                                         # версии CLI/схемы + совместимость с сервером
```

### 2.1 Флаги `dqa run`

| Флаг | Дефолт | Смысл |
|---|---|---|
| `--config pack.json` | **обязателен** | конфиг-пакет из веба (вопросы+правила+hash+fingerprint) |
| `--mode decisions\|fast_batch\|both` | **из пакета** (fallback `decisions`) | режим прогона; пакет — источник истины о задаче |
| `--models key1,key2` | **из пакета** | переопределение моделей пакета на один прогон (отладка, A/B; §2.1) |
| `--threads N` | **серверный дефолт** | желаемый параллелизм на сервере; без флага клиент не передаёт значение (§7) |
| `--glob PATTERN` | `*` (с `-r` — `**/*`) | разворачивание директорий самим CLI — первоклассный механизм ради Windows (§3) |
| `--recursive, -r` | off | рекурсивный обход директорий |
| `--files-from FILE [--null]` | — | список путей из файла (`-` = stdin), `--null` — NUL-терминированный (`find -print0`) |
| `--manifest FILE` | — | JSON-манифест: группировка «текст + до 8 картинок» в один материал (§3) |
| `--image IMG` (повторяемый) | — | картинки одиночного материала (с путём/stdin-входом); отключает конвенцию §3.5 для этого материала |
| `--stdin` | неявный при пустом входе | один текстовый материал из stdin; `--name STR` задаёт имя (дефолт `stdin`) |
| `--format json\|ndjson\|csv\|table` | `json` | формат вывода; `table` — только в TTY (§4) |
| `--output, -o FILE` | `-` (stdout) | файл результата, атомарная запись |
| `--report PATH` | — | полный JSON-отчёт на диск независимо от stdout (§6.4) |
| `--outcome-filter ID[,ID]` | — | оставить в выводе только файлы с перечисленными исходами |
| `--fail-on LIST` | `error` | исходы, дающие exit 10 (§5.2); id валидируются против пакета до прогона |
| `--skip-processed FILE` | — | идемпотентность между прогонами, ключ = content hash + семантический fingerprint пакета (§6.3) |
| `--timeout SEC` | `0` = без лимита | общий дедлайн клиента; истёк → exit 75 (§6.1) |
| `--retry N` | `2` | ретраи транспорта/5xx с backoff (§6.1) |
| `--encoding utf-8\|cp1251` | `utf-8` | детерминированная кодировка входных текстов (§3.3) |
| `--quiet` / `--verbose` | off | уровень stderr |
| `--profile NAME`, `--server URL` | конфиг/env | точка подключения (§8); **`--token` не существует** — токен только env/файл (§8.2) |
| `--dry-run` | off | алиас `dqa validate` для тех же аргументов |

**Переопределение моделей (`--models`).** «Тот же пакет на другой
модели, не трогая пакет»: отладка и A/B моделей. Пакет всегда несёт
`settings.models` (§12.2), поэтому флаг — всегда **замещение**, а не
дополнение; без флага — модели пакета. Порядок перечисления не значим
(в fingerprint модели сортируются). Ключи валидируются до прогона
против списка сервера (capabilities): неизвестный ключ → exit 65 со
списком доступных; остановленная модель — то же поведение, что у
остановленной модели из пакета (§2.3). Один флаг = один набор на
прогон; A/B — два прогона + `dqa diff` (§11 №11), никаких матриц
прогонов. Эффективный набор входит в fingerprint: при переопределении
клиент пересчитывает его сам (§12.2), и ключи `--skip-processed` разных
наборов не смешиваются. Подмена всегда видна в отчёте
(`config.models_overridden`, §4.1) и в `run_start` (§4.2).

### 2.2 Неинтерактивность и discoverability

CLI всегда неинтерактивен: ни одна команда не задаёт вопросов; ввод ждёт
только явный/неявный stdin. Интерактивный prompt в CI = зависший job.
Удобство первого запуска решается явно вызванными `dqa config init` и
`dqa doctor`, а не модальностью `run`. Недостающий обязательный параметр
→ exit 64 с именем флага и примером вызова.

### 2.3 Тексты ошибок: «что случилось + что делать»

Стиль, перенесённый из варианта A (его лучший раздел), — обязателен для
всех ошибок клиента. Примеры нормы:

- `Не удаётся подключиться к http://qa.internal:8000 (connection refused).
  Проверьте, что сервер запущен, или смените адрес: dqa config set …` — exit 69.
- `Модель clef-local не запущена на сервере. Запустите её в веб-интерфейсе
  (менеджер моделей) и повторите.` — exit 69 (серверный 409 на старте job).
- `Модель clef-local упала посреди прогона: 3 файла без решения (см. per-file
  errors в отчёте).` — exit 10 (упавшие файлы — это сработавший дефолтный
  `--fail-on error`, §5.2; job сам доработал).
- `Конфиг-пакет mod.json изменён после экспорта: hash не сошёлся.
  Переэкспортируйте пакет из веб-интерфейса.` — exit 65.
- `Не указаны материалы и stdin пуст. Примеры: dqa run file.txt --config p.json ·
  dqa run dir/ --glob '*.txt' --config p.json` — exit 64.
- `--fail-on rewiew: в пакете нет исхода "rewiew". Исходы пакета: invite,
  reserve, reject (см. dqa pack show pack.json).` — exit 64.
- `Файл claim_557_p1.jpg подпадает под две группы: claim.txt и claim_557.txt.
  Переименуйте файл или задайте группировку явно: --manifest m.json
  (см. dqa validate — группы показываются до прогона).` — exit 65.

Traceback Python пользователь не видит никогда, кроме скрытого `--debug`.
`-v` добавляет HTTP-трассу (метод, путь, статус, latency, тело ошибки
сервера) — достаточно для баг-репорта без перепроса.

### 2.4 Политика совместимости контрактов

Семвер раздельно для трёх контрактов: (а) флаги и exit-коды CLI,
(б) JSON-схема результата (`schema`), (в) минимальная версия сервера.
Внутри мажорной версии поля JSON **только добавляются** (потребитель
обязан игнорировать неизвестные поля — это правило зашито в SKILL.md);
удаление/переименование поля или смена семантики exit-кода = новая
мажорная `schema`. Перед прогоном клиент сверяет свою `schema` с
диапазоном сервера (capabilities, §12.4): вне диапазона → exit 69 до
старта с текстом «обновите CLI до ≥X / сервер до ≥Y». Устаревший флаг =
deprecation warning в stderr минимум один мажорный цикл, потом отказ с
подсказкой. Потребители никогда не парсят stderr и таблицу — парсинг
человеческих форматов исключён по построению.

Стабильность машинных ключей пакета: `outcome.id` и `question.id`
неизменяемы, `label`/`color`/порядок — не контракт; потребитель,
опирающийся на label/индекс, — вне гарантий (норма и обоснование —
§6.9(а), зашито в SKILL.md). Переопределения командной строки
(`--models`) — осознанные и всегда видимые в отчёте, но живут в вызове,
а не в пакете: воспроизводимость конвейера = пакет + командная строка.

## 3. Ввод

### 3.1 Источники входа

1. **Позиционные пути** — файлы и директории. Директория разворачивается
   по `--glob` (дефолт `*`, с `-r` — `**/*`). Глоб разворачивает **CLI, а
   не shell**: на Windows шелл глобы не разворачивает, поэтому `--glob` —
   первоклассный механизм, а не костыль. Поддерживаемые типы: тексты
   `.txt .md .json` (json = материал-объект, как `input: dict|list` в
   `DecideRequest`, `backend/schemas.py:71`), картинки
   `.png .jpg .jpeg .webp .gif`. Файл-картинка = один материал с одним
   изображением (как `files[].image` в пресете `batch_photo_moderation.json`).
   Неизвестное расширение → ошибка с подсказкой. HEIC отвергается текстом,
   дословно повторяющим серверный (`backend/schemas.py:111-114`).
   Развёрнутые файлы проходят **конвенцию группировки** «текст + фото»
   (§3.5): часть картинок станет вложениями текстовых материалов, а не
   отдельными материалами.
2. **stdin**: `cat f.txt | dqa run --config p.json` — неявно (ноль
   позиционных аргументов + stdin не-TTY); явная форма `--stdin`
   равноправна (самодокументируемая форма для агентов и SKILL.md). Имя
   материала — `--name`, дефолт `stdin`. Картинки через stdin не
   поддерживаются (бинарь в пайпе — источник порчи данных); для
   одиночного vision-материала — `--image`:
   `dqa run post.txt --image p1.png --image p2.png --config p.json`.
3. **`--files-from list.txt`** — один путь на строку, `#` — комментарии;
   `--files-from - --null` — NUL-терминированный список для связки с
   `find -print0` (пути с пробелами и кириллицей не ломаются).
4. **`--manifest m.json`** — JSON-массив `{"path": …, "name": …,
   "images": ["a.png", …]}`: точный набор входов от скрипта/агента и
   группировка «текст + до 8 картинок» в один материал пакетно (то, что
   `--image` умеет только в одиночном режиме). Манифест — **высший
   приоритет** группировки: конвенции §3.5 к его входам не применяются.

Пресет-формат веба (`files[]` с `content`/`image`) в CLI-ввод не
принимается: пресеты — формат мастерской, CLI работает с реальной ФС;
конфиг-пакет (`--config`) и вход разделены жёстко.

### 3.2 Валидация до прогона — `dqa validate` / `--dry-run`

Локально, без обращений к моделям: пакет валиден, `version`
поддерживается, пересчитанный `hash` совпадает с записанным (каноникализация
— §12.2); пути существуют и читаемы; лимиты картинок (≤8, ≤20 МБ base64 —
приходят из capabilities, не зашиты, §12.4) соблюдены; id исходов в
`--fail-on` существуют в пакете; ключи `--models` — против списка из
capabilities (неизвестный → ошибка со списком доступных), эффективные
модели и факт подмены показываются. **Группировка §3.5 показывается до
прогона обязательно**: каждый материал — с типом (`text` / `image` /
`text+N images`) и списком прикреплённых картинок; предупреждения —
картинки, не подошедшие ни к одному тексту (станут отдельными
материалами), и группы сверх лимита изображений; неоднозначность (§3.5)
— ошибка валидации. С `--skip-processed`
сводка учитывает манифест: «новых N, пропущено M» — главное число
инкрементального cron'а. Вывод — JSON-сводка: `files_total`,
`files_ok`, `files_skipped` с причинами, оценка `n_files × n_models`
инференсов, ETA и порядок токенов из калибровки сервера с честной пометкой
`estimate: true` (точный бюджет до прогона невозможен — длина генерации
неизвестна; это sanity-gate «вы точно хотите 40 000 файлов?», не биллинг).
План свыше 50 материалов печатается усечённо (первые 50 + счётчики) —
усечение касается **только успешных групп**: ошибки и предупреждения
(неоднозначности, сироты, лимиты) — всегда полным списком, иначе
систематическую коллизию имён чинили бы по одной за прогон.
Exit 0/65. Правило для всех потребителей и зашито в SKILL.md: **большой
прогон всегда предваряется validate**.

### 3.3 Битые, пустые, дублирующиеся файлы; кодировки

- **Пустой текст** → `skipped` с `reason: "empty"` (сервер отвергает
  пустой `input` без изображений, `backend/schemas.py:83-89`; клиент
  дублирует проверку, чтобы не жечь прогон).
- **Нечитаемый/битый** (ошибка чтения, битый base64 картинки) →
  `skipped` + `reason: "unreadable"`, прогон остальных продолжается.
- **Кодировка текста**: детерминированно — UTF-8 с допуском BOM
  (`utf-8-sig`); невалидный UTF-8 → `skipped`, `reason: "encoding"`, с
  подсказкой `--encoding cp1251` (типовой случай файлов с Windows-машин).
  Эвристического угадывания кодировки нет: молчаливое перекодирование —
  скрытая порча материала, детерминированность решений важнее удобства.
- **Дубликаты**: дедупликация по sha256 содержимого (для сгруппированного
  материала — составной `content_sha256` по §3.5); повторный файл не
  уходит на модели, в результате — `skipped`, `reason: "duplicate"`,
  `duplicates_of`.
- Один битый файл никогда не роняет прогон при наличии хотя бы одного
  валидного входа. Ноль валидных входов → exit 65.

### 3.4 Очень большие папки (10⁵ файлов)

Перечисление входа — потоковое (ленивый обход, без списка 100k путей в
памяти; дедуп-множество хэшей — ~3 МБ на 100k файлов, приемлемо).
Загрузка материалов в job — чанками (§12.3), клиент никогда не собирает
одно тело в 100 МБ. `--report` при `files_total` выше порога (10 000)
автоматически пишется в NDJSON-построчном виде: гигабайтный цельный JSON не собирается в
памяти и не «переименовывается атомарно» наполовину. Жёсткий потолок
`max_files_per_job` приходит из capabilities; превышение → exit 65 с
текстом «разбейте вход или поднимите лимит на сервере». Авто-разбиение
на несколько job'ов осознанно отложено (§15): оно ломает корреляцию
«один прогон = один run_id».

### 3.5 Группировка «текст + фото»: конвенция именования

Реальный сценарий — ИС вываливает в папку-обменник письма с претензиями
и приложенные фото одним плоским списком, манифеста у ИС нет. Для него —
одна детерминированная конвенция, работающая **по умолчанию, без флагов**.
Это тот же сценарий, что веб закрывает ручным прикреплением картинок
(`batch.js:217-229`, пресет `batch_returns_claims.json`: `{name,
content, images[]}`), — конвенция покрывает его без потерь.

**Правило.** Текстовый файл `БАЗА.ext` (txt/md/json) поглощает картинки
**той же директории** с именами `БАЗА.<imgext>` и `БАЗА_<суффикс>.<imgext>`:
`claim_557.txt` собирает `claim_557.jpg`, `claim_557_p1.jpg`,
`claim_557_фото2.png` в один материал. Разделитель — только `_`;
расширение регистронезависимое; basename перед сравнением
нормализуется в NFC (APFS отдаёт NFD — перенос папки macOS↔Windows не
развалил бы группы); с `-r` группировка — в пределах каждой директории.
Картинка, не подошедшая ни к одному тексту, — самостоятельный материал,
как прежде. Приоритет: `--manifest` (явная группировка) > конвенция >
файл=материал; конвенция применяется только к материалам из директорий
и `--files-from` — прямой позиционный файл её не триггерит, а явный
`--image` отключает её для своего материала. Отдельного флага
отключения нет — где конвенция мешает, там нужен манифест (§13).

**Совпадение базы регистрозависимое** — на регистронезависимых ФС
(Windows, macOS) это ловушка: `Claim_557.TXT` и `claim_557_p1.jpg`
**не** сгруппируются, хотя в проводнике имена «одинаковые». Validate
предупреждает о сиротах, похожих на группу с другим регистром.

**Когда конвенция применима.** Она требует контроля именования на
выгрузке: ИС именует файлы по правилу, с уникальными непрефиксными id
(текст `Претензия.txt` рядом с `Претензия_557.txt` сделает картинки
второго неоднозначными → exit 65). Если имена не контролируются
(`IMG_20261015_143022.jpg`), конвенция даст ноль групп и фото молча
уйдут отдельными материалами — тогда сразу `--manifest`. Страховка без
validate: `run` печатает в stderr счётчик сирот (`N картинок без
группы → отдельные материалы`).

**Неоднозначность — ошибка, не выбор.** Картинка под двумя базами
(`claim.txt` и `claim_557.txt`, файл `claim_557_p1.jpg`) → exit 65
(§2.3): «длинная база побеждает» — молчаливое гадание с чужим фото.
Группы видны в `dqa validate` **до** прогона (§3.2) — конвенция без
предпросмотра была бы магией.

**Порядок изображений** — лексикографический по имени файла
(`claim_557.jpg` раньше `claim_557_p1.jpg`). Порядок — часть контракта:
`DecideRequest.images` передаётся модели как есть
(`backend/clef.py:56`), промпт «на первом фото…» чувствителен.
Лексикографика ставит `_p10` раньше `_p2` — нумеруйте с ведущим нулём
(`_p01.._p08`); natural sort не вводится (недетерминированная
сложность, §13), а серверный лимит (≤8 сегодня) делает однозначные
номера нормой.

**Лимиты и дубли.** ≤8 изображений и ≤20 МБ base64 на материал (из
capabilities, §12.4): превышение → ошибка validate с подсказкой про
`--manifest`; 4+ фото — предупреждение, что в вебе (лимит 3,
`batch.js:22`) материал не открыть. Одинаковое фото внутри материала
схлопывается; одна фотография в двух материалах — не дубль (дедуп §3.3 —
на уровне материала).

**Идентичность.** `content_sha256` — всегда по **сырым байтам** файлов
(до декодирования и срезания BOM: ключ не зависит от `--encoding`);
для материала с картинками — `composite_content_sha256` из
`dqa_common.materials`: sha256 от конкатенации бинарных
`sha256(текст) ‖ sha256(карт₁) ‖ …` в порядке вложений, без имён и
метаданных. Ключ §6.3 и джойн `dqa diff` реагируют на замену/перестановку
фото, но не на переименование. Для structured input helper использует JCS;
сырые файлы CLI хэширует именно как байты. Отдельный metadata-aware
`material_hash` нужен для ordered `materials_fingerprint`;
`run_fingerprint = SHA256(JCS({config_fingerprint, materials_fingerprint}))`.
Эти значения не смешиваются со старым frontend djb2 или rename-stable
`content_sha256`. Клиент отдаёт хэши в чанках upload (§12.3), а `/start`
независимо пересчитывает их и effective config fingerprints — сервер не
доверяет клиентскому ожиданию и не является простым эхом. **Тип в выводе:**
`material.type` + состав вложений (§4.1); смешанная папка (текст /
фото / текст+фото) легальна, тип виден в validate и отчёте.

Отложено: конвенция «подпапка = материал» (`claims/<id>/letter.txt +
*.jpg`) — v1.1 по первому реальному потребителю (§15); до неё случай
закрывается `--manifest`, который генерирует скрипт выгрузки.

## 4. Вывод

### 4.1 JSON-схема результата — стабильный контракт (`--format json`)

Всегда конверт, независимо от числа материалов:

```json
{
  "schema": 1,
  "run_id": "run_01JEXAMPLE…",
  "cli_version": "1.0.0",
  "server": {"url": "http://127.0.0.1:8000", "version": "1.5.0"},
  "config": {"path": "pack.json", "version": 1, "fingerprint_version": 1,
             "hash": "sha256:…", "fingerprint": "sha256:…",
             "effective_hash": "sha256:…", "effective_fingerprint": "sha256:…",
             "models_overridden": true, "mode_overridden": false,
             "models_pack": ["clef-27b"]},
  "mode": "decisions",
  "models": ["clef-27b", "qwen3-32b"],
  "aggregation": "mean_probability_v1",
  "threads_effective": 4,
  "started_at": "2026-10-23T10:15:00Z", "finished_at": "…", "duration_s": 222.4,
  "summary": {"files_total": 12, "files_ok": 10, "files_failed": 1,
              "files_skipped": 1,
              "decisions": {"invite": 7, "reserve": 2, "reject": 1}},

    {
      "path": "inbox/resume_01_petrov.txt", "name": "resume_01_petrov.txt",
      "content_sha256": "…", "status": "ok",
      "material": {"type": "text", "images": []},
      "decision": {"outcome": "invite", "label": "Пригласить",
                   "rule": "q9>=3 && q3.yes>=0.6", "is_default": false},

        "q9": {"type": "score", "score": 3.71,
               "by_model": {"clef-27b": 3.6, "qwen3-32b": 3.82}},
        "q3": {"type": "yes_no", "answer": "yes", "confidence": 0.96,
               "probabilities": {"yes": 0.96, "no": 0.04},
               "by_model": {"clef-27b": {"yes": 0.93, "no": 0.07}, "…": {}}}
      },
      "usage": {"prompt_tokens": 1840},
      "metrics": {"duration_s": 18.2, "label_mass_min": 0.87},
      "errors": []
    },
    {"path": "inbox/empty.txt", "status": "skipped", "reason": "empty",
     "material": {"type": "text", "images": []},
     "decision": null, "errors": []},
    {"path": "inbox/claim_557.txt", "status": "ok",
     "material": {"type": "text+images", "images": [
                  {"name": "claim_557_p1.jpg", "sha256": "…"},
                  {"name": "claim_557_p2.jpg", "sha256": "…"}]},
     "decision": {"outcome": "manual", "label": "Ручная проверка",
                  "rule": null, "is_default": true},
     "answers": {"…": {}}, "errors": []},
    {"path": "inbox/huge.png", "status": "error",
     "material": {"type": "image", "images": [{"name": "huge.png",
                                               "sha256": "…"}]},
     "decision": null,
     "errors": [{"stage": "server", "model": "clef-27b",
                 "message": "Суммарный объём изображений больше 20 МБ"}]}

```

Принципы схемы:

- `decision.outcome` — **id исхода** из пакета (машинный ключ; ветвление
  скриптов только по нему, `label` — человеческое имя), `rule` — текст
  сработавшего правила (ответ «почему», §4.5).
- `material` — состав материала: `type` ∈ `text | image | text+images`,
  `images[]` — вложения (`name`, `sha256`) в порядке отправки на модель
  (§3.5). Поле добавлено к схеме аддитивно — мажорная версия не меняется.
- `config.hash` / `config.fingerprint` — значения исходного файла;
  `effective_hash` / `effective_fingerprint` — пересчитанные с учётом
  `--models` и `--mode`. Полный effective hash нужен последующему web matching;
  effective semantic fingerprint — ключ `--skip-processed` (§6.3) и основа
  миграционной политики §6.9. Overrides не переписывают пакет. `models` в
  корне — эффективный набор; `models_overridden`, `mode_overridden` и
  `models_pack` делают подмену видимой.
- `answers[q]` — агрегат `mean_probability_v1`, пошедший в правила, плюс
  разрез `by_model` и полные canonical runs: `{model, mode, ok, answers,
  usage, metrics, prompt_format_version?, decision, trace, error?}`. Для
  yes_no/choice вероятности усредняются компонентно по успешному canonical
  проходу и доступным значениям (missing не ноль); score — среднее
  арифметическое. Top answer и ничьи детерминированы порядком вариантов вопроса.
  В `both` canonical outcome строится только по ordinary decisions; fast-проход —
  диагностика без второго веса SGLang, SystemOne/remote chat выполняется один раз.
  В `fast_batch` canonical aggregate использует единственный доступный проход
  каждой модели: fast SGLang и ordinary SystemOne/remote chat. Индивидуальные
  решения и один aggregate decision вычисляет `dqa_common.decision`; сырые
  ответы не выбрасываются. Additive usage суммируется по фактическим вызовам,
  wall duration не суммируется.
- Ошибки — **per-file массив**, не единичное поле: файл может упасть на
  части моделей и всё равно получить решение по остальным — тогда
  `status: "ok"`, но `errors` непуст, модель перечислена. Дефолтный
  `--fail-on error` срабатывает и на такой per-model error; при ослабленной
  политике это degraded exit 2 (§5.2).
- `status`: `ok | error | skipped`; `reason` у skipped:
  `empty | unreadable | encoding | duplicate | already_processed`.
- `run_id` — сквозной корреляционный ключ с серверным журналом (§10).
- stdout всегда UTF-8, `ensure_ascii=false` (кириллица читаема в логах и
  diff'ах; потребители обязаны читать UTF-8 — правило зашито в SKILL).

### 4.2 NDJSON-поток (`--format ndjson`)

Одна строка = одно событие, по мере готовности файлов:

```
{"schema":1,"type":"run_start","run_id":"…","files_total":120,"threads_effective":4,"models":["qwen3-32b"],"models_overridden":true}
{"type":"file","i":1,"path":"…","status":"ok","decision":{…},"answers":{…}}
{"type":"file","i":2,"path":"…","status":"error","errors":[…]}
{"type":"run_end","summary":{…},"duration_s":…,"status":"completed"}
```

Обоснование событийной обёртки (а не «голых» записей файлов): сервер
стримит per-file события (`/api/run`, §12.3) — NDJSON честно их
проксирует; `run_start` несёт `run_id` и `threads_effective`; `run_end`
с `summary` — бесплатный контроль целостности потока (обрыв отличим от
конца); CI стримит решения в следующий шаг, не дожидаясь всей пачки;
крах посередине не портит выданные строки. Цена — обязательная
фильтрация `select(.type=="file")` у потребителя; она зафиксирована как
shape-правило №2 в SKILL.md и показана в каждом NDJSON-рецепте. Порядок
событий — по готовности (`i` — порядковый номер входа), сортировка путей
в стриме не обещается; для предсказуемого порядка — цельный `json`
(файлы отсортированы по пути).

### 4.3 CSV (`--format csv`)

Одна строка на файл: `path,status,outcome,label,confidence,<по колонке
на вопрос — краткий агрегированный ответ>,errors`. Без `by_model` (для
per-model анализа — JSON). Порядок колонок стабилен и следует порядку
вопросов в пакете; новые вопросы — в конец. Кодировка — UTF-8 с BOM
(Excel на Windows открывает кириллицу корректно только так); это
осознанное исключение из «stdout = чистый UTF-8» именно для csv.

### 4.4 Таблица (`--format table`) — опциональный человеческий формат

Колонки `ФАЙЛ | ИСХОД | УВЕРЕННОСТЬ | ВРЕМЯ`, исход подсвечен цветом из
пакета (`color` в outcomes → ANSI). Только когда stdout — TTY: в пайпе
`--format table` → ошибка с подсказкой (парсинг таблицы скриптом
невозможен по построению). ANSI — если терминал поддерживает цвета,
иначе монохром (Windows cmd без VT — читаемая таблица, не мусор из
escape-кодов). Не дефолт: дефолт всегда `json`, потому что
TTY-зависимый auto-формат — второй контракт, который надо тестировать,
а машина — первичный пользователь. Человеку после веб-мастерской таблица
важна, поэтому она есть — но по явному флагу.

### 4.5 `dqa explain` и `dqa diff` — локальные команды разбора

- `dqa explain <path> --report r.json`: из отчёта (без сервера) печатает
  по материалу исход, сработавшее правило (`decision.rule`), ответы с
  вероятностями и разрез `by_model`, ошибки. Закрывает самый частый
  вопрос мастерской «почему этому материалу такое решение» — ответ уже
  лежит в отчёте (`answers` + `rule` + `config.hash`), сервер нужен
  только для сырых ответов моделей по `run_id`.
- `dqa diff r1.json r2.json`: рабочий цикл мастерской «стало ли лучше
  после правки вопроса/правила». Джойн двух отчётов по `content_sha256`:
  переключения исходов (`outcome: invite → reject`) и дельты ответов
  сверх порога. Формат — минимальный: таблица переходов со счётчиками +
  список переключившихся файлов (table в TTY, json в пайпе); отдельной
  версионируемой схемы у diff **нет** — третий выходной контракт не
  вводится. Записи `already_processed` (`answers: null`, §6.3) участвуют
  в переключениях, но не в дельтах. Оба отчёта должны быть полными
  (json или ndjson — формат сниффится). Типовое употребление: один
  вход, два прогона с `--config old.json` / `--config new.json`, затем
  `dqa diff`.

## 5. Exit-коды

### 5.1 Единая таблица

| Код | Условие | Семантика |
|---|---|---|
| 0 | Все файлы ok, политика `--fail-on` не сработала | успех |
| 2 | Есть файлы `status=error`, per-model errors или `skipped` с reason ∈ {empty, unreadable, encoding}; политика НЕ сработала | degraded (частичный успех) |
| 10 | Сработала политика `--fail-on` (включая псевдо-исход `error`) | «проверка не пройдена», данные полные |
| 64 | Ошибка вызова: нет `--config`, неизвестный флаг, несовместимые флаги, опечатка в `--fail-on` | EX_USAGE |
| 65 | Валидация не пройдена: битый пакет (JSON/version/hash, `enabled:false` при CLI `require_decision`), 0 валидных файлов, превышен лимит входа, неоднозначная группировка (§3.5), неизвестный ключ модели (`--models`) | EX_DATAERR |
| 66 | Вход недоступен: пути не существуют | EX_NOINPUT |
| 69 | Сервер недоступен / несовместимы версии схем / обрыв стрима без восстановления | EX_UNAVAILABLE |
| 70 | Внутренняя ошибка клиента / job упал целиком / манифест `--skip-processed` занят другим процессом | EX_SOFTWARE |
| 75 | Истёк `--timeout` (ретрай уместен) | EX_TEMPFAIL |
| 77 | Сервер ответил 401/403 (когда auth появится на сервере, §12.5) | EX_NOPERM |
| 130 | Прервано пользователем (Ctrl-C) — `128+SIGINT` | отмена |

Разнесение: **0/2/10 — о данных** (смотрит логика пайплайна), **≥64 — о
запуске** (смотрит on-call). Ctrl-C — именно 130, а не 75: 130
распознают CI-системы и shell-идиомы, а 75 (EX_TEMPFAIL) означает
«ретрай уместен» — для ручной отмены это ложный сигнал; 75 остаётся
таймауту.

### 5.2 `--fail-on` и приоритеты кодов

`--fail-on reject` / `--fail-on reject,reserve` — id исходов из пакета.
Спец-значения: `error` (**дефолт**; срабатывает на `status=error` и на
любой per-model error, даже если файл получил `status=ok` по остальным
моделям), `any` (любой не-default исход), `none`.
Дефолт `error` делает CLI из коробки честным шагом CI: падение материала
= падение шага; бизнес-решения (`reject`) шаг не роняют, пока явно не
попросили. Id валидируются против пакета до прогона (опечатка → exit 64).

При совпадении условий действует **явный приоритет** (сверху вниз;
применяется первый подходящий):

1. `64/65/66` — вызов и вход (до старта job);
2. `69/77` — сервер недоступен/несовместим/не пустил;
3. `70` — job упал целиком, внутренняя ошибка;
4. `130`, затем `75` — прерывания (отмена пользователем важнее таймаута);
5. `10` — политика `--fail-on` сработала;
6. `2` — degraded без сработавшей политики;
7. `0`.

Следствия, закрывающие прежнее противоречие «1 vs 2»:

- При дефолтном `--fail-on error` файл с ошибкой → exit **10** (ошибка —
  это и есть сработавшая политика), а exit 2 достижим только при
  `--fail-on` без `error` (или `none`) — тогда degraded сигналится
  отдельно. Коды 1 и 3 не используются вовсе (1 зарезервирован, чтобы не
  путаться с родовым failure CI).
- Политика важнее degraded (10 > 2): то, ради чего шаг стоит в CI, не
  должно маскироваться; детальный расклад всегда есть в финальной строке
  stderr (`итог: exit 10 · политика reject: 3 файла · ошибки: 1 файл ·
  пропущено: 2`) и в отчёте.
- `skipped` с reason `already_processed`/`duplicate` — рутинные, на exit
  не влияют (иначе каждый инкрементальный cron-прогон был бы «красным»).

## 6. Пайплайн-механика

### 6.1 Таймауты, ретраи, идемпотентность запросов

Connect-timeout 10 c (фикс.), read — без лимита (job живёт долго, события
идут стримом). `--timeout SEC` — общий дедлайн: истёк → клиент запрашивает
отмену job, частичные результаты пишутся (в `--report` всегда), exit 75.
`--retry N` (дефолт 2): только транспортные сбои и 5xx, backoff
1s→2s→4s + jitter. 4xx (422 валидация, 409 модель не запущена) не
ретраятся — они детерминированы. Создание job несёт client-supplied
`Idempotency-Key` (uuid на вызов): повтор после обрыва сети не плодит
второй прогон (серверная часть — §12.3). Сам прогон чисто
вычислительный, побочек нет — повторный вызов безопасен по построению;
при `--skip-processed` повтор просто догонит манифест.

### 6.2 Отмена и сигналы — best-effort, честные статусы

SIGINT/SIGTERM: клиент шлёт `POST /api/run/{run_id}/cancel`, ждёт
подтверждения до 5 c, сохраняет частичные результаты, exit 130. Второй
Ctrl-C — немедленный выход с `run_id` в stderr для ручной отмены.
Отмена — **best-effort, а не гарантия**: сервер помечает job
`cancel_requested`, гасит asyncio-таски (httpx-коннекты закрываются;
sglang обычно прерывает генерацию по дисконнекту — подлежит
верификации), но облачные API не отменяются — их токены уже сожжены.
Финальный статус job — `cancelled` или `completed_partial`; оба честно
отражаются в `run_end.status` (`completed | cancelled |
completed_partial`) и stderr. На Windows семантика
Ctrl-C/Ctrl-Break в консоли эквивалентна (console control handler);
принцип «не оставлять сироту-прогон, жгущий GPU» — главная причина, что
отмена обязательна, пусть и best-effort.

### 6.3 Идемпотентность между прогонами — `--skip-processed FILE`

FILE — пополняемый NDJSON-манифест
`{"key": "sha256:…", "fingerprint": "sha256:…", "outcome": …, "run_id": …}`.
**Ключ = content_sha256 материала (§3.5) + эффективный
`config.effective_fingerprint`** (при `--models` — пересчитанный клиентом, §12.2:
два набора моделей на одном входе — разные ключи, чужие решения не
подставляются): переименование файла не провоцирует перепрогон,
изменение содержимого — провоцирует, семантическая смена пакета
(правила, вопросы, модели → новый fingerprint) инвалидирует старые
записи, а косметика (label, color) — нет (§6.9, §12.2). Файлы с совпавшим ключом получают `status:
"skipped", reason: "already_processed"` и не уходят на сервер; при этом
в запись отчёта CLI **подставляет решение из манифеста**
(`decision.outcome` и `run_id` прошлого прогона) — потребитель ниже по
пайплайну видит однородные решения и доисполняет сбойные действия
(§6.8). У таких записей **`answers: null`** (ответов в манифесте нет;
опционально манифест может хранить весь per-file JSON — тогда
подставляются и answers). **Single-writer**: клиент
берёт эксклюзивную advisory-блокировку манифеста (flock / LockFileEx) на
весь прогон; занят → до 5 c ожидания, затем exit 70 с текстом «манифест
занят другим процессом dqa; дождитесь его или используйте отдельный
манифест». Параллельные cron-инстансы обязаны иметь либо разные
манифесты, либо сериализоваться блокировкой — это задокументированное
правило, а не молчаливая гонка с порчей файла. Рост манифеста без GC —
принятая цена (append-only журнал — это и есть аудит; ротация — §14).

### 6.4 `--report <path>` — артефакт аудита

Полный JSON-отчёт (схема §4.1, без `--outcome-filter`)
пишется на диск независимо от stdout-формата, атомарно
(временный файл + rename; для больших прогонов — NDJSON-режим §3.4).
Типовая схема: stdout кормит следующий шаг пайпа, `--report` — артефакт
для `dqa explain`, `dqa diff` и аудита. Отмена/таймаут/обрыв не теряют
частичный отчёт.

### 6.5 Обрыв стрима событий

Обрыв SSE/стрима посреди job ≠ отмена: job продолжает работать на
сервере. Клиент делает `--retry` попыток переподключения. В v1
переподключение начинает стрим заново (события с начала; клиент
дедуплицирует по `i`/`path` — записи идемпотентны). Целевое решение —
reattach по `run_id` с продолжением после последнего `seq`
(`GET /api/run/{run_id}/events?after=<seq>`) и `dqa run --attach
<run_id>` — отложено в v1.1 как зависящее от server-side ретеншена job
(§12.3, §15). Исчерпание ретраев → exit 69, в stderr — `run_id` и
подсказка «job жив на сервере, результаты не потеряны».

### 6.6 Прогресс и наблюдаемость

В stderr: строка прогресса `12/120 files · 2 err · eta 4m10s`
(перерисовка `\r` только на TTY; в пайп — построчно, пригодно для логов
CI), диагностика сервера, deprecation warnings. `--quiet` — только
фатальные ошибки (в cron тишина — by design: шаг, ждущий уведомления,
обязан ветвиться по exit-коду сам; это оговорено в SKILL и примерах).
`--verbose` — события job, ретраи, HTTP-трасса, `run_id`. Тела
материалов в логи клиента не попадают никогда (приватность по
умолчанию). Корреляция: `run_id` печатается в stderr при старте и лежит
в корне результата; серверный журнал индексируется по нему; «почему
такое решение» — через `dqa explain` из отчёта (§4.5), глубже — по
`run_id` на сервере.

### 6.7 Интеграционные паттерны потребителя

Следующий шаг после утилиты — детерминированный обработчик в ИС
заказчика (скрипт, не агент). Граница ответственности едина: **dqa
считает, потребитель действует**; dqa не пишет во внешние системы
(хуки отвергнуты, §13); контракт — отчёт §4.1 плюс exit-коды §5.

- **Папка-обменник → прогон → разметка в ИС** (основной сценарий:
  скрининг резюме, рекламации). ИС выгружает файлы; обработчик:
  `dqa validate` → `dqa run --skip-processed … --report r.json` → скрипт
  проставляет статусы по `outcome.id`. Прогон упал (exit ≥64) — разметка
  не запускается; разметка упала — перезапускается на том же отчёте
  (§6.8), перепрогон не нужен.
- **Cron-поллинг** — та же связка по расписанию, инкрементально
  (сценарий №2 §11): `already_processed` несут решения (§6.3) —
  обработчик доисполняет действия, сбойные в прошлый запуск.
- **CI-gate** — read-only: `dqa run --fail-on reject --report
  artifacts/gate.json`, exit 10 = блок публикации (сценарий №1 §11).
- **Очередь/broker** — worker прогоняет сообщения одиночными вызовами
  или микробатчами `--files-from`; exit-код маппится в ack (0/2/10) /
  nack с requeue (69/75) / dead-letter (64/65/66); redelivery лечится
  журналом §6.8.

Обязанности потребителя (зашиты в SKILL.md): ветвление по `outcome.id`
с default-веткой; действия — по финальному отчёту с журналом (§6.8);
exit-код — до разбора stdout.

Единый рабочий обработчик (python, ~30 строк) — входная точка howto;
справка по нормам — §6.8:

```python
#!/usr/bin/env python3
# «Прогон → разметка статусов в ИС». Журнал ОБЯЗАТЕЛЕН: записи
# already_processed несут решения всей истории (§6.3) — без журнала каждый
# запуск переисполнял бы её целиком (DOS собственной ИС).
import json, os, subprocess, sys

REPORT, LEDGER = "state/r.json", "state/done.ndjson"
STATUS = {"invite": "invited", "reserve": "reserve", "reject": "rejected"}
code = subprocess.run(["dqa", "run", "--config", "packs/screening.json",
    "exchange/in/", "--skip-processed", "state/seen.ndjson",
    "--report", REPORT, "--fail-on", "none"]).returncode
if code >= 64:   # сбой запуска, не данных — разметку не начинаем
    sys.exit(f"dqa failed: exit {code}")
report = json.load(open(REPORT))
fp = report["config"]["effective_fingerprint"]
done = {json.loads(l)["key"] for l in open(LEDGER)} if os.path.exists(LEDGER) else set()
with open(LEDGER, "a") as ledger:   # append-only + flock, философия §6.3
    for f in report["files"]:
        if not f.get("decision"):
            continue                # error/skipped без решения — не наша забота
        key = f"dqa:{fp}:{f['content_sha256']}"
        if key in done:
            continue                # уже исполнено
        outcome = f["decision"]["outcome"]
        if outcome not in STATUS:   # default-ветка: новый исход — алерт
            sys.exit(f"ALERT: неизвестный исход {outcome} ({f['path']}) — проверьте пакет")
        # set-status идемпотентен сам; create-действия — только с key как
        # внешним id (create-if-absent), иначе дубли
        is_set_status(f["path"], STATUS[outcome], idempotency_key=key)
        ledger.write(json.dumps({"key": key, "outcome": outcome,
                                 "run_id": report["run_id"]}) + "\n")
```

### 6.8 Идемпотентность downstream-действий

`--skip-processed` (§6.3) решает «не пересчитывать», но не «не
переделывать»: статус в ИС можно проставить дважды — этот слой целиком
на стороне потребителя. Четыре нормы:

1. **Действия — по финальному отчёту, не по стриму.** NDJSON — для
   наблюдения; стрим не гарантирует полноты (обрыв/отмена) и
   однократности потребления — действие по событию внутри цикла при
   повторе даёт двойные действия.
2. **Ключ действия — `dqa:<config.effective_fingerprint>:<content_sha256>`.**
   Материал адресуется `content_sha256` (переживает переименование;
   `path` — не ключ), редакция правил — fingerprint: смена правил даёт
   новое действие, повтор по ключу — no-op. `run_id` — для аудита.
   Версия модели на сервере в ключ не входит: апгрейд весов меняет
   ответы без смены fingerprint — задокументированный риск, манифест
   тогда обновляют осознанно.
3. **Действие идемпотентно в целевой ИС.** «Проставить статус»
   идемпотентно само; «создать тикет» — передавая ключ как внешний id
   (create-if-absent). ИС без внешних ключей → журнал действий (ниже) —
   единственная защита, single-writer обязателен.
4. **Восстановление = перезапуск обработчика целиком** на том же
   отчёте (не «с середины»). Сбой внутри прогона — перезапуск всей
   связки: `--skip-processed` не пересчитает материалы, а решения в
   записях `already_processed` (§6.3) дадут доисполнить действия.

Журнал действий — append-only NDJSON с блокировкой (философия §6.3);
рабочий шаблон — единый обработчик §6.7.

### 6.9 Устойчивость интеграций к изменению пакета

Пакет правил — живой; интеграции (jq-фильтры, `--fail-on`, скрипты
разметки) не должны рушиться от минимальных правок. Четыре решения.

**(а) Опора на `outcome.id`, не на label/порядок/индекс.** Id
генерируется один раз и не редактируется; в редакторе он показан только
для чтения (`<code>` в свёрнутом и развёрнутом состоянии) — **неизменяем
по построению**. Экспорт пресета/пакета и batch JSON dump сохраняют его
дословно (проверено по коду, закреплено в §12.2). Потребитель ветвится
`select(.decision.outcome=="reject")` — никогда по label или индексу
(§2.4, shape-правило №4 SKILL.md).

**(б) Два хэша вместо одного: `hash` + `fingerprint`.** Полный `hash`
меняется от любой правки — ключ идемпотентности на нём жёг бы
перепрогон от каждой косметики. `fingerprint` — хэш только «действующей
конфигурации»: вопросы, правила, id **и порядок** исходов (движок
first-match, `decision.js:88-104`), модели; без label/color и прочей
косметики (точный состав — §12.2). Fingerprint — ключ
`--skip-processed` (§6.3) и downstream-действий (§6.8).

**(в) `--fail-on` — по id; исчезнувший id ловится до прогона** — exit
64 со списком актуальных id (§2.3, §5.2); актуальные id — из `dqa pack
show`.

**(г) Миграция на новую редакцию — три шага существующими средствами:**
A/B-прогон эталона + `dqa diff` (все переключения исходов, §4.5);
ревизия id — `jq -r '.decision.outcomes[].id' old.json new.json | sort |
uniq -c` (`dqa pack diff` — v1.1, §15); выкатка — манифест сам
инвалидируется по fingerprint, действия перепроставляются с новыми
ключами (§6.8). Откат = возврат файла пакета.

**Матрица устойчивости:**

| Изменение пакета | Влияние на интеграцию | Защита |
|---|---|---|
| Переименован `label` / изменён `color` исхода (id тот же) | нет: ветвление по id; меняется только вывод для людей | контракт (а); `fingerprint` не меняется → без перепрогона |
| Переупорядочены исходы (те же id) | решения могут измениться (first-match); jq по id не ломается. Цена: пересчёт всей накопленной истории — перед выкаткой проверяйте план через validate | порядок входит в `fingerprint` → авто-перепрогон; `dqa diff` показывает переключения |
| Добавлен исход (новый id) | в отчётах появляются новые значения `outcome` | default-ветка обработчика: неизвестный id = алерт, не скип (§6.7) |
| Удалён исход | `--fail-on` с мёртвым id → exit 64 до прогона со списком актуальных; jq-фильтры перестают матчить | валидация id до прогона (в); ревизия (г) |
| Изменены правила/пороги, вопросы, модели | решения меняются ожидаемо | `fingerprint` → авто-перепрогон; `dqa diff` для приёмки |
| Изменён порядок вопросов | `answers` адресуются по id; ломаются только колонки CSV (§4.3) | машинные потребители — на json/ndjson |
| Переименование самого id исхода | убило бы все интеграции | невозможно по построению (а) |

## 7. Многопоточность

`--threads N` — **пожелание серверу**, не локальный пул. Параллелятся
материалы внутри job на сервере; внутри материала модели идут
параллельно (как `asyncio.gather` по `req.models` в `/api/decide`,
`backend/app.py:488`). Семантика:

- **Дефолт — серверный, не зашитый в клиенте**: без флага клиент не
  передаёт значение; сервер знает свои модели, RAM и очередь GPU,
  клиент — нет. Рекомендуемый серверный дефолт объявляется в
  capabilities (`default_threads`, §12.4).
- Сервер вправе зажать значение своим лимитом (`max_threads`); факт
  возвращается в `run_start.threads_effective` и stderr-прогрессе.
  Реальный ускоритель — внутренний батчинг/очередь модельного сервера,
  а не наши потоки; поэтому `threads_effective`, а не обещание.
- **Backpressure**: загрузка материалов чанками (§12.3); переполненная
  очередь сервера отвечает 429 + `Retry-After` — клиент ждёт и повторяет
  чанк (не расходует ретраи сбоев). В v1 серверного 429 может не быть —
  деградация до обычных 5xx-ретраев зафиксирована как допустимая (§12.4).
- **Частичные сбои моделей**: одна модель из `models[]` упала на файле →
  решение по оставшимся, `errors[]` фиксирует модель и причину (зеркало
  per-model `{ok:false,error}` из `/api/decide`); упали все →
  `status: "error"` файла, остальные продолжаются. Строгость реакции —
  через `--fail-on` (дефолт `error`).
- **Переопределённые модели (`--models`)** ведут себя по тем же правилам:
  серверный дефолт/лимит потоков и обработка остановленной модели не
  зависят от того, пришёл набор из пакета или из флага.

## 8. Конфигурация клиента

### 8.1 Иерархия и профили

Приоритет (сверху вниз): **флаги → env → файл → дефолт**.

- Файл: `~/.config/dqa/config.toml` (macOS/Linux) /
  `%APPDATA%\dqa\config.toml` (Windows), права 600 при создании через
  `dqa config`. Формат:
  ```toml
  default_profile = "local"
  [profiles.local]   server = "http://127.0.0.1:8000"
  [profiles.staging] server = "https://dqa.staging.example.com"
  ```
- Env: `DQA_SERVER`, `DQA_TOKEN` (впрок, §12.5), `DQA_PROFILE`,
  `DQA_CONFIG_DIR`.
- Флаги: `--server`, `--profile`.
- Дефолт без конфига: `http://localhost:8000`, без токена.

`dqa config show` печатает эффективные значения **с источником каждого**
(`server = … # env DQA_SERVER`), токен маскируется (`dqa_…f3a9`) —
это ответ на «почему он ходит не на тот сервер». Агент в CI использует
только env (файл не нужен, секреты не седлаются в конфиги); человек —
профили.

### 8.2 Токен — никогда флагом

Флага `--token` **нет по построению**: значение флага видно в
`ps`/журналах CI. Токен доступа к серверу — только `DQA_TOKEN` или файл
конфига (600). В v1 серверной auth нет (§12.5): поле и env зарезервированы,
клиент шлёт заголовок, если токен задан, сервер его пока игнорирует;
401/403 клиент обрабатывает уже сейчас (exit 77 с текстом «проверьте
DQA_TOKEN»), чтобы включение auth на сервере не ломало CLI-контракт
задним числом. В SKILL.md токен помечен «заработает, когда появится auth
на сервере» — агенту не обещают несуществующее.

### 8.3 `dqa doctor`

Единая диагностика среды одной командой (первый запуск на новой машине):
версия Python/бинаря и платформа → доступность сервера →
`/api/version` и совместимость схем → capabilities (лимиты, threads) →
статусы моделей (`/api/health`) → auth-проба → при указании пакета — его
валидация и список исходов. Каждая проверка — строка `OK/FAIL + что
делать`. Exit 0, только если всё зелёное; первый FAIL → соответствующий
код (69/77/65). Для агентов — `--format json`.

## 9. Дистрибуция (Win/Mac)

### 9.1 v1: python-модуль в релизном zip со шимами

Утилита едет **в том же релизном zip**, что и приложение
(`scripts/build_release.sh`, `dist/decision-qa-{mac-arm64,windows}.zip`):
каталоги `cli/` с пакетом `dqa` и независимый `dqa_common/` (Python
≥3.12; явные зависимости `httpx` и `rfc8785`, остальное stdlib) + шимы
`dqa` (shell) и `dqa.cmd` (Windows).
Шим обязан: предпочесть Python из venv проекта (co-located установка),
иначе найти системный (на Windows — лаунчер `py`, не только `python` на
PATH), проверить версию и наличие `httpx`/`rfc8785`, при нехватке —
честный текст «что делать» + отсылка к `dqa doctor`. Версия CLI =
`VERSION` проекта, релизный цикл общий. Требования: Windows 10+
(cmd/PowerShell), macOS 13+ arm64, сеть до сервера.

Обоснование фазы: нулевая новая сборочная цепочка, co-located сценарий
(та же машина, что и приложение) покрыт сразу. Признаваемая правда: цена
CLI — на других машинах (CI-раннер, ноутбук аналитика), где Python'а
может не быть.

### 9.2 Цель: single-binary — зафиксирована

Как только появится потребитель CLI вне серверной машины — сборка
`dqa-windows-x64.exe` / `dqa-macos-arm64` (PyInstaller `--onefile`,
~15–25 МБ) на существующих релизных раннерах обеих платформ. Контракт
CLI (флаги, exit-коды, схема) спроектирован так, что переезд трогает
только упаковку: stdlib + две явные внешние зависимости
`httpx`/`rfc8785` переживают PyInstaller тривиально. Самообновления не будет никогда:
непиннутая версия убивает воспроизводимость конвейера; обновление —
осознанный шаг, при смене мажорной `schema` релиз несёт миграционную
заметку.

### 9.3 Кириллица и Windows-консоль

Заявленная поддержка Windows при русскоязычном продукте требует явных
решений (все — v1): stdout всегда UTF-8 (`ensure_ascii=false`); клиент
переключает консоль Windows на UTF-8 для своего вывода (и восстанавливает
по выходу); ANSI — при поддержке терминалом, иначе монохром; stderr
пишется в UTF-8 независимо от cp866/cp1251
консоли; входные тексты — `utf-8-sig` с флагом `--encoding cp1251`
(§3.3); пути с кириллицей и пробелами — через `--files-from --null` или
манифест (§3.1), никогда через построчный `ls`. CSV — UTF-8 с BOM (§4.3).

name: decision-qa

# decision-qa (dqa)

## Когда применять
Есть конфиг-пакет pack.json (экспорт из веб-интерфейса Decision-QA) и файлы,
по которым нужны решения. НЕ применять, если правила ещё не отлажены —
это делается в веб-мастерской.

## Предусловия и эскалация
1. Сначала `dqa doctor` (или `dqa doctor --format json`). Не прошёл —
   ОСТАНОВИСЬ и сообщи человеку текст FAIL-строки; НЕ чини сервер сам,
   НЕ ретрай в цикле.
2. Не знаешь id исходов для --fail-on — `dqa pack show pack.json`, не гадай строками.
3. Большой прогон (сотни+ файлов) — всегда сначала `dqa validate`:
   она покажет files_ok, оценку времени и ошибки входа без расхода моделей.

## Контракт вызова
dqa run --config pack.json [файлы|директория [--glob '*.txt'] |
        --files-from list.txt [--null] | --manifest m.json | --stdin]
        [--image img.png ...] [--format ndjson|json|csv] [-o out.json]
        [--report r.json] [--fail-on outcome1,outcome2|error|any|none]
        [--models key1,key2] [--threads N] [--timeout SEC]
        [--skip-processed seen.ndjson] [--quiet]
Обязательно: --config и источник входа (для stdin — явный --stdin).
Сервер: env DQA_SERVER. Токен: ТОЛЬКО env DQA_TOKEN (флага токена нет;
auth появится на сервере позже — тогда DQA_TOKEN заработает; сейчас
сервер его не требует). Никогда не передавай секреты аргументами командной
строки — они видны в ps и логах.

## Коды выхода — проверяй ПЕРЕД разбором stdout
0  все ок, политика --fail-on не сработала
2  частичный успех: есть файлы status=error/skipped — разбери
   .files[] | select(.status != "ok"), это НЕ фатал
10 сработала политика --fail-on (по дефолту error): данные полные, решай
   по .summary и .files[] — это сигнал о ДАННЫХ, не о сбое конвейера
64/65/66  ошибка вызова/валидации/входа — чини аргументы, НЕ ретрай
69  сервер недоступен/несовместим или оборвался стрим — ретрай позже,
    при повторе — эскалация человеку (см. run_id в stderr)
70  внутренняя ошибка / job упал / манифест занят другим процессом
75  истёк --timeout — ретрай уместен (частичные данные в --report)
77  401/403 — проверь DQA_TOKEN (когда auth включена на сервере)
130 прервано пользователем (Ctrl-C), job на сервере отменяется

## Форма вывода (shape-правила — читай всегда)
1. stdout — ТОЛЬКО данные; stderr — прогресс и логи, оттуда данные НЕ читать.
2. json: ВСЕГДА конверт — результаты только в .files[] (даже для одного
   файла это .files[0]); счётчики в .summary; версия контракта — "schema": 1;
   неизвестные поля ИГНОРИРОВАТЬ (схема растёт только добавлением полей).
3. ndjson: строка = СОБЫТИЕ; записи файлов — только
   select(.type=="file"); run_start/run_end — обрамление (summary в конце
   потока — контроль его целостности). Никогда не разбирай ndjson без
   фильтра по .type.
4. Решение читай из .files[].decision.outcome (id исхода), НЕ парси label.
   label и порядок исходов — не контракт: label свободно переименовывают
   между версиями пакета, ветвление по label/индексу сломается.
5. Файл может быть ok с непустым errors[] (упала часть моделей) — при
   важности per-model смотри .files[].answers.<q>.by_model.
6. stdout — UTF-8 с кириллицей без экранирования; читай как UTF-8.
7. Тип материала — .files[].material.type (text|image|text+images),
   вложения — .files[].material.images[] в порядке отправки на модель.

## Правила интеграций (если по результатам действует другой софт)
1. Ветвление строго по outcome.id; разбор исходов ИСЧЕРПЫВАЮЩИЙ, с
   default-веткой: неизвестный id (в новой версии пакета добавили исход) —
   алерт человеку, а не молчаливый пропуск.
2. Мутирующие действия во внешних системах — ТОЛЬКО после завершения
   прогона, по финальному отчёту (json/-o/--report). NDJSON-стрим — для
   наблюдения; действие по событию внутри стрима = гонка и двойные действия.
3. Действия идемпотентны: ключ действия dqa:<config.effective_fingerprint>:<content_sha256>
   (статус идемпотентен сам; тикет — ключ как внешний id, create-if-absent).
   path — не ключ (переименование = «новый» объект). Сбой посреди обхода:
   перезапусти обработчик на том же отчёте целиком — already_processed
   несут решение из прошлого прогона, действия доисполнятся.
4. Журнал действий обязателен (ИС без внешних ключей): append-only
   done.ndjson {key, outcome, run_id} после каждого успешного действия;
   ключи из журнала пропускаются. Без журнала каждый запуск переисполняет
   всю историю already_processed — DOS собственной ИС.
5. Косметическая правка пакета (label/color) НЕ меняет config.effective_fingerprint и
   не требует перепрогона; смена правил/вопросов/моделей — меняет, и
   --skip-processed сам инвалидирует старые записи.
6. --models — для отладки и A/B; в продакшн-cron модели — только из пакета.
   Подмена всегда видна в отчёте (config.models_overridden), ключи
   идемпотентности разных наборов разделены эффективным fingerprint.

## Лимиты входа (узнавай здесь, а не из ошибок)
≤8 изображений на материал; ≤20 МБ base64 суммарно; тексты >~200 КБ —
дорогой prefill, лучше резать; типы: .txt .md .json .png .jpg .jpeg .webp .gif;
HEIC не поддерживается (конвертируй в JPEG). Актуальные значения —
`dqa doctor` (capabilities сервера).

## Рецепты
1. Разобрать входящие интервью (инкрементально, идемпотентно):
   dqa run --config screening.json inbox/ --glob '*.txt' \
     --skip-processed seen.ndjson --report r.json --format json -o out.json
2. Только «на разбор» из отчёта:
   jq -r '.files[] | select(.decision.outcome=="reserve") | .path' r.json
3. Один текст из переменной:
   printf '%s' "$text" | dqa run --config pack.json --stdin --name case.txt
   …исход: jq -r '.files[0].decision.outcome' из вывода
   Одиночный материал с фото:
   dqa run post.txt --image p1.png --image p2.png --config p.json \
     | jq -r '.files[0].decision.outcome'
4. Стрим с реакцией по мере готовности (БЕЗ перемещения файлов внутри цикла —
   сначала собери исходы, действуй после завершения прогона):
   dqa run --config pack.json inbox/ --format ndjson \
     | jq -rc 'select(.type=="file") | {path, outcome: .decision.outcome}' \
     > outcomes.ndjson
   # затем — действия по outcomes.ndjson (прогон уже завершён)
5. Почему материалу такое решение:
   dqa explain inbox/ivanov.txt --report r.json
6. Сравнить две версии правил (A/B пакета):
   dqa run --config old.json inbox/ -o r1.json --fail-on none
   dqa run --config new.json inbox/ -o r2.json --fail-on none
   dqa diff r1.json r2.json
   A/B моделей (тот же пакет): то же с --models clef-27b / --models qwen3-32b
7. Проверка перед большим прогоном:
   dqa validate --config pack.json big_folder/ --format json \
     | jq '{files_ok, est_requests, estimate_s}'
8. Рекламации «письмо + фото» из папки-обменника (конвенция basename):
   # claim_557.txt + claim_557_p1.jpg + claim_557_p2.jpg → один материал
   dqa validate --config returns.json /exchange/claims/   # СНАЧАЛА: группы
     # validate покажет text+N images по каждому материалу и картинки,
     # не подошедшие ни к одному тексту (станут отдельными материалами)
   dqa run --config returns.json /exchange/claims/ \
     --skip-processed seen.ndjson --report r.json --fail-on none
   # раскладка по исходам — по .files[].decision.outcome (id!),
   # см. правила интеграций

## Типичные ошибки агента
- Забыт --config → exit 64. - Нет файлов поддерживаемого типа → files_total=0,
  exit 65. - Разбор ndjson без select(.type=="file") — сломается на run_start.
- Не проверен exit-код до jq: при ≥64 stdout может быть пуст.
- Перемещение/удаление входных файлов, пока прогон ещё идёт, — гонка;
  действия над файлами — только после завершения dqa.
- Ветвление по label или порядку исходов вместо outcome.id — сломается на
  первой косметической правке пакета.
- Пакет «письма + фото» без validate: картинки, не подошедшие под конвенцию,
  ушли отдельными материалами и получили собственные решения (следи за
  счётчиком сирот в stderr).
- Кириллические тексты с Windows-машин → reason "encoding": чини флагом
  --encoding cp1251, не перекодируй файлы молча сам.
- Повторный прогон «в лоб» после обрыва: безопасен (прогон вычислительный),
  а с --skip-processed ещё и догонит только необработанное.

## 11. Примеры (сценарии)

**1. CI-gate: проверка папки входящих, блок по отклонённым.**
```bash
dqa run --config packs/moderation.json incoming/ \
  --fail-on reject --report artifacts/moderation.json
# exit 10 → джоба красная; отчёт — артефакт сборки
```

**2. Ночной cron: отчёт, ретраи, идемпотентность, тишина.**
```bash
dqa run --config packs/returns.json /data/claims/ --recursive \
  --timeout 7200 --retry 4 --fail-on none \
  --report /reports/claims-$(date +%F).json \
  --skip-processed /data/.dqa-processed.ndjson --quiet
# уведомления — по exit-коду самим cron-обёртчиком, не из логов dqa
```

**3. Взгляд человека после отладки вопросов в вебе.**
```bash
dqa run ~/interviews/ --glob '*.txt' --config packs/support-qa.json \
  --format table --report reports/interviews.json
dqa explain ~/interviews/ivanov.txt --report reports/interviews.json
```

**4. Агентский скилл «разбери входящие интервью» — стрим, действия после
завершения.**
```bash
dqa run --config packs/interviews.json --manifest new.json --format ndjson \
  | jq -rc 'select(.type=="file") | {path, outcome: .decision.outcome}' > outcomes.ndjson
# затем — раскладка/действия по outcomes.ndjson (прогон уже завершён)
```

**5. Интеграция с последующим софтом через exit-код + JSON.**
```bash
dqa run --config pack.json batch/ -o r.json --fail-on reject
code=$?
case $code in
  0)  python publish.py --decisions r.json ;;
  10) python triage.py --decisions r.json ;;
  2)  python triage.py --decisions r.json --include-errors ;;
  *)  alert "dqa failed: exit $code" ;;   # ≥64: сбой запуска, не данных
esac
```

**6. Один материал из stdin внутри агента.**
```bash
cat transcript.txt | dqa run --config packs/interviews.json \
  --stdin --name candidate_557.txt | jq -r '.files[0].decision.outcome'
```

**7. Оценка перед большим прогоном.**
```bash
dqa validate --config packs/photos.json photos_40k/ --format json \
  | jq '{files_ok, est_requests, estimate_s}'
```

**8. A/B правил в мастерской (тот же вход, два пакета).**
```bash
dqa run --config packs/v3.json bench/ -o r_v3.json --fail-on none --quiet
dqa run --config packs/v4.json bench/ -o r_v4.json --fail-on none --quiet
dqa diff r_v3.json r_v4.json
```

**9. Windows: кириллические пути и кодировка.**
```cmd
find-действие не нужен: dqa run "C:\интервью" --glob "*.txt" --encoding cp1251 ^
  --config pack.json --format csv -o razbor.csv
```

**10. Рекламации из ИС: письма с фото, разметка статусов обратно.**
ИС вываливает в обменник `claims/`: `claim_557.txt` + `claim_557_p1.jpg` +
`claim_557_p2.jpg` (конвенция basename, §3.5) — пакет `returns.json` с
вопросами по тексту и фото (аналог пресета `batch_returns_claims.json`).
```bash
dqa validate --config packs/returns.json /exchange/claims/
# каждый claim_* — материал text+N images; «сиротские» фото — предупреждение
dqa run --config packs/returns.json /exchange/claims/ \
  --skip-processed /data/.dqa-claims.ndjson \
  --report /reports/claims-$(date +%F).json --fail-on none --quiet
python mark_claims.py --report /reports/claims-$(date +%F).json
# ветвление по outcome.id, идемпотентные статусы в ИС, журнал (§6.7-§6.8)
```
Если ИС выгружает `claims/<id>/letter.txt + фото` — до появления
конвенции «подпапка = материал» (v1.1, §15) скрипт выгрузки генерирует
`--manifest`, результат тот же.

**11. A/B моделей из командной строки (тот же пакет).**
```bash
dqa run --config packs/screening.json bench/ --models clef-27b \
  -o r_a.json --fail-on none --quiet
dqa run --config packs/screening.json bench/ --models qwen3-32b \

dqa diff r_a.json r_b.json   # переключения исходов между моделями
# подмена видна: config.models_overridden=true + models_pack;
# матрицы прогонов нет — один флаг = один набор, A/B = два прогона + diff
```

## 12. Зависимости от сервера (блокеры, в честном порядке)

CLI не строится, пока не решены (1)–(3); (4)–(5) — до выкатки за пределы
одной машины. Порядок важен: это, а не форматы вывода, определяет сроки.

### 12.1 Реализовано: общий Python-порт; остаётся подключение к run engine

`dqa_common/decision.py` — независимый от FastAPI/backend порт
`conditionDetail`/`evalRules`/`evaluateDecision`/`explainDecision` с
JS-shaped camelCase output. Общая fixture
`backend/tests/fixtures/decision_parity.json` исполняется и pytest, и node:
точные ключи результата и полный trace, threshold 0.5/score 0, только `lt`
отличается от `gte`, empty-condition rules пропускаются без trace, порядок
outcome/rule и first hit, первый default (у default тоже могут быть rules),
missing values → `value:null, ok:false`, no hit без default → `null`, полный
trace у explain. Пустые dict/list и ноль учитываются по JS-truthiness;
`enabled` остаётся обязанностью вызывающего слоя. Старый `/api/decide` и его
HTTP-ответ этим изменением не затронуты; следующий server run engine должен
вызывать этот порт, а не создавать вторую реализацию правил.

### 12.2 Реализовано: конфиг-пакет v1 и JCS parity

Новый пакет отделён от legacy-пресетов (их формат и нормализация не меняются).
Структура: `version:1`, `fingerprint_version:1`, `questions`, `decision`,
`settings{mode, models, temperature?, prompt_formats?, inference?,
aggregation:"mean_probability_v1"}`, опциональные `name`/`description`/`ui`,
`hash`, `fingerprint`. Дополнительные execution-поля settings входят в
semantic projection — изменение любого inference-параметра обязано менять
effective fingerprint. Материалы в пакет не встраиваются. Веб собирает его
через «Файл → Экспорт конфига для CLI» из `buildQuestionsPayload` и clean
decision без `collapsed`/UI; direction остаётся в полном пакете, но не в
семантике. Batch записывает фактический `decisions`; temperature присутствует
только как реальный inference-параметр.

- **Строгая валидация.** Общие Python/JS validators проверяют структуру
  question/outcome/rule/condition, типы, references и диапазоны согласованно с
  текущими схемами. ID вопросов/исходов обязательны, непусты и уникальны и
  никогда не перегенерируются. Пустые web-наборы и empty-condition rules не
  запрещены искусственно. Python loader дополнительно отклоняет duplicate JSON
  keys и NaN/Infinity. `decision.enabled:false` легален в shared/web-валидации
  и входит в fingerprint; CLI decision pipeline вызывает валидацию с
  `require_decision:true` и отклоняет такой пакет (exit 65 с подсказкой).
- **Полный `hash`.** `sha256:` + SHA-256 от RFC 8785/JCS полного пакета без
  **обоих** полей `hash` и `fingerprint`. Входят name/description, direction,
  label/color и UI: любая такая правка меняет integrity hash, но не обязана
  запускать перепрогон.
- **Семантический `fingerprint`.** SHA-256 от JCS явной проекции:
  questions{id,type,question,yes,no,options(name+description),levels} в исходном
  порядке, decision{enabled,outcomes:[{id,isDefault,rules}]} с порядком
  исходов/правил/условий, settings{mode,models(сортированные),temperature? и
  все прочие inference-параметры,aggregation}. Исключены label/color исходов,
  direction, name/description и UI; описания опций входят, поскольку попадают
  в промпт. Порядок моделей сам по себе fingerprint не меняет.
- **Effective overrides.** `--models` и `--mode` изменяют только effective
  copy. Клиент пересчитывает и semantic fingerprint, и effective full hash;
  исходный файл и его hash/fingerprint остаются неизменными. Оба effective
  значения доступны для последующего web matching и попадают в отчёт (§4.1).
- **JCS — только проверенные библиотеки.** Python dependency —
  `rfc8785==0.1.4` (Trail of Bits, Apache-2.0); browser — vendored
  `canonicalize 2.1.0` (Apache-2.0) с pinned commit, tarball integrity и
  лицензией в `frontend/static/vendor/`. Своя каноникализация запрещена.
  `backend/tests/fixtures/config_pack_parity.json` общий для pytest/node и
  включает официальные RFC-vectors с provenance, Unicode key ordering, `-0`,
  exponent forms, `0.30000000000000004`, cosmetic vs semantic edits, overrides,
  material fingerprints и aggregation/both/partial cases.
- **Prompt formats.** Effective config хранит optional per-model
  `prompt_formats`; экспорт из веба переносит туда текущий `pinnedFormats`
  для воспроизводимости существующего прогона. Если версия не задана, server run
  закрепляет первую успешно сообщённую версию на весь job и записывает
  фактические версии в итоговый effective config/result; новые прогоны больше
  не полагаются на клиентский pin.
- **ID дословно.** Веб показывает `outcome.id` read-only в обоих состояниях
  карточки; rename/reorder/collapse/normalize/export его не меняют. Batch JSON
  dump аддитивно содержит `decisions[file][model].id`. Потребители продолжают
  ветвиться по ID, а не label/index (§6.9а).

### 12.3 Блокер: контракт `/api/run` целиком

Эндпоинта нет (`backend/app.py` знает только `/api/decide`:454 и
`/api/version`:498); job-реестра нет (единственный образец —
`_ACTIVE_TRIALS` в `trial.py:36`, in-memory, один прогон на сессию).
Требуемый контракт:

- **Жизненный цикл job**: `POST /api/run` (config pack или его hash +
  mode + threads? + Idempotency-Key) → `run_id`; загрузка материалов;
  старт; события; финальный результат; ретеншен результатов (TTL) для
  reattach.
- **Загрузка payload — выбрано: чанковый upload-then-run.** `POST
  /api/run/{id}/files` принимает чанки (ориентир: ≤50 материалов или ≤16
  МБ на чанк, пороги — из capabilities), затем `POST /api/run/{id}/start`.
  Запись чанка — `{path, input, images[], material, content_sha256,
  material_hash}`: группировку и ожидаемые хэши вычисляет **клиент** (§3.5),
  а `/start` независимо пересчитывает raw/composite/material hashes,
  effective config и `materials_fingerprint`/`run_fingerprint`. В file-события
  и результат попадают проверенные значения (§4.1), не слепое эхо клиента.
  Отвергнутые альтернативы: (а) один POST со всеми материалами — тело в
  сотни МБ (500 файлов × 200 КБ ≈ 100 МБ), нет гранулярности ретраев и
  backpressure, частичный приём невозможен; (б) полноценное файловое
  хранилище с upload-сессиями — избыточно для вычислительного
  stateless-конвейера. Чанки дают: ретрай на гранулярности чанка,
  серверный контроль очереди (429 + `Retry-After`), потоковую отправку
  100k-входа без сборки тела в памяти.
- **События**: SSE (`StreamingResponse`-инфраструктура есть,
  `router.py:218`, но trial-стрим привязан к session_id чата — нужен
  отдельный эндпоинт). События `run_start/file/run_end` (+`run_cancelled`),
  каждое с монотонным `seq` — задел под `?after=<seq>` для reattach (v1.1).
- **Отмена**: `POST /api/run/{id}/cancel` → статусы
  `cancel_requested → cancelled | completed_partial`; гашение
  asyncio-таск уже частично существует (`trial.py:391-395`); прерывание
  генерации sglang по дисконнекту — верифицировать; облачные API не
  отменяются (токены сожжены) — best-effort зафиксирован в §6.2.
- **Лимиты и таймаут job**: `max_files_per_job`, `max_concurrent_jobs`,
  серверный дедлайн job (сегодня 500 файлов × `REQUEST_TIMEOUT=600с`
  worst-case — 83 часа бессмертного job'а; `TRIAL_TIMEOUT_S=300` —
  антиспам ассистента, не лимит пакетов).
- **Дедуп по Idempotency-Key** при создании job — сервер хранит ключи в
  пределах ретеншена.

### 12.4 Capabilities-эндпоинт

`GET /api/run/capabilities` (или расширение `/api/version`): лимиты входа
(8 изображений, 20 МБ — сегодня зашиты в `backend/schemas.py:11-12`, у
фронта вообще `MAX_FILE_IMAGES=3` — клиент обязан получать их от сервера,
а не дублировать константы), `default_threads`/`max_threads`,
поддерживаемые режимы, диапазон схем (`min_schema`/`max_schema`), лимиты
job'ов, флаг `auth_required`, список доступных моделей (валидация
`--models`, `dqa doctor`). `dqa doctor` и `dqa validate` читают его;
клиент без capabilities работает по консервативным дефолтам с warning.

### 12.5 Задел под изоляцию v1.3 (мультитенантность)

Сервер сегодня однопользовательский: глобальный `mm.REGISTRY`, нет auth,
нет per-user квот; два прогона с `--threads 8` на одном GPU устроят
взаимный DoS. CLI-контракт обязан **уже сейчас** включить: `run_id`
сквозной (есть), токен в клиенте (есть, впрок, §8.2), обработку 401/403
(exit 77), поле владельца в job (серверная данность будущего). Тогда
изоляция v1.3 не сломает CLI задним числом.

### 12.6 Прочие серверные требования

ETA-калибровка для `validate` (агрегат `metrics.duration_s` из
`backend/app.py:437` по моделям; до его появления `validate` честно
отдаёт `estimate: null`); gzip-транспорт для base64-картинок (+33%
объёма: 20 МБ лимит ≈ 27 МБ на материал — приемлемо co-located, для
удалённого сервера нужен gzip и предупреждение в validate); реестр
пакетов и `--doc <id>` — позже, блок `config` в схеме результата устроен
так, чтобы добавить `doc_id` без смены мажорной версии.

## 13. Отвергнутые альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| Автономный режим (модели внутри CLI) | Данность: креды и модели на сервере; дубль движка = два контракта правил и рассинхрон решений между вебом и конвейером |
| Отдельные команды `dqa decide` / `dqa batch` | Режим определяется входом; две команды — двойной help, двойные тесты, переключение команды при росте объёма |
| Интерактивный визард по умолчанию | Зависший prompt в CI — классическая авария; удобство человека — явные `config init` / `doctor` |
| Shape-shifting JSON (объект для 1 файла, массив для N) | Скрипт «проверил один файл → поставил в пайплайн» ломается ровно на смене формы; всегда конверт с `files[]` (§4.1) |
| TTY-auto-формат (table в терминале, jsonl в пайпе) как дефолт | Два визуальных контракта; машина первична. Конвенция gh/docker признана, но table принят опциональным явным форматом (§4.4) |
| NDJSON из «голых» записей файлов | Без `run_start`/`run_end` обрыв потока неотличим от конца, `run_id` неоткуда взять (§4.2) |
| `--tee` (дублирующий вывод) | Мутная семантика при csv-основном-потоке; `--report` решает задачу честнее (полный артефакт независимо от stdout) |
| Exit-код = исход решения | Исходы — произвольные id из пакета, N исходов на N материалов; семантика «ошибка процесса» смешивается с «политика сработала». Вместо этого `--fail-on` → exit 10 |
| Exit 75 (EX_TEMPFAIL) для Ctrl-C | 75 означает «ретрай уместен» — ложный сигнал для ручной отмены; 130 (`128+SIGINT`) распознают CI и shell-идиомы |
| Хуки `--on-outcome cmd` / `--post-hook` | CLI не планировщик: скрытая точка отказа, shell-injection, смешение exit-семантики; «выход кормит следующий шаг» наблюдаемее. Агенту хук не нужен — он читает JSON |
| Догон упавшего через `comm`/`jq`/process-substitution | Ломается на путях с пробелами/кириллицей, требует jq/sort, на Windows не работает вовсе; `--skip-processed` по content+config hash решает это одной строкой (§6.3) |
| Resume-состояние прогонов в CLI (`~/.dqa/state`) | Клиент без состояния проще и честнее; догон — `--skip-processed`; серверный reattach по run_id — v1.1 (§6.5) |
| Гарантированная «подтверждённая» отмена job | Недостижима без кооперации модельного сервера; облачные API не отменяются. Честные статусы cancel_requested/cancelled (§6.2) |
| Токен флагом `--token` | Виден в ps и журналах CI; только env/файл (§8.2) |
| Эвристическое угадывание кодировки входа | Молчаливое перекодирование — скрытая порча материала; детерминированный `--encoding` (§3.3) |
| Server-side дедуп обработанных | Сервер — stateless-конвейер; состояние идемпотентности — у вызывающей стороны |
| Один POST со всеми материалами / файловое хранилище upload-сессий | См. §12.3: выбран чанковый upload-then-run |
| Точный бюджет токенов до прогона | Невозможен (длина генерации неизвестна); честная оценка с `estimate: true` |
| YAML-конфиг клиента / YAML-вывод | Лишний парсер и диалекты; TOML и json/jq достаточны |
| Конфиг-пакет по умолчанию (`~/.config/dqa/default.pack`) | Скрытый дефолт главного входа делает cron-пайплайны невоспроизводимыми; `--config` обязателен всегда |
| Картинки через stdin; пресет (`files[]`) как вход CLI | Бинарь в пайпе — порча данных; пресеты — формат мастерской, CLI работает с ФС (§3.1) |
| Авто-разбиение входа на несколько job'ов при превышении лимита | Ломает корреляцию «прогон = run_id»; v1 — отказ с подсказкой (§3.4) |
| Несколько пакетов на один вход за один прогон | Промпты разные — двойной расход неизбежен; батчинг пакетов — серверная оптимизация, не клиентская. Рецепт: два прогона + общий манифест с разными fingerprint работает уже сейчас (§6.3) |
| Единый полный `hash` пакета как ключ идемпотентности | Косметическая правка (label/color) жгла бы полный перепрогон; введён семантический `fingerprint` рядом с `hash` (§6.9б, §12.2) |
| `fingerprint` только от правил, без вопросов и моделей | Правка текста вопроса или смена модели меняет ответы при тех же правилах — манифест не инвалидировался бы, потребитель ехал бы на протухших решениях (§6.9б) |
| Ветвление потребителей по `label` или индексу исхода | label — человеческое имя, переименовывается свободно; индекс ломается перестановкой. Контракт — только `outcome.id`, неизменяемый по построению (§6.9а) |
| Мутирующие действия потребителя по NDJSON-стриму в реальном времени | Стрим не гарантирует полноты (обрыв/отмена) и однократности потребления — двойные проставления статусов; действия только по финальному отчёту (§6.8) |
| Отдельный флаг отключения конвенции группировки (`--group none`) | Третий способ сделать то же, что делает `--manifest`; два механизма группировки достаточно: конвенция по умолчанию + явный манифест (§3.5) |
| `--config -`, явный `-` для stdin, `--no-dedup`, мульти-файловый `--skip-processed`, ручной `--report-format` | Вторые способы без потребителя: пакет — файлом из веба; stdin — неявный/`--stdin`; дедуп прозрачен; ротация манифеста — §14; NDJSON-отчёт — автоматически по порогу §3.4 |
| Модели строго только из пакета | Пересмотрено по требованию владельца: «тот же пакет на другой модели» — реальный сценарий отладки/A/B; ограждения — видимость подмены в отчёте и разделение ключей эффективным fingerprint (§2.1, §12.2) |
| `--models-file`, матрица прогонов по наборам моделей | Один флаг = один набор на прогон; A/B — два прогона + `dqa diff` (§11 №11) |
| Эвристическая авто-группировка «похожих имён» (префикс/расстояние) | Молчаливые промахи = фото чужой претензии в материале; детерминированные конвенции + предпросмотр в validate + ошибка при неоднозначности (§3.5) |
| Два разделителя конвенции basename (`_` и `-`) | Удваивает класс неоднозначностей (`claim-557_p1.jpg`) ради удобства именования; один разделитель `_` детерминирован, ИС может переименовать на выгрузке (§3.5) |
| Правило «наиболее длинная база побеждает» при неоднозначности группы | Молчаливое гадание там, где цена ошибки — чужое фото в материале; неоднозначность = exit 65 с подсказкой (§3.5) |
| Картинка-«сирота» (не подошла ни к одному тексту) = ошибка | Легальный смешанный пакет: пресет `batch_photo_moderation.json` — сплошь картинки-материалы; «сирота» — предупреждение validate, не ошибка (§3.5) |
| Дедуп одинаковых изображений между разными материалами | Материалы разные — оба должны ехать на модель; дедуп работает на уровне материала (§3.3), оптимизация байт-передачи — серверное дело (§3.5) |
