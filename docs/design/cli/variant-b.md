# Decision-QA CLI — концепция, вариант B (оптика «машина в пайплайне»)

> Статус: дизайн-документ, код не трогаем.
> Оптика: CLI — конвейерный шаг, вызываемый из CI, cron, shell-скриптов и
> AI-агентов. Человек за терминалом — вторичный сценарий.
> Данности (не перепроектируем): CLI = тонкий HTTP-клиент поверх сервера
> Decision-QA (`POST /api/run`: job + события прогресса, отмена, частичные
> результаты; режимы `decisions`/`fast_batch`/`both`; многопоточность —
> на сервере). Конфиг — версионируемый JSON-пакет (вопросы + правила +
> настройки + `version` + `hash`), экспорт из веба. Креды — только на
> сервере, автономного режима нет.

Ключевые решения одним абзацем: бинарник `dqa`; stdout — только данные
(JSON/NDJSON/CSV), stderr — только прогресс и диагностика; JSON-схема
результата — версионируемый стабильный контракт (`"schema": 1`); решения
по материалам маппятся в exit-коды через `--fail-on`; Ctrl-C шлёт отмену
job на сервер, чтобы не жечь GPU/токены на сироте-прогоне.

---

## 1. Командная модель

### 1.1 Субкоманды

```
dqa run      [входы...]   прогнать материалы и вынести решения (основная)
dqa validate [входы...]   проверить конфиг и вход ДО прогона (dry-run)
dqa config   init|show|set …   клиентская конфигурация (сервер, токен, профили)
dqa version             версия CLI + схемы + проверка совместимости с сервером
```

Никакой магии по умолчанию: `dqa` без аргументов → usage в stderr и exit 64.

### 1.2 Флаги `dqa run`

| Флаг | Дефолт | Смысл |
|---|---|---|
| Флаг | Дефолт | Смысл |
|---|---|---|
| `--config pack.json` | **обязателен** | конфиг-пакет из веба (вопросы+правила+hash) |
| `--mode decisions\|fast_batch\|both` | `decisions` | режим прогона (как в `/api/run`) |
| `--threads N` | `4` | желаемый параллелизм на сервере (§5) |
| `--output, -o FILE` | `-` (stdout) | файл результата; `-` = stdout |
| `--format json\|ndjson\|csv` | `json` | формат вывода (§3) |
| `--fields a,b,c` | все | проекция полей per-file (§3.4) |
| `--manifest FILE` / `--stdin` + `--name` | — | список входов / один текст из stdin (§2.1) |
| `--fail-on LIST` | `error` | исходы, дающие ненулевой exit (§4.2) |
| `--report PATH` | — | полный JSON-отчёт на диск независимо от stdout (§4.3) |
| `--timeout SEC` / `--retry N` | `0` / `2` | дедлайн клиента / ретраи транспорта (§6.1) |
| `--quiet` / `--verbose` | off | уровень stderr (§6.2) |
| `--profile NAME` | конфиг/env | профиль сервера (§7) |
| `--skip-processed FILE` / `--no-dedup` | — | идемпотентность между прогонами / дедуп внутри (§4.5, §2.3) |
| `--dry-run` | off | синоним `dqa validate` |

### 1.3 Неинтерактивность по умолчанию — обоснование

CLI **всегда неинтерактивен**: ни одна команда не задаёт вопросов, ввод
ждёт только явный `--stdin`. (1) Первичный пользователь — скрипт и агент;
неявный prompt в CI превращается в зависший job — классическая авария
конвейеров. (2) Удобство человека решается явно вызванной
`dqa config init`, а не неявным поведением `run`. (3) Недостающий
обязательный параметр → exit 64 с именем недостающего флага — агент
парсит сообщение и исправляет вызов.

### 1.4 Политика совместимости CLI-контракта

Семвер раздельно для трёх контрактов: (а) флаги и exit-коды CLI,
(б) JSON-схема результата (`schema`), (в) минимальная версия сервера.
Внутри мажорной версии поля JSON **только добавляются**; удаление,
переименование или смена семантики exit-кода = новая мажорная `schema`.
Устаревший флаг = deprecation warning в stderr минимум один мажорный
цикл, потом отказ с подсказкой. Перед прогоном клиент сверяется с
сервером через `GET /api/version` (`backend/app.py:498`, расширяется
полем поддерживаемых схем): несовместимость → exit 69 до старта (§8.3).

## 2. Ввод

### 2.1 Источники входа

1. Позиционные аргументы — файлы и/или директории. Директория читается
   нерекурсивно, `-r/--recursive` — рекурсивно. Поддерживаемые типы
   фиксированы: тексты `.txt .md .json` (json = материал-объект, как
   `input: dict|list` в `DecideRequest`, `backend/schemas.py:71`),
   картинки `.png .jpg .jpeg .webp .gif` (сервер принимает data URL;
   лимиты — ≤8 изображений и ≤20 МБ base64 суммарно,
   `backend/schemas.py:11-12`). Картинка = отдельный материал (как
   `files[].image` в пресете `batch_photo_moderation.json`); смешанный
   материал «текст+картинки» — через JSON-манифест (ниже).
2. `--manifest FILE` — точный набор входов от скрипта/агента без
   shell-glob'ов: либо по одному пути на строку (`#` — комментарии),
   либо JSON-массив `{"path": …, "name": …, "images": […]}` (поле
   `images` — до 8 путей картинок, прикрепляемых к текстовому материалу).
3. `--stdin` — один текстовый материал из stdin; имя — `--name`.
   Картинки через stdin **не поддерживаем**: бинарь в пайпе — источник
   порчи данных, картинки только файлами.
4. Пресет-формат (`files[]` с `content`/`image`) в CLI-ввод **не
   принимается**: пресеты — формат веб-мастерской; CLI работает с реальной
   ФС. Конфиг-пакет (`--config`) и вход разделены жёстко.

### 2.2 Валидация ДО прогона — `dqa validate` / `--dry-run`

Локально, без обращений к моделям: конфиг-пакет валиден, `version`
поддерживается, пересчитанный `hash` совпадает с записанным (защита от
правок руками); все пути существуют и читаемы, расширения поддержаны,
лимиты картинок соблюдены; `--fail-on` ссылается на существующие исходы
пакета. В stdout — JSON-сводка: `files_total`, `files_ok`,
`files_skipped` с причинами, оценка `n_files × n_models` инференсов и
ETA из калибровки сервера (§6.5). Exit 0/65 по итогу.

### 2.3 Битые, пустые, дублирующиеся файлы

- **Пустой текст** → `skipped` с `reason: "empty"`: сервер отвергает
  пустой `input` без изображений (`backend/schemas.py:83-89`), клиент
  дублирует проверку, чтобы не жечь прогон.
- **Нечитаемый/битый** (ошибка чтения, невалидный UTF-8, битый base64
  картинки) → `skipped` + `reason`, прогон остальных продолжается.
- **Дубликаты**: дедупликация по sha256 содержимого; повторный файл не
  уходит на модели, в результате — со ссылкой `duplicates_of`.
  `--no-dedup` отключает.
- Файл с ошибкой валидации никогда не роняет весь прогон, если есть
  хотя бы один валидный вход. Ноль валидных входов → exit 65.

## 3. Вывод

### 3.1 JSON-схема результата (стабильный контракт)

```json
{
  "schema": 1,
  "run_id": "run_01JEXAMPLE…",
  "cli_version": "0.9.0",
  "server": {"url": "http://127.0.0.1:8000", "version": "1.4.0"},
  "config": {"path": "pack.json", "version": 3, "hash": "sha256:…"},
  "mode": "decisions",
  "models": ["clef-27b", "qwen3-32b"],
  "started_at": "2026-10-23T10:15:00Z", "finished_at": "…", "duration_s": 222.4,
  "summary": {"files_total": 12, "files_ok": 10, "files_failed": 1,
              "files_skipped": 1,
              "decisions": {"invite": 7, "reserve": 2, "reject": 1}},
  "files": [
    {
      "path": "inbox/resume_01_petrov.txt", "name": "resume_01_petrov.txt",
      "content_sha256": "…", "status": "ok",
      "decision": {"outcome": "invite", "label": "Пригласить",
                   "rule": "q9>=3 && q3.yes>=0.6", "is_default": false},
      "answers": {
        "q9": {"type": "score", "score": 3.71,
               "by_model": {"clef-27b": 3.6, "qwen3-32b": 3.82}},
        "q3": {"type": "yes_no", "answer": "yes", "confidence": 0.96,
               "probabilities": {"yes": 0.96, "no": 0.04},
               "by_model": {"clef-27b": {"yes": 0.93, "no": 0.07}, "…": {}}}
      },
      "usage": {"prompt_tokens": 1840},
      "metrics": {"duration_s": 18.2, "label_mass_min": 0.87},
      "errors": []
    },
    {"path": "inbox/empty.txt", "status": "skipped", "reason": "empty",
     "decision": null, "errors": []},
    {"path": "inbox/huge.png", "status": "error", "decision": null,
     "errors": [{"stage": "server", "model": "clef-27b",
                 "message": "Суммарный объём изображений больше 20 МБ"}]}
  ]
}
```

Принципы схемы:

- `decision.outcome` — **id исхода** из конфиг-пакета (машинный ключ,
  ветвление скриптов только по нему), `label` — человеческое имя,
  `rule` — текст сработавшего правила (для ответа «почему», §10).
- `answers[q]` — агрегат, пошедший в правила решения, плюс разрез
  `by_model`: вероятности/скор каждой модели отдельно. Зеркалит per-model
  `answers` ответа `/api/decide` и фронтовое представление
  (`frontend/static/results.js:41-58`: `yes_no` → `probabilities`,
  `choice` → топ-вариант + распределение, `score` → число).
- Ошибки — **per-file массив**, не единичное поле: файл может упасть на
  части моделей и всё равно получить решение по остальным — тогда
  `status: "ok"`, но `errors` непуст и модель перечислена (частичный
  сбой модели ≠ сбой файла, см. §5).
- `run_id` — сквозной корреляционный ключ с серверным журналом (§10).

### 3.2 CSV

Одна строка на файл: `path,status,outcome,label,confidence,<по колонке
на вопрос — краткий агрегированный ответ>,errors`. Без `by_model`
(для per-model анализа — JSON). Порядок колонок стабилен и следует
порядку вопросов в пакете; новые вопросы добавляются в конец — не ломает
`cut -f1-3` у потребителей.

### 3.3 NDJSON-поток — да

`--format ndjson` (синоним `--stream`): одна строка = одно событие:

```
{"schema":1,"type":"run_start","run_id":"…","files_total":120,"threads_effective":4}
{"type":"file","i":1,"path":"…","status":"ok","decision":{…},"answers":{…}}
{"type":"file","i":2,"path":"…","status":"error","errors":[…]}
{"type":"run_end","summary":{…},"duration_s":…}
```

Обоснование: (1) `/api/run` уже отдаёт события прогресса и частичные
результаты — NDJSON честно их проксирует, CI стримит решения в следующий
шаг, не дожидаясь всей пачки (критично при 10³–10⁴ файлов); (2) это
единственный формат, пригодный и для стрима, и для постфактум-парсинга
(`jq -c`, построчные агрегаторы); (3) отмена/крах посередине не портит
уже выданные строки — каждая самодостаточна, а цельный JSON при обрыве
был бы потерян целиком. Дефолтом остаётся цельный `json` (мелкие прогоны
и человек); рекомендация для конвейеров — `ndjson`.

### 3.4 `--output` и `--fields`

`-o FILE` — запись результата в файл, stdout при этом пуст. Запись
атомарна (временный файл + rename): читающий шаг никогда не видит
полуфайл. `--fields path,decision.outcome,answers.q3.confidence` —
dot-path проекция per-file для json/ndjson (уменьшает payload агенту,
которому нужен только исход); для csv задаёт колонки и их порядок.

## 4. Встраивание действий по решению

### 4.1 Таблица кодов выхода

| Код | Условие | Основание |
|---|---|---|
| 0 | Все файлы ok, нет исходов из `--fail-on` | успех |
| 1 | Есть файлы с исходами из `--fail-on`, ошибок нет | «проверка не пройдена» |
| 2 | Частичный успех: есть `status=error`/`skipped`, но валидация и job прошли | degraded |
| 64 | Ошибка вызова: нет `--config`, неизвестный флаг | EX_USAGE |
| 65 | Валидация входа/конфига не пройдена (0 валидных файлов, битый пакет) | EX_DATAERR |
| 66 | Вход недоступен (пути не существуют) | EX_NOINPUT |
| 69 | Сервер недоступен / несовместимые версии схемы | EX_UNAVAILABLE |
| 70 | Внутренняя ошибка клиента / job упал целиком | EX_SOFTWARE |
| 75 | Таймаут (`--timeout`) или подтверждённая отмена | EX_TEMPFAIL |

Принцип: 0/1/2 — **о данных** (смотрит логика пайплайна), ≥64 — **о
самом запуске** (смотрит on-call). Диапазон `sysexits.h` выбран, чтобы не
пересекаться с 1/2, которые CI-системы трактуют особо.

### 4.2 `--fail-on <исходы>`

Список id исходов из конфиг-пакета: `--fail-on reject` или
`--fail-on reject,reserve`. Спец-значения: `any` (любой не-default
исход), `error` (любой файл со `status=error` — **дефолт**), `none`.
Дефолт `error` делает CLI из коробки честным шагом CI: падение материала
= падение шага, а бизнес-решения (`reject`) шаг не роняют, пока их явно
не попросили. Состав валидируется против исходов пакета до прогона:
опечатка → exit 64, а не тихо пропущенный исход.

### 4.3 `--report <path>`

Полный JSON-отчёт (схема §3.1, без `--fields`-проекции) пишется на диск
даже при `--format csv` в stdout. Типовая схема: stdout кормит следующий
шаг пайпа, `--report` — артефакт для аудита. Атомарная запись, как §3.4.

### 4.4 Хуки/пост-команды — отвергнуто (анти-паттерн)

Произвольные `--on-reject 'cmd …'` / `--post-hook` **не добавляем**:
(1) скрытая точка отказа и shell-injection поверх пайплайна, ошибку хука
не отличить в exit-коде от ошибки прогона; (2) всё, что делает хук,
оркестратор делает лучше — `dqa run … || handle_fail` либо ветвление по
JSON/exit-коду в следующем шаге; контракт «выход кормит следующий шаг»
— unix-way и наблюдаемее; (3) AI-агенту хук не нужен: он читает JSON и
сам вызывает следующий инструмент. Единственное возможное исключение на
будущее — декларативный `--move-to DIR` (раскладка файлов по папкам
исходов, без exec); в v1 не входит.

### 4.5 Идемпотентность

`--skip-processed FILE`: FILE — пополняемый NDJSON-манифест
`{"content_sha256": …, "outcome": …, "run_id": …}`. Файлы, чей sha256 уже
в манифесте, получают `status: "skipped", reason: "already_processed"` и
не уходят на сервер. Ключ — **хэш содержимого, не путь**: переименование
не провоцирует перепрогон, изменение содержимого — провоцирует.
`--no-dedup` действует внутри одного прогона, `--skip-processed` — между
прогонами; манифест можно генерировать и самому из вывода (`jq`), флаг
лишь делает это удобным. Server-side дедупа нет: сервер —
stateless-конвейер, состояние идемпотентности — у вызывающей стороны.

## 5. Многопоточность

`--threads N` (дефолт 4) — **пожелание серверу**, не локальный пул.
Параллелятся материалы внутри job на сервере (server-side threads);
внутри материала модели идут параллельно, как в `/api/decide`
(`asyncio.gather` по `req.models`, `backend/app.py:488`). Семантика:

- клиент передаёт `threads` один раз при создании job; локально ничего не
  параллелит (тонкий клиент) — гонок файлов/памяти на клиенте нет;
- сервер вправе зажать значение своим лимитом (vision-модели, память);
  факт возвращается в `run_start.threads_effective` и stderr-прогрессе;
- **backpressure**: файлы грузятся в job чанками; переполненная очередь
  сервера отвечает 429 + `Retry-After`, клиент ждёт и повторяет чанк
  (это не расходует ретраи из §6.1);
- **частичные сбои моделей**: одна модель из `models[]` упала на файле →
  решение по оставшимся, `errors[]` фиксирует модель и причину (зеркало
  per-model `{ok:false,error}` из `/api/decide`); упали все →
  `status: "error"` файла, остальные продолжаются. Строгость реакции —
  через `--fail-on error` (дефолт) или его ослабление.

## 6. Производственные аспекты

### 6.1 Таймауты и ретраи

Connect-timeout 10 c (фикс.), read — без лимита: job живёт долго,
зависший job ловится `--timeout SEC` (общий дедлайн; истёк → отмена job,
частичные результаты в отчёт, exit 75). `--retry N` (дефолт 2): только
транспортные сбои и 5xx, backoff 1s→2s→4s + jitter. 4xx (422 валидация,
409 модель не запущена) **не ретраятся** — они детерминированы.
Идемпотентность создания job — client-supplied `Idempotency-Key` (uuid
на вызов): повтор после обрыва сети не плодит второй прогон.

### 6.2 Прогресс: stderr против stdout

Жёстко: **stdout — данные, stderr — люди и логи**. В stderr: строка
прогресса `12/120 files, 2 err, eta 4m10s` (через `\r` только на TTY; в
пайп — построчно, пригодно для логов CI), диагностика сервера,
deprecation warnings. `--quiet` гасит всё, кроме фатала; `--verbose`
добавляет события job (старт модели, ретраи) и `run_id`. Поэтому
`dqa run … | jq …` работает без вытеснения прогресса.

### 6.3 Сигналы

SIGINT/SIGTERM: клиент шлёт `POST /api/run/{run_id}/cancel` (отмена —
данность сервера), ждёт подтверждения до 5 c, сохраняет частичные
результаты (если задан `--report` — пишет), exit 75. Второй Ctrl-C —
немедленный выход с `run_id` в stderr для ручной отмены. Подтверждённая
отмена обязательна, а не best-effort: иначе GPU/токены продолжают гореть
на сироте-прогоне.

### 6.4 Лимиты

Клиентские, fail fast до отправки: ≤8 картинок на материал, ≤20 МБ
base64 суммарно (зеркало `backend/schemas.py:11-12`); текст >~200 КБ —
предупреждение (не ошибка) из-за длинного prefill. Серверные лимиты
приходят в capabilities `/api/run` и показываются `dqa validate`.

### 6.5 Оценка стоимости/времени до запуска

`dqa validate` выводит `n_files × n_models` инференсов и ETA: сервер
отдаёт калибровку последних прогонов (средний `duration_s` на файл по
модели — есть в `metrics.duration_s`, `backend/app.py:437`), для
облачных моделей — порядок токенов (`prompt_tokens`). Точный бюджет до
прогона невозможен (длина генерации неизвестна), поэтому рядом с числом
честно стоит `estimate: true`; это sanity-gate «вы точно хотите прогнать
40 000 файлов?», а не биллинг.

## 7. Конфигурация клиента

Иерархия (позже = выше приоритет): **файл < env < флаги**.

- Файл: `~/.config/dqa/config.toml` (macOS/Linux) /
  `%APPDATA%\dqa\config.toml` (Windows). `dqa config init` создаёт,
  `dqa config set profiles.staging.server …` правит, `dqa config show`
  показывает эффективные значения с источником каждого
  (`server = …  # env DQA_SERVER`).
- Env: `DQA_SERVER`, `DQA_TOKEN`, `DQA_PROFILE`, `DQA_CONFIG_DIR`.
- Флаги: `--server`, `--token`, `--profile` на любой команде.
- Профили — несколько серверов в одном файле:
  ```toml
  default_profile = "local"
  [profiles.local]   server = "http://127.0.0.1:8000"
  [profiles.staging] server = "https://dqa.staging.example.com"
  ```
  Агент в CI использует только env (файл не нужен, секреты не седлаются
  в конфиги); человек — профили. Токен здесь — токен доступа к серверу;
  креды моделей остаются на сервере (данность). Токен в файле → chmod
  600, при более широких правах — предупреждение.

## 8. Установка и обновление (Win/Mac)

### 8.1 Форма дистрибуции

Единый бинарник на платформу — `dqa-windows-x64.exe`,
`dqa-macos-arm64` — собирается в том же релизном пайплайне
(`scripts/build_release.sh`, данность: дистрибуция в релизном zip).
Python-зависимостей на машине пользователя нет (упаковка типа
PyInstaller/shiv либо статическая сборка; выбор движка — отдельное
решение, на контракт не влияет).

### 8.2 Зависимости

Ноль внешних рантайм-зависимостей; сеть — только HTTP к серверу.
macOS: документируем снятие quarantine; Windows: нотация про SmartScreen
в README релиза.

### 8.3 Обновление и несовместимость схем

`dqa version` печатает версию CLI, `schema` результата и (при доступном
сервере) версию сервера + поддерживаемый диапазон схем. Перед `run`
клиент сверяет свой `schema` с серверным диапазоном (расширение
`/api/version`): вне диапазона → exit 69 с текстом «обновите CLI до ≥X
/ сервер до ≥Y». Старая CI-джоба падает явно, а не молча парсит новый
JSON. Самообновления нет — непиннутая версия убивает воспроизводимость
конвейера; обновление — осознанный шаг, релиз при смене мажорной
`schema` несёт миграционную заметку.

```markdown
# decision-qa

## Когда применять
Есть конфиг-пакет pack.json (экспорт из веб-интерфейса Decision-QA) и файлы,
по которым нужны решения. НЕ применять, если правила ещё не отлажены —
это делается в веб-мастерской.

## Контракт вызова
dqa run --config pack.json [файлы|директория|--manifest m.txt|--stdin]
        [--format ndjson|json|csv] [-o out.json] [--report r.json]
        [--fail-on outcome1,outcome2|error|none] [--threads N] [--timeout SEC]
Обязательно: --config и хотя бы один источник входа.
Сервер/токен: env DQA_SERVER и DQA_TOKEN.

## Коды выхода — проверяй ПЕРЕД разбором stdout
0 — все ок, нет исходов из --fail-on · 1 — есть такие исходы (данные полные,
разбирай) · 2 — частичный успех (status=error/skipped) · 64/65/66 — ошибка
вызова/валидации/входа (чини аргументы, НЕ ретрай) · 69 — сервер недоступен
или несовместимы версии (ретрай позже/эскалация) · 70/75 — внутренняя ошибка
/ таймаут или отмена (частичные данные в --report).

## stdout
Только данные: JSON-документ или NDJSON (строка = файл). Прогресс и ошибки
— в stderr, оттуда данные НЕ читать. Ключевые поля: .summary.decisions
(счётчики исходов), .files[].decision.outcome (id исхода),
.files[].status (ok|error|skipped), .files[].errors[].message,
.run_id (корреляция с серверным журналом). Поле "schema": 1;
неизвестные поля игнорировать.

## Рецепты
1. Разобрать входящие интервью:
   dqa run --config screening.json inbox/ --format ndjson \
     | jq -rc 'select(.type=="file") | {path, outcome: .decision.outcome}'
2. Список «на разбор»:
   dqa run --config pack.json inbox/ -o r.json --fail-on none
   jq -r '.files[] | select(.decision.outcome=="reserve") | .path' r.json
3. Проверка входа без расхода моделей:
   dqa validate --config pack.json inbox/
4. Один текст из переменной:
   printf '%s' "$text" | dqa run --config pack.json --stdin --name case.txt

## Типичные ошибки агента
- Забыт --config → exit 64. - Нет файлов поддерживаемого типа →
  files_total=0, exit 65. - Парсить stderr как данные — нельзя.
- Не проверить exit-код до jq: при exit ≥64 stdout может быть пуст.
```

## 10. Наблюдаемость конвейера

- **run_id** — серверный id job: печатается в stderr при старте и лежит в
  корне результата. Это корреляционный ключ: серверный журнал
  (`server/logs/app.log`) индексируется по нему.
- **Что логирует клиент**: stderr — события job (старт, чанки, ретраи,
  отмена) с таймстампами; `--verbose` — HTTP-трассы без тел (метод, путь,
  статус, latency). Тела материалов в логи клиента не попадают никогда
  (приватность по умолчанию).
- **«Почему этому материалу такое решение»** отвечается без сервера из
  самого отчёта: per-file `answers` с агрегатом и `by_model`
  вероятностями, `decision.rule` (сработавшее правило), `config.hash`
  (гарантия, что вопросы и правила — именно отлаженные в вебе). Глубокий
  разбор (сырые ответы моделей, `label_mass`, токены) — по `run_id` на
  сервере.
- **Метрики конвейера**: `summary` + per-file `metrics.duration_s` дают
  производительность прямо из отчёта; NDJSON-стрим скармливается
  агрегатору (`jq`/Vector) для дашборда «файлов/час, доля ошибок, ETA».

## 11. Примеры (реальные сценарии)

**1. CI-gate: проверка папки входящих, блок по отклонённым.**
```bash
dqa run --config packs/moderation.json incoming/ \
  --fail-on reject --report artifacts/moderation.json
# exit 1 → джоба красная; отчёт — артефакт сборки
```

**2. Ночной cron с отчётом, ретраями и идемпотентностью.**
```bash
dqa run --config packs/returns.json /data/claims/ --recursive \
  --threads 8 --timeout 7200 --retry 4 --fail-on none \
  -o /reports/claims-$(date +%F).json \
  --skip-processed /data/.dqa-processed.ndjson
```

**3. Агентский скилл «разбери входящие интервью»: стрим, реакция по мере
готовности файлов.**
```bash
dqa run --config packs/interviews.json --manifest new.txt --format ndjson |
while read -r line; do
  [ "$(jq -r '.decision.outcome // empty' <<<"$line")" = reject ] &&
    mv "$(jq -r .path <<<"$line")" rejected/
done
```

**4. Интеграция с последующим софтом через exit-код + JSON.**
```bash
if dqa run --config pack.json batch/ -o r.json --fail-on reject,error; then
  python publish.py --decisions r.json
else
  code=$?
  [ $code -eq 1 ] && python triage.py --decisions r.json || alert "dqa: exit $code"
fi
```

**5. Один материал из stdin внутри агента (без файлов).**
```bash
cat transcript.txt | dqa run --config packs/interviews.json \
  --stdin --name candidate_557.txt | jq -r '.files[0].decision.outcome'
```

**6. Оценка стоимости перед большим прогоном.**
```bash
dqa validate --config packs/photos.json photos_40k/ --format json |
  jq '{files_ok, est_requests, estimate_s}'
```

**7. Инкрементальная обработка потока файлов.**
```bash
dqa run --config pack.json new/ --skip-processed seen.ndjson \
  --format csv -o daily.csv --fail-on none
```

## 12. Отвергнутые альтернативы и почему

| Альтернатива | Почему отвергнута |
|---|---|
| Автономный режим (модели внутри CLI) | Данность: креды и модели на сервере; дубль движка = два контракта правил и рассинхрон решений между вебом и конвейером |
| Интерактивный визард по умолчанию | Зависший prompt в CI — классическая авария; удобство человека — явная `dqa config init` (§1.3) |
| Хуки/пост-команды (`--on-reject cmd`) | Скрытая точка отказа, shell-injection, смешение exit-семантики; unix-way «выход кормит следующий шаг» наблюдаемее (§4.4) |
| YAML-конфиг клиента | Лишний парсер и диалекты YAML в single-binary; TOML проще и детерминированнее |
| Локальный пул потоков в клиенте (N HTTP-прогонов) | Данность: многопоточность на сервере; клиентский параллелизм плодит N job'ов, ломает отмену, частичные результаты и run_id-корреляцию |
| «Человеческий» текстовый вывод как дефолт | Машина — первичный пользователь; pretty = `jq`; второй контракт вывода не поддерживаем |
| Единый exit 1 на всё | CI не отличит «данные отклонены» от «клиент сломан»; разнесение 0/1/2 vs ≥64 — обязательная семантика (§4.1) |
| Самообновление бинарника | Непиннутая версия убивает воспроизводимость; обновление — осознанный шаг с миграционной заметкой (§8.3) |
| Server-side дедуп обработанных | Сервер — stateless-конвейер; состояние идемпотентности — у вызывающей стороны (`--skip-processed`, §4.5) |
| Точный бюджет токенов до прогона | Невозможен (длина генерации неизвестна); вместо него честная оценка из калибровки сервера с `estimate: true` (§6.5) |
| NDJSON как единственный формат | Цельный JSON нужен мелким прогонам и `--report`; NDJSON — стриму. Два формата, одна `schema` (§3.3) |
| Картинки через stdin | Бинарь в пайпе — источник порчи данных; картинки только файлами (§2.1) |
| Пресет (`files[]`) как вход CLI | Пресеты — формат веб-мастерской; CLI работает с реальной ФС, конфиг и вход разделены (§2.1) |

## 13. Открытые вопросы

- Точная форма событий `/api/run` (SSE vs polling): CLI-контракт от неё
  изолирован, но §6.2 (прогресс) и §6.3 (отмена) требуют финализации
  серверного протокола до реализации клиента. В текущем коде эндпоинта
  `/api/run` ещё нет — есть только `/api/decide` (`backend/app.py:454`).
- `--doc <id>` из реестра конфигов — зафиксировано как «позже»; блок
  `config` в схеме результата устроен так, чтобы добавить `doc_id` без
  смены мажорной версии.
- Состав `by_model` для режима `fast_batch` (его метрики отличаются —
  `MODE_LABELS`, `frontend/static/results.js:10`): уточнить, что
  агрегирует сервер, прежде чем фиксировать поля в `schema: 1`.
- Формат калибровки ETA (`dqa validate`, §6.5): нужен серверный
  эндпоинт статистики прогонов либо честная деградация до
  «оценки нет».
