# Исследование best practices для фичи «разметка результатов» — рабочий материал

Собрано тремя исследовательскими агентами по официальной документации продуктов
(октябрь 2026). Пометки в отчётах: [подтверждено] — прямой источник,
[интерпретация] — вывод/перенос на наш случай. Это внутренний рабочий материал
для концепт-документа `docs/review-marks-concept.md`, не часть публичной доки.

---

## Отчёт 1. Label Studio и Prodigy — UX-паттерны ревью и разметки

### 1.1 Label Studio (Enterprise): статусная модель ревью

**Машина состояний задачи.** Ядро — два состояния: `Needs Review` → `Done`.
Переход настраивается: «Task is reviewed after at least one accepted annotation»
или «...after all annotations are reviewed». Состояние `Done` влияет сразу на
четыре вещи: задача исчезает из review stream, меняется значение колонки
**Reviewed** в Data Manager, попадает в экспортный снапшот «только ревьюнутые»
и считается в дашбордах. [подтверждено]

**Действия ревьюера — три, а не два.** В review stream (отдельный режим по
кнопке «Review All Tasks») на аннотации доступны кнопки **Accept**,
**Fix & Accept** (поправить и принять — «исправил мелочь сам, не гоняя
туда-сюда») и **Reject**. Reject — меню с опциями: *No Rework* (дефолт),
*Return to Annotator*, *Pass to Another Annotator*; исходная аннотация и факт
отклонения остаются в Data Manager и дашбордах. Есть настройка «Reviewers must
leave a comment on reject». [подтверждено]

**Порядок и выборка ревью.** Review stream упорядочивается по ID или случайно;
Data Manager сортируется по аннотатору, agreement или confidence score модели
(ревьюить «самые неуверенные» первыми). **Review Sampling**: Basic (процент
задач) и Agreement-based (низкосогласованные — почти все). Опция «Show only
finished tasks». [подтверждено]

**Комментарии.** Панель Comments у аннотации; комментарий прилинковывается к
региону/полю («pointed feedback»). Состояния resolved/unresolved. В Data
Manager — колонки: Comment texts, Comments (счётчик), Unresolved comments,
Commented at, Commented authors. [подтверждено]

**Плотный список (Data Manager).** Таблица с настраиваемыми колонками,
фильтрами (конъюнкция условий), табами-видами. Ревью-информация — колонки
Reviewed, Reviewers, счётчик аннотаций; фильтры по review outcome, ревьюеру,
автору комментария. Клик по задаче — preview с вкладками аннотаций и сеткой
side-by-side. Ground truth — жёлтая звезда у ID аннотации. Часть колонок
скрывается по роли. [подтверждено]

**Прогресс и метрики.** Дашборд Reviews: всего ревью, время, соотношение
accepted / fixed+accepted / rejected. Acceptance score =
(accepted + fix&accepted) / reviewed по последнему вердикту. [подтверждено]

### 1.2 Prodigy: быстрый бинарный триаж

**Философия.** «One task at a time», каждая разметка — «simple and intuitive
decision»: одна карточка, решение одним нажатием. [подтверждено]

**Три исхода и клавиши.** Ответ пишется как `"answer": "accept"|"reject"|"ignore"`.
Хоткеи: `a` accept, `x` reject, `space` ignore, `backspace/del` undo,
`cmd/ctrl+s` сохранить, `f` flag (закладка «разобрать позже», независима от
вердикта), `h` инструкции, `0–9` выбор опции. Клавиши переназначаемы. На
тачах — свайпы. Цвета: accept зелёный #4fd364, reject красный #f74c4a, ignore
серый #b9b9b9. [подтверждено]

**Почему быстро** [интерпретация]: (а) решение = одна клавиша без мыши;
(б) авто-продвижение к следующей карточке; (в) ответы уходят на сервер
батчами в фоне — нет блокирующего «сохранить»; (г) история 10 последних
решений в сайдбаре с мгновенным откатом — undo дёшев; (д) сайдбар с
виджетом прогресса и счётчиками.

**Review recipe.** Группирует аннотации разных сессий по `_input_hash`,
восстанавливает исходный пример, даёт выбрать правильную версию; флаг
`--auto-accept` принимает примеры, где все согласны, — человек смотрит
только расхождения. [подтверждено]

### 1.3 Паттерны для плотной таблицы (из отчёта 1)

- Статус — мини-метка в ячейке, действие — по hover/клавише (не плодим три
  кнопки в каждой ячейке).
- Счётчики-колонки вместо контента (Comments: 3, Unresolved: 1), текст — по
  клику в панель.
- Фильтры первого класса: по вердикту, комментариям, неуверенности,
  расхождениям.
- Вкладки/сетка для сравнения версий.
- Сортировка по неопределённости (confidence/agreement).
- Прилинкованные комментарии — к ячейке, не «ко всей задаче».
- Цветовая семантика действий: зелёный/красный/серый.

### 1.4 Модели данных (отчёт 1)

Prodigy: плоский JSON `{answer, flagged?, _task_hash, _input_hash}`, экспорт
JSONL, `--flagged-only`. Label Studio: вердикт — отдельная сущность review
(accepted/rejected + сценарий reject), привязана к аннотации; считается
последний вердикт; экспорт-снапшоты «только ревьюнутые»; ground truth — флаг
на аннотации; комментарии с resolved-статусом и ссылкой на регион/поле.

Вывод: минимальная запись — `{run_id, question_id, model, verdict,
comment?, ts, updated_ts}`; JSONL/CSV-экспорт + опция «только размеченные».

### 1.5 Что заимствовать (отчёт 1)

1. Три состояния ✓/✗/? с однобуквенными хоткеями + дешёвый undo (история
   последних N решений).
2. «Fix & Accept» одним шагом.
3. Обязательный комментарий при ✗ (опция LS).
4. Фильтры по вердикту/комментариям/неуверенности + счётчики-колонки.
5. Плоский JSONL-экспорт с явным полем вердикта.
6. Флаг-закладка «разобрать позже», независимый от вердикта.
7. Прогресс-виджет разметки (X из Y, доля ✓/✗/?).

Избыточно: роли и очереди LS Enterprise, review sampling, версии/сессии
Prodigy, привязка комментариев к регионам контента (достаточно ячейки).

## Отчёт 2. Argilla, Doccano, Labelbox — роли, статусы, IAA, экспорт

### 2.1 Argilla (v2.x)

**Роли:** owner / admin / annotator; метаданные записи могут быть скрыты от
аннотаторов. [подтверждено]

**Двухуровневая статусная модель** [подтверждено]:
- Ответ (response, per-user per-record): missing / draft / submitted /
  discarded. Очереди Pending/Draft/Submitted/Discarded; обратно в Pending
  запись не возвращается никогда («прогресс не откатывается»).
- Запись (record): pending → completed при наборе минимального числа
  submitted-ответов (дефолт 1). Webhook на record.completed.

**UI:** Focus view (одна запись, после Submit — автоматически следующая;
рекомендован против смещений) и Bulk view (список 10/25/50/100, collapse/
expand строк фиксированной высоты, bulk-разметка + фильтры). **Suggestions** —
предсказания модели иконкой ✨ в кнопке лейбла, предзаполненный ответ со
score; согласие = один клик Submit. Прогресс-панель с личными счётчиками.

**Хоткеи** [подтверждено]: Enter — Submit, Backspace — Discard, Cmd/Ctrl+S —
draft, 1/2/3 — выбор лейбла, ↑/↓ — между вопросами, ←/→ — между записями,
Tab — активация формы, Esc — выход из textarea.

### 2.2 Doccano

Роли: project administrator / annotator / annotation approver (approver
подтверждает примеры — состояние checked). Collaborative annotation —
аннотаторы видят чужие метки и подтверждают. Хоткеи: у каждого лейбла
односимвольный suffix key. Статусной модели записей нет — только флаг
«подтверждён». [подтверждено]

### 2.3 Labelbox

Роли: Owner/Admin/Member + проектные LABELER/REVIEWER/TEAM_MANAGER/ADMIN.
Workflow — node-based конвейер: Initial labeling → Initial review → Rework →
Done. Статусы data row: TO_LABEL/IN_REVIEW/IN_REWORK/DONE, меняются только
автоматически. Reject → автоматом в Rework (опционально переназначение
автору). Массовое «Move to task» до 10 000 строк. **Audit log** на строку +
`workflow_history` в экспорте (Move/Accept/Reject/Rework с автором и
таймстампом). Фильтры маршрутизации: labeled by, annotation, sample
probability, consensus average, issue category, время разметки/ревью.
[подтверждено]

**Benchmarks** — «золотые» строки с эталоном, подмешиваются в очередь;
accuracy разметчика против эталона. **Consensus**: % coverage + # labels
(дефолт 2); скор 0–1 в реальном времени; «победитель» выбирается ревьюером
кликом по трофею (selected_label_id в экспорте); фильтр «Consensus
agreement». [подтверждено]

Хоткеи: E — Submit/Save, Q — Skip, Backspace — Delete, Esc — Deselect,
Tab/Shift+Tab — навигация, 1/2/3 — инструменты. [подтверждено]

### 2.4 Паттерны для плотной таблицы (из отчёта 2)

- Очереди-вкладки по статусу со счётчиками; инвариант «в Pending не вернуть».
- Auto-advance: Submit → следующая неразмеченная ячейка.
- Suggestion-as-prefill: вердикты одной клавишей/кликом, без диалогов.
- Focus/Bulk режимы.
- Одноклавишные вердикты с мнемоникой (1=✓ 2=✗ 3=?).
- Подсветка расхождений (consensus) + фильтр «расходятся»; trophy-выбор
  победителя = «отметить лучший ответ модели».
- Всегда доступные гайдлайны (раскрываемая панель рядом с таблицей).
- Audit-лог по клику — история смен вердикта во всплывашке.

### 2.5 Модели данных и экспорта (отчёт 2)

Argilla: запись = fields + responses[] (per-user: status, values, user_id,
таймстампы) + suggestions[] (value, score, agent) + metadata + vectors.
Экспорт to_disk/from_disk — настройки датасета + записи одним бандлом,
восстанавливаемым на другом инстансе. Doccano: JSONL {doc_id, text, labels,
username} — автор вшит в строку; размеченный JSONL реимпортируется. Labelbox:
NDJSON data-row-centric (одна строка = одна запись со всей историей);
labels[] с created_by/created_at/updated_at, reviews[], performance_details,
workflow_status + workflow_history[], selected_label_id; предсказания моделей
лежат отдельно от ground-truth; version: "1.0.0" — версионирование формата.

Общий знаменатель: (1) вердикт и lifecycle-статус — разные поля; (2) автор и
таймстампы на каждой аннотации; (3) предсказания модели рядом, но отдельно от
человеческой разметки; (4) экспорт — JSONL/NDJSON, реимпортируемый, с версией
схемы; (5) переносимость = «схема задачи + записи + разметка» одним бандлом.

### 2.6 Что заимствовать (отчёт 2)

- Статусная модель Argilla в миниатюре: ячейка = {verdict, comment, status:
  draft/submitted/discarded, author, created_at, updated_at} + производный
  статус строки pending/completed.
- Auto-advance, вкладки-очереди со счётчиками, Focus/Bulk, одноклавишные
  вердикты, фильтры по статусу/модели/вероятности, сортировка по score.
- Ответы моделей как suggestions (отдельная сущность), разметка поверх,
  ничего не затирая.
- Экспорт JSONL с version/автором/таймстампами + реимпорт того же файла;
  бандл «правила + прогон + разметка» (Argilla to_disk).
- Лёгкий audit-trail: append-only история смен вердикта.
- Consensus-lite: подсветка расхождений + фильтр «расходятся» (boolean).

Избыточно сейчас (но не блокировать): роли/права (достаточно поля author со
значением "local"), workflow-граф, benchmark-скоринг, встроенные IAA-метрики
(ни у Argilla, ни у doccano их в UI нет — считаются внешне на экспорте),
мультиформатный экспорт и push в HF Hub.

## Отчёт 3. LangSmith, Humanloop, Weave, Phoenix — ревью выводов моделей

(W&B куплена CoreWeave 2025, доки Weave на docs.coreweave.com; Humanloop
закрыта 8 сентября 2025, документация доступна.)

### 3.1 LangSmith — annotation queues

- Два стиля очередей: single-run (один элемент за раз) и pairwise PAQ (два
  прогона side-by-side, выбор «A лучше / B лучше / Равны»; PAQ записывает
  бинарный фидбек на оба прогона — одно действие размечает две ячейки).
- Статусы элемента: Needs Review → Needs Others' Review → Completed.
  Левая панель — список со статусами, центр — input/output, правая —
  инструкции и рубрика.
- Рубрика = feedback keys: continuous (min/max, float) и categorical
  (label + числовой score; пишется в value и score).
- Хоткеи [подтверждено]: PAQ — A/B/E, Enter на последнем пункте = Done и
  переход к следующему.
- Наполнение очереди: вручную (до 100), чекбоксами из таблицы runs,
  automation rules (по фильтру — ошибки, низкий скор).
- Возврат в цикл: Add to Dataset (можно отредактировать output → эталон);
  экспорт датасета в CSV / JSONL / OpenAI fine-tuning формат. Align
  Evaluator: человеческие правки из очереди → few-shot примеры LLM-судьи.
- Сравнение экспериментов: виды Compact/Full/Diff; регрессии красным,
  улучшения зелёным относительно baseline; кнопки регрессий/улучшений в
  шапке колонки фидбека = фильтр «только ухудшившиеся». Фильтры по
  input/output, status, latency, metadata, tag, feedback.

### 3.2 Arize Phoenix — span/trace annotations

- Три типа аннотаций: categorical (👍/👎), continuous (0–100), freeform.
  У конфига — направление оптимизации Maximize/Minimize/None.
- Каждая аннотация = label + score + explanation. Встроенный конфиг
  user_feedback: positive (1.0) / negative (0.0).
- Хоткеи — часть конфигурации рубрики (цифры категориям, стрелки скорам);
  цель названа явно: «rapid annotation».
- Annotator kind: Human / LLM / Code; источник API/APP. Вкладка Annotations
  показывает автора и kind — «видно, где аннотаторы расходятся». Уровни:
  span, trace, session. REST API batch до 1000, upsert по имени конфига.
- Error analysis workflow [подтверждён цитатой]: фильтруешь трейсы по
  значениям аннотаций («llm spans that are incorrect») → экспортируешь
  выборку в датасет → датасет для экспериментов/fine-tuning/human-aligned
  eval. Аннотации пропагируются в metadata примеров датасета; оценщики при
  прогоне видят эту metadata → регрессии относительно прошлой разметки и
  человечески-калиброванные LLM-судьи.

### 3.3 W&B Weave — feedback + human annotation scorers

- Три формы фидбека: эмодзи-реакции (👍/👎/+любой), заметки (макс 1024
  символа, Enter сохраняет), произвольный структурированный объект.
  Фидбек-объект: id, created_at, feedback_type, payload.
- Human Annotation scorer — именованный версионируемый объект (boolean,
  integer, enum); панель Annotate на странице трейса; колонка Annotations в
  таблице Traces.
- Compare evaluations: ≥2 оценки → Compare; baseline переназначаем,
  порядок drag&drop; радарная диаграмма + per-metric графики; цветной бейдж
  разницы с baseline с учётом направления метрики; тумблер Diff only;
  инлайн-предупреждения о несогласованности датасета/скореров. Dataset
  results: строка = пример, колонки = вывод каждой оценки; клик — side-by-side
  detail; для двух оценок — scatter-плоты, выделение региона (brush)
  фильтрует таблицу.

### 3.4 Humanloop — human evaluators

- Batch-генерация по датасету → таблица заполняется выводами → фидбек
  ставится прямо в колонке rating таблицы или в drawer → Mark as complete →
  агрегаты в Stats. Дефолтный evaluator «rating» с лейблами good/bad
  подключён ко всем новым промптам.
- Review-таб с Focus mode и фильтрами; датасет делится на чанки;
  отфильтрованный вид шарится URL'ом; виден прогресс и число оставшихся
  суждений; последнее суждение помечает evaluation complete.
- Из drawer лога кнопка «Editor →» загружает лог в редактор промпта.

### 3.5 Паттерны для плотной таблицы (из отчёта 3)

- Быстрый вердикт в ячейке без открытия детали (Humanloop — прямо в колонке
  таблицы; деталь — drawer по клику).
- Клавиатурная скорость как first-class: хоткеи на вердикты + авто-переход к
  следующей неразмеченной ячейке.
- Фильтр «только ошибки» = фильтр по значению разметки (Phoenix) +
  кнопки-фильтры регрессий в шапке колонки (LangSmith); scatter-brush (Weave)
  = выделил расходящиеся → таблица отфильтрована.
- Baseline + цветной дифф (красный/зелёный относительно базового прогона) —
  для проверки, что новая версия правил не ломает размеченное.
- Diff only — скрыть одинаковые строки/колонки.
- Разметка на уровне ячейки, а не строки (PAQ пишет фидбек на оба прогона
  раздельно; Phoenix различает span/trace/session).
- Скрытие чужих оценок до сдачи своей (LangSmith) — для независимости
  разметчиков (опционально).

### 3.6 Модели данных (отчёт 3)

- Унифицированная тройка у всех четырёх: label (категория) + score (число) +
  explanation/comment (текст). LangSmith: categorical хранит label в value и
  число в score; Phoenix: label/score/explanation; Weave: feedback_type +
  payload.
- Именованная рубрика (feedback key / config name / scorer name) — разметка
  привязана к именованному критерию → несколько осей без смены модели
  (напр. «корректность», «источник ошибки»). Phoenix: upsert по имени конфига.
- Атрибуты автора/источника: Phoenix annotator kind Human/LLM/Code — задел
  под разметку AI-ассистентом.
- Экспорт: де-факто стандарт CSV/JSONL + формат OpenAI fine-tuning.

### 3.7 Что заимствовать (отчёт 3)

1. Трёхзначная категориальная рубрика с числовым скором (✓=1, ✗=0, ?=null) +
   отдельное поле комментария (модель Phoenix/LangSmith).
2. Хоткеи на вердикты и авто-продвижение.
3. Фильтр по значению разметки («только ✗») как основа error-analysis;
   экспорт отфильтрованного в именованный набор = корпус ошибок /
   регрессионный набор (паттерн «filter → export to dataset»).
4. Именованные ключи разметки — задел под вторую ось («тип ошибки: FP/FN»)
   без смены модели данных.
5. Baseline-дифф между прогонами.
6. Поле annotator/source сразу — задел под разметку AI-ассистентом
   (зеркалит Phoenix Human/LLM/Code и LangSmith Align Evaluator).

Избыточно: очереди с резервациями/кворумом, pairwise как отдельный режим
(наша таблица уже side-by-side), thread/session-уровни, эмодзи-реакции,
версионирование scorer-объектов, автоправила маршрутизации, серверный
multi-tenancy, LLM-as-judge калибровка (этап 2).

## Сводная выжимка (общее у всех трёх отчётов)

1. **Вердикт + комментарий + автор + таймстампы** — минимальная запись
   разметки; label/score/explanation — унифицированная тройка.
2. **Скорость триажа** — вердикт одним действием (hover-клик или одна
   клавиша), без диалогов; дешёвый undo; авто-продвижение.
3. **Фильтр «только ошибки/расхождения» + счётчики прогресса** — ядро
   error-analysis workflow.
4. **Разметка поверх предсказаний, отдельным слоем** — ответы моделей не
   затираются; разметка экспортируется вместе с ними одним бандлом.
5. **Экспорт CSV/JSONL с версией схемы, реимпортируемый** — стандарт;
   «filter → export» = корпус ошибок.
6. **Роли — поле author сегодня, права завтра**; не строить multi-role UI,
   но заложить поля.
7. **Расхождение моделей = аналог inter-annotator disagreement** — подсветка
   и фильтр, без метрик согласия в v1.
