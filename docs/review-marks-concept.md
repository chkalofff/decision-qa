# Концепт: разметка результатов прогонов (review marks)

> Статус: концепт v1.3 (после двух независимых ревизий + онбординг разметки
> в туре), к реализации. Опирается на
> исследование `docs/review-marks-research.md` (паттерны Label Studio, Prodigy,
> Argilla, Doccano, Labelbox, LangSmith, Phoenix, Weave, Humanloop) и на текущий
> UI (`frontend/static/results.js`, `batch.js`, `saveas.js`, `assistant.js`
> и др.). Термины UI — как в коде: чип, чипса моделей, дрилдаун, ячейка,
> строка, оверлей, поповер, шапка результатов (sticky), тултип (dist-tip),
> плашка.

## 1. Зачем фича

«Вердикт» отлаживает классификацию под автопилот: цена ошибки — ложноположительное
срабатывание (спам признан спамом, хотя не спам) или ложноотрицательное. Цикл работы
аналитика: прогон → разбор глазами → правка контекста/вопросов/порогов/моделей →
новый прогон. Сегодня разбор живёт только в голове аналитика: результаты можно
смотреть, но нельзя зафиксировать «здесь ошибка», «здесь согласен», «это спорно»
и «почему». Следствия:

- находки теряются между прогонами — сравнение «стало ли лучше» делается по памяти;
- разбор нельзя передать коллеге (файл сессии везёт результаты, но не выводы);
- ассистент не видит, что аналитик уже отверг, и предлагает правки вслепую;
- нет корпуса ошибок — базы для регрессионных проверок и будущей калибровки.

Фича превращает просмотр результатов в разметку: вердикт (✓ верно / ✗ ошибка /
? спорно) + комментарий на любом уровне гранулярности, с сохранением в файле
сессии и попаданием в снапшот ассистента.

**Критерии успеха (проверяемо):**

1. Вердикт на строке/ячейке ставится одним кликом (hover-триада) или одной
   клавишей, без открытия дрилдауна и без диалогов (Prodigy-бенчмарк скорости).
   Проверяется DOM-ассертами: клик по кнопке триады / keydown `Digit2` → пометка
   в state, ни одного диалога не открыто.
2. Комментарий: ≤ 2 действия от пометки до фокуса в поле ввода (DOM-ассерт:
   клик по 💬 → фокус в textarea поповера).
3. Триаж батча 30 файлов × 3 вопроса (90 ячеек) — ≤ 6 минут с хоткеями.
   Проверяется ручным чек-листом юзабилити-прогона (секундомер, прогон с
   хоткеями против прогона мышью) — инструментального замера в проекте нет,
   чек-лист фиксируется в реализационной задаче.
4. Ненавязчивость: строка/ячейка без пометок при отсутствии hover визуально
   неотличима от текущей (все контролы разметки — hover-only или за тоглом);
   проверка глазами на ширинах ~550 и ~1440 px (Definition of Done для UI).
5. Разметка переживает цикл «Сохранить как…» → «Открыть…» на другом экземпляре
   без потерь (включая remap id файлов пакета) — покрыто DOM-тестами.
6. Ассистент отвечает на запрос «разбери мои ошибки» по снапшоту без
   дополнительных действий пользователя.

## 3. Модель данных разметки

### 3.1 Запись пометки

Разметка — плоский список пометок (Prodigy/Doccano-стиль, без вложенных
сущностей). Одна пометка = одна запись:

```json
{
  "id": "m_3f9a2c",
  "target": { "scope": "batch", "file": "f_a1b2c3", "question": "q2", "model": "clef-9b" },
  "verdict": "reject",
  "comment": "Ложное срабатывание: вопрос клиента, а не реклама.",
  "criterion": "correctness",
  "author": "local",
  "created_at": "2026-10-13T14:02:11.203Z",
  "updated_at": "2026-10-13T14:20:41.990Z"
}
```

| Поле | Значение | Обоснование (JTBD → паттерн) |
|---|---|---|
| `id` | `m_` + случайный суффикс (генератор как `genId()` файлов пакета) | Стабильная ссылка для undo-стека и будущего audit-лога |
| `target.scope` | `"single"` / `"batch"` | Страница-источник; у страниц разные наборы ключей цели |
| `target.model` | ключ модели (`clef-9b`) | Дифференциация по моделям (JTBD 4); отсутствует у пометок «вопрос»/«файл» |
| `target.mode` | `decisions` / `fast_batch` / `clef` / … | В одиночном режиме «Оба» у модели два прогона — цель должна их различать. Значение ровно как у прогона в `flattenRuns` (`results.js`): `res.metrics.mode \|\| runMode` — иначе пометка не найдёт свой чип/ячейку |
| `target.question` | id вопроса из **снапшота** результатов (`state.results.questions` / `state.batch.questions`) | Привязка к снапшоту, а не к живому редактору: правка вопросов после прогона не роняет разметку (3.2, раздел 7) |
| `target.file` | id файла пакета (`f_…`) | Ячейка/строка пакета; при экспорте-импорте remap'ится (раздел 8) |
| `target.decision` | `true` | Пометка на исход решения (чип/ячейка «Решение»), JTBD 10 |
| `verdict` | `"accept"` / `"reject"` / `"unsure"` (✓/✗/?) или `null` | Трёхзначная рубрика Prodigy/Phoenix; «unsure» покрывает и флаг-закладку Prodigy «разобрать позже»; `null` — заметка-комментарий без вердикта |
| `comment` | строка, опционально, одна на пометку | Phoenix explanation (JTBD 3); тредов нет — один автор |
| `criterion` | `"correctness"` (единственное значение в v1) | Именованная ось рубрики LangSmith/Phoenix — задел под «тип ошибки: FP/FN» без смены схемы |
| `author` | `"local"` | Phoenix annotator kind Human/LLM — задел под `assistant` (раздел 9) и multi-user |
| `created_at` / `updated_at` | ISO-строки | Labelbox/Argilla — таймстампы на каждой аннотации; `updated_at` фиксирует последнюю правку вердикта/комментария |

Отсутствующие поля `target` задают уровень гранулярности. Ключ цели
(дедупликация, undo, поиск пометки при рендере) — фиксированный формат с
явным сегментом уровня, чтобы `decision:true` не требовал исключений и уровни
не коллидировали (пометка «прогон» и пометка «решение этого прогона» — разные
ключи):

| Уровень | target | Ключ цели | Где ставится |
|---|---|---|---|
| Прогон (одиночный) | `{scope:"single", model, mode}` | `single\|run\|<model>\|<mode>` | дрилдаун чипа прогона |
| Ответ на вопрос (одиночный) | `{scope:"single", model, mode, question}` | `single\|cell\|<model>\|<mode>\|<qid>` | строка режима A, ячейка режима B |
| Строка вопроса (сравнение) | `{scope:"single", question}` | `single\|q\|<qid>` | строка режима B (без model — «вопрос целиком») |
| Решение (одиночный) | `{scope:"single", model, mode, decision:true}` | `single\|dec\|<model>\|<mode>` | чип решения / оверлей |
| Модель в пакете | `{scope:"batch", model}` | `batch\|model\|<model>` | поповер статистики модели (ⓘ чипсы) |
| Файл целиком | `{scope:"batch", file}` | `batch\|file\|<fileId>` | строка файла (th) |
| Ячейка пакета | `{scope:"batch", file, question, model}` | `batch\|cell\|<fileId>\|<qid>\|<model>` | ячейка таблицы |
| Решение пакета | `{scope:"batch", file, model, decision:true}` | `batch\|dec\|<fileId>\|<model>` | ячейка «Решение» / оверлей |

### 3.2 Инварианты

- **Одна пометка на цель.** Ключ цели — из таблицы выше. Повторный вердикт
  перезаписывает `verdict` и бампит `updated_at`; повторный клик по активному
  вердикту снимает пометку (toggle). Комментарий без вердикта допустим
  (`verdict: null`) — «заметка»: считается в 💬-счётчиках и в «размечено»,
  но не в ✓/✗/? (формулы — 4.8).
- **Пометка привязана к снапшоту результатов**, а не к живому редактору.
  Одиночный режим: `state.results.questions` уже снапшотится при прогоне.
  Пакет: сегодня снапшотится только `state.batch.decision`, а таблица рендерится
  по живому `buildQuestionsPayloadQuiet()` — поэтому **фича добавляет снапшот
  вопросов пакета**: `state.batch.questions` пишется при старте `runBatch`
  (с `direction`, как `withDirections` у одиночного), и `renderBatchResults`
  рендерит таблицу по снапшоту, а не по живому редактору (пустой прогон —
  живые вопросы, как сейчас). Это симметрично одиночному режиму
  (`resultQuestions`) и делает ссылку `target.question` несгораемой при
  stale-правках: удаление вопроса после прогона больше не прячет колонку и
  не сиротит её пометки. Изменение существующего поведения (таблица перестаёт
  следить за живыми правками) осознанно: расхождение уже покрыто жёлтой
  stale-плашкой, а соответствие «таблица = то, что прогонялось» важнее для
  разметки. CSV/JSON-экспорт пакета тоже строится по снапшоту.
- **Хранение в state и имена.** Одиночный режим — `state.results.marks`
  (массив); пакет — `state.batch.marks` (массив, sibling `state.batch.results`).
  Сознательно внутри/рядом с результатами: экспорт «Сохранить как…»,
  демо-снапшот тура и restore-функции уже оперируют этими объектами —
  разметка едет вместе с результатами, сброс результатов сбрасывает разметку.
  Правило имён: в state и в файле сессии одно имя — **`marks`**
  (`results.marks`, `batch_results.marks`); `reviewMarks` — только поле
  снапшота ассистента (camelCase, как `batchResults` и прочие поля снапшота).
- **Версия схемы:** `marks_version: 1` рядом со списком (в экспорте — поле
  контейнера, раздел 8). Импорт файла с `marks_version > 1` пропускает разметку
  с предупреждением в format-banner («разметка из более новой версии не
  загружена»), результаты открываются как сейчас.

### 3.3 Заложено «на вырост», но не реализуется

- `criterion` — вторая ось разметки (FP/FN, «источник ошибки»): именованные
  ключи LangSmith. UI выбора оси не делаем; поле уже в схеме.
- `author` — разметка ассистентом (`"assistant"`, pending-приёмка) и именованные
  пользователи. Прав и ролей нет (один локальный пользователь), но поле есть.
- История смен вердикта (append-only audit Labelbox): в v1 только `updated_at`;
  структура `id` + иммутабельность ключа цели не блокируют добавление истории.

## 4. UI-концепт по поверхностям

### 4.1 Общие принципы

1. **Триада ✓ ✗ ? + 💬** — единственный контрол разметки на всех поверхностях.
   Цвета — из существующей палитры: ✓ `var(--green)`, ✗ `var(--red)`,
   ? `var(--yellow)` (семантика Prodigy accept/reject/ignore).
2. **Hover-only:** контролы появляются при наведении как absolute-оверлей у
   правого края строки/ячейки и **не меняют раскладку** (нет reflow, шеврон ▾
   и контент не двигаются). Якорь для absolute — `position: relative` на
   `.res-row`, `.res-cell` и `th` файла (добавляется в CSS этой фичей; у
   `.batch-cell` уже есть). Без hover и без пометки разметки в потоке нет —
   строка pixel-идентична текущей (критерий успеха №4).
3. **Постоянная индикация помеченного, не ломающая геометрию:**
   - строка (`.res-row`) — значок вердикта в потоке перед шевроном (строка и
     так flex-wrap, место резиновое) + цветная кромка слева через
     `box-shadow: inset 3px 0 0 <цвет>` (не `border-left`: бордер сдвинул бы
     контент на 3px и сломал pixel-идентичность непомеченных соседей);
   - ячейка (`.res-cell`, `.batch-cell`) — значок вердикта мини-бейджем
     (10 px) **absolute-оверлеем в правом верхнем углу**, не в потоке:
     ячейки `white-space: nowrap`, инфлоу-значок расширил бы колонку и
     разъехалась бы сетка (противоречило бы «геометрия сохраняется» из 4.4).
     Рамка помеченной ячейки — тоже `box-shadow: inset 0 0 0 1px <цвет>`;
   - комментарий — бейдж `💬n` рядом со значком (у ячеек — тем же оверлеем).
4. **Конфликты жестов исключены конструкцией:**
   - клик по строке/ячейке открывает дрилдаун (режим A/B) — клики по триаде
     делают `stopPropagation` (как `batch-att-remove` и `batch-model-chip-info`);
   - hover показывает dist-tip с распределением — tip имеет `pointer-events:
     none` и не перекрывает триаду; триада живёт в DOM строки/ячейки, не в tip;
   - клик по чипу решения открывает оверлей «как получилось решение» — вердикт
     на решение ставится внутри оверлея (и хоткеем с hover, см. 5.1), чип не
     обрастает кнопками;
   - drag&drop файлов пакета — триада строки файла стартует не с drag-handle,
     конфликта нет.
5. **Новый модуль `review.js`** (данные, поповер комментария, хоткеи, undo,
   фильтры) + точечная интеграция в `results.js`/`batch.js` (рендер значков и
   триад). События — через существующий pub/sub (`emit("review")`); точечное
   обновление DOM пометки **без полного `renderResults()`** — иначе слетают
   hover и открытые дрилдауны (тот же инвариант, что «не перерендеривать
   результаты по поллингу models»). По AGENTS.md в том же изменении
   обновляются: `ARCHITECTURE.md` (модуль `review.js`, поля state
   `results.marks` / `batch.marks` / `batch.questions`, поля файла сессии
   `results.marks` / `batch_results.{questions, marks, marks_version}`, поле
   снапшота `reviewMarks`, правило в `prompts.py` + ветка обрезки в
   `serialize_snapshot`, `help.js` — новый шаг тура после `demoRun`) и тесты:
   DOM (`frontend/tests/review.test.mjs` по доменной структуре; шаг тура
   разметки — в `help.test.mjs`: позиция сразу после `demoRun`, интерактивный
   backdrop, подсветка `#results-card`) и backend (обрезка
   `serialize_snapshot` с reviewMarks,
   рядом с `test_serialize_snapshot_prioritizes_results_over_context`).

### 4.2 Строка вопроса — режим A (один прогон)

Цель пометки: `{model, mode, question}` — ответ единственного прогона.

```
нет пометки, без hover — как сейчас, без отличий:
┌────────────────────────────────────────────────────────────────┐
│ ⊙ Спам?              ▰▰▰▰▱▱▱▱   да · 96%                     ▾ │
└────────────────────────────────────────────────────────────────┘

hover — триада всплывает у правого края поверх строки (absolute, шеврон на месте):
┌────────────────────────────────────────────────────────────────┐
│ ⊙ Спам?              ▰▰▰▰▱▱▱▱   да · 96%  ┌──────────────┐   ▾ │
│                                           │ ✓   ✗   ?   💬 │   │
│                                           └──────────────┘   │
└────────────────────────────────────────────────────────────────┘

помечено «ошибка» — постоянные маркеры без hover:
┌────────────────────────────────────────────────────────────────┐
┃ ⊙ Спам?              ▰▰▰▰▱▱▱▱   да · 96%                  ✗  ▾ │
└────────────────────────────────────────────────────────────────┘
  ▲ красная кромка слева (inset box-shadow 3px — без reflow)

помечено + комментарий, тоггл 💬 в шапке включён — превью под строкой:
┌────────────────────────────────────────────────────────────────┐
┃ ⊙ Спам?              ▰▰▰▰▱▱▱▱   да · 96%              ✗  💬1 ▾ │
┃   └ 💬 Ложное срабатывание: вопрос клиента, а не реклама…       │
└────────────────────────────────────────────────────────────────┘

активен фильтр «только ✗» — строки без ✗ скрыты, в шапке «показано 4 из 10»
```

- Клик по ✓/✗/? — вердикт сразу, без диалога (JTBD 1–2). Клик по активному
  вердикту снимает пометку. Клик по 💬 — поповер комментария (раздел 6).
- Пометка видна и в дрилдауне строки (`renderAnswerDrilldown`): значок и
  комментарий продублированы в `res-detail-caption`-строке — там же можно
  править через 💬.

### 4.3 Строка сравнения — режим B (несколько прогонов)

Два уровня целей на одной строке: ячейка прогона `{model, mode, question}` и
строка вопроса `{question}` (без модели — «вопрос плохо сформулирован», JTBD 11).

```
┌──────────────────────────────────────────────────────────────────────┐
│ ⊙ Тон позитивный?  ┌──────────┐ │ ┌──────────┐ │ ┌──────────┐   ⚡ ▾ │
│                    │ 9B       │ │ │ 27B      │ │ │ JEV      │      │
│                    │ да · 88% │ │ │ нет · 71%│ │ │ да · 93% │      │
│                    │ ▮▮▮▮▮▮▮▯  │ │ │ ▮▮▮▮▮▯▯▯ │ │ │ ▮▮▮▮▮▮▮▮ │      │
│                    └──────────┘ │ └──────────┘ │ └──────────┘      │
└──────────────────────────────────────────────────────────────────────┘

hover на ячейке 27B — триада в правом верхнем углу ячейки (overlay):
│                    ┌──────────┐ │ ┌──────────┓ │                     │
│                    │ 9B       │ │ │ 27B  ✓✗?💬┃ │                     │

размечено: у 9B — ✓, у 27B — ✗ с комментарием, у строки вопроса — ? :
│ ⊙ Тон позитивный?  ┌──────────┐ │ ┌──────────┐ │ ┌──────────┐ ⚡ ? ▾ │
│                    │ 9B     ✓ │ │ │ 27B  ✗💬1│ │ │ JEV      │      │
│                    └──────────┘ │ └(inset-   │ │ └──────────┘      │
│                                 │  рамка)    │ │                     │
```

- Триада **строки** появляется у правого края (левее ⚡/▾) при hover на текст
  вопроса; триада **ячейки** — при hover на ячейку. Вложенности hover-зон нет:
  ячейка — отдельный элемент `.res-cell`, зоны не пересекаются.
- Значки вердиктов в ячейках — absolute-оверлей в углу (4.1.3), геометрия
  ячеек не меняется.
- Расхождение (⚡) и пометки независимы: строка может быть и «расходится», и
  «? спорно» — оба маркера видны (фильтр «расхождения» — раздел 5.3).

### 4.4 Ячейка батч-таблицы

Цель: `{file, question, model}`. Ячейки крошечные (`.batch-cell` — ответ +
⚠), поэтому: триада — overlay в правом верхнем углу ячейки по hover (якорь —
существующий `position: relative`); постоянный значок вердикта — absolute
мини-бейдж в углу (не в потоке, колонка не расширяется); рамка помеченной
ячейки — inset box-shadow (не фон: фон занят conf-*/dir-* семантикой ответа).

```
┌────────────┬───────────┬───────────┬──────────┬───────────┐
│ Файл       │ Спам? ·9B │ Спам?·27B │ Тон? ·9B │ Решение·9B│
├────────────┼───────────┼───────────┼──────────┼───────────┤
│ №1 a.txt ▾ │ да · 96%  │ да · 91%  │ 2.1 из 4 │ [Спам]    │
│ №2 b.txt ▾ │ да · 88%✗ │ нет · 55% │ 3.0 из 4 │ [Спам] ✗  │
└────────────┴───────────┴───────────┴──────────┴───────────┘
(✗ в таблице показан условно в строке; в реальности — absolute-бейдж
в углу ячейки, не в потоке, 4.1.3; у бейджа решения — суффикс чипа, 4.6)

hover на ячейке:                помеченная ячейка:
┌───────────┐                   ┏━━━━━━━━━━━┓
│ да · 88%  │ ← триада overlay  ┃ да · 88% ✗┃ ← мини-бейдж в углу (overlay),
│      ✓✗?💬│                   ┗━━━━━━━━━━━┛   рамка inset, ширина колонки
└───────────┘                   				 не меняется
```

- Hover-тултип распределения по ячейке сохраняется (dist-tip,
  `pointer-events: none`) — конфликта нет.
- Фильтры в таблице не скрывают, а **глушат** ячейки (`opacity: .35`): сетка
  «файлы × вопросы × модели» обязана сохранять геометрию, иначе потеряется
  навигация. Строки файлов без единой подходящей ячейки скрываются целиком,
  агрегатная строка «Итого» остаётся (считается по всем, с пометкой
  «фильтр активен»).

### 4.5 Строка файла (батч)

Цель `{file}` — «файл целиком» (неформат, исключить из корпуса, JTBD 11).
Триада появляется в `th` строки правее шеврона дрилдауна при hover на th:

```
│ №2 · b.txt ▾  ✓ ✗ ? 💬 │   ← hover на th; клики не мешают
                              имени (превью) и шеврону (дрилдаун)
```

Индикация: значок вердикта у номера файла (`№2 ·`), виден и в списке файлов
слева? Нет — только в таблице результатов: список файлов относится к вводу,
не к прогону (его перерендер на каждый чих уже есть; раздуваем diff — нет).

### 4.6 Чип решения и ячейка «Решение»

Цель: `{model, mode, decision:true}` (одиночный), `{file, model, decision:true}`
(батч). Сам чип не обрастает кнопками: hover-подсказка и клик уже заняты
(`attachDecisionTip` → оверлей). Вердикт ставится:

- в оверлее «как получилось решение» — новый блок внизу `decision-overlay-body`;
- хоткеем с hover на чипе (раздел 5.1);
- постоянный мини-значок вердикта суффиксом чипа, если помечен.

```
Решение: [Clef 9B: Спам ✓] [Jev: Не спам ✗] [⚡ решения различаются]
                    ▲ постоянный мини-значок внутри чипа

оверлей «как получилось решение», нижний блок:
┌───────────────────────────────────────────────────────┐
│ Clef 9B — как получилось решение                  ✕   │
│ ┌ dec-group «✓ Спам» ┐ ┌ dec-group «✗ Отклонить» ┐    │
│ ... ✓/✗-строки условий (существующее) ...            │
│ ───────────────────────────────────────────────────── │
│ Ваша оценка решения:  [✓] [✗] [?]   💬 Комментарий…   │
└───────────────────────────────────────────────────────┘
```

Та же механика в ячейке «Решение» батч-таблицы (бейдж — тот же
`attachDecisionTip`): вердикт через оверлей/хоткей, значок суффиксом бейджа.
Поповер комментария, открытый из блока внутри оверлея, — над оверлеем и
закрывается по Esc первым (стек — 6.1).

### 4.7 Чип прогона (одиночный) и прогон модели в пакете

Цель `{model, mode}` — «прогон целиком» (JTBD 9). Поверхность — дрилдаун чипа
прогона (`renderRunDetail`), дополнительная строка под метриками:

```
┌ Clef 9B · обычный — 4.2 с · 310 ток/с ────────────────────────┐
│ Режим: обычный   Длительность: 4.2 с   Доля на вариантах: …   │
│ ───────────────────────────────────────────────────────────── │
│ Оценить прогон:  [✓] [✗] [?] [💬]                             │
└───────────────────────────────────────────────────────────────┘
```

Индикация — значок вердикта в `run-chip-head` (рядом с `run-chip-metrics`).

В пакете уровень «прогон модели по всем файлам» (`{scope:"batch", model}`)
ставится в поповере статистики модели (ⓘ на `.batch-model-chip`,
`batch-model-popover`): дополнительная строка «Оценить прогон: ✓ ✗ ? 💬» под
строками статистики. Индикация — мини-значок на чипсе модели рядом с ⓘ.
Ограничение: сам поповер статистики остаётся на z-index 90 (существующий) —
на демо-шагах тура он под затемнением, поэтому пометку уровня «модель в
пакете» на демо поставить нельзя (осознанно: это единственная поверхность
уровня; все остальные уровни разметки на демо работают). Не регрессия.

### 4.8 Шапка результатов: ревью-тулбар (обе страницы)

Одиночный режим — новая строка в `#results-sticky` (под `#decision-chips`),
рендерится только когда есть результаты:

```
┌──────────────────────────────────────────────────────────────────┐
│ 10 вопросов · уверенность 87%   [сошлись по 7 из 10]             │
│ [Clef 9B · обычный — …] [Jev · обычный — …]                      │
│ Решение: [9B: Спам] [Jev: Не спам] [⚡ решения различаются]       │
│ ──────────────────────────────────────────────────────────────── │
│ ✓8 ✗3 ?1 💬4 · размечено 12 из 30   [Фильтр: все ▾] [💬̲] [⟲]    │
└──────────────────────────────────────────────────────────────────┘
```

Пакет — такая же строка в `#batch-results` между `.batch-chips` (сводка) и
`.batch-sel-row` (чипсы моделей).

Состав тулбара (слева направо):

1. **Счётчики прогресса** `✓n ✗n ?n 💬n · размечено X из Y`. Формулы
   (когерентные, один набор целей для всех счётчиков страницы):
   - **Y** — число размечаемых целей на странице по всем уровням: ячейки
     ответов (вопрос × прогон / файл × вопрос × модель), строки вопросов
     режима B, чипы/ячейки решений, чипы прогонов (одиночный) / прогоны
     моделей и файлы (пакет). Считается по результатам целиком и не зависит
     от чипс-фильтра видимости моделей — иначе Y прыгал бы при клике по чипсе.
   - **X** — цели с пометкой любого вида (`verdict != null` или непустой
     `comment`); заметки `verdict: null` входят.
   - **✓n/✗n/?n** — число пометок с соответствующим вердиктом среди того же
     набора целей (одна пометка на цель — совпадает с числом целей).
   - **💬n** — пометки с непустым `comment`.
   - Пометки-сироты (цель не отображается: модель удалена из реестра и т.п.)
     не входят ни в один счётчик, но остаются в данных и попадают в экспорт.
   Паттерн: дашборд-счётчики Label Studio / сайдбар-прогресс Prodigy (JTBD 12).
2. **«Фильтр: … ▾»** — кнопка с menu-dropdown (существующий паттерн меню):
   радио-список фильтров раздела 5.3. Активный не-«все» фильтр превращается в
   чип с ✕ рядом со счётчиком.
3. **💬** — icon-btn-тоггл «показать/скрыть комментарии» (персист в
   `localStorage dq-review-comments`, дефолт — скрыты; JTBD 13). Скрыты =
   видны только бейджи `💬n`.
4. **⟲** — icon-btn undo, `disabled` при пустом стеке, title «Отменить
   последнюю пометку (U)».

Тулбар — единственное постоянное добавление в шапку; когда пометок ноль,
строка сворачивается до компактного `Разметка: 0 из Y [Фильтр ▾] [💬]` —
счётчики нулевых вердиктов не печатаются.

## 5. Быстрая (массовая) разметка

### 5.1 Механика скоростного триажа

Основной цикл массовой разметки (пакет, 30–100 файлов): глаза по строке →
hover на ячейку → клик по вердикту или клавиша → следующая. Требования к нему:

- **Вердикт одним кликом** с hover-триады (JTBD 1) — без дрилдауна, поповеров,
  диалогов. Humanloop-паттерн «фидбек прямо в колонке таблицы».
- **Одноклавишные вердикты** (Prodigy-паттерн, мнемоника как у Labelbox 1/2/3):
  - `1` — ✓ верно, `2` — ✗ ошибка, `3` — ? спорно;
  - `4` или `C` — открыть поповер комментария к hover-цели;
  - `U` (и `Ctrl/Cmd+Z` вне полей ввода) — undo;
  - сопоставление — по **`e.code`** (`Digit1`…`Digit4`, `KeyC`, `KeyU`,
    `KeyZ`), а не `e.key`: в русской раскладке `e.key` даёт «с»/«г», и хоткеи
    умирали бы. Код клавиши раскладконезависим. DOM-тест обязан включать кейс
    `key: "с", code: "KeyC"`;
  - клавиша применяется к **активной цели** — элементу под курсором. Уход
    курсора цель **не сбрасывает**: последняя hover-цель «паркуется» (лёгкий
    контур у припаркованной цели), клавиши продолжают работать на неё —
    иначе клавиатура без мыши мертва. Новый hover перехватывает цель;
  - цифры при открытом поповере комментария: фокус в textarea — печатаются
    как текст; фокус вне textarea — меняют вердикт цели поповера (триада
    поповера — та же цель).
- Гард: хоткеи молчат, если фокус в `input/textarea/select`, CodeMirror
  (`cm-focused`), открыт лайтбокс/превью/диалог, открыт тур (шаги подсветки)
  или идёт прогон. Открытый оверлей решения хоткеи НЕ глушит: его
  decision-цель становится активной (клик по чипу, открывшему оверлей,
  паркует её), и клавиши 1/2/3/4 применяются к ней — иначе хоткей попадал
  бы в припаркованную цель, скрытую под оверлеем. Поповер комментария
  получает цифры по правилу выше.
- **Разметка во время прогона невозможна конструктивно:** пометки сбрасываются
  при старте прогона (раздел 7), триады не рендерятся и хоткеи молчат при
  `state.running` / `state.batch.running`. Инкрементальный перерендер
  `renderBatchResults` на каждый готовый файл разметке не мешает — её в этот
  момент не существует.
- **Undo** — in-memory стек последних 10 операций (поставить/снять/сменить
  вердикт, сохранить комментарий). Подтверждение — визуальная вспышка цели
  (краткая подсветка фона), без тостов (тостовой системы в приложении нет,
  плодить её ради undo не надо). Паттерн — история решений Prodigy, срезанная
  до клавиши и кнопки ⟲ в тулбаре.

### 5.2 Осознанное отсутствие авто-продвижения

Prodigy/Argilla/Humanloop дают скорость авто-переходом «submit → следующая
карточка». Мы **не** делаем авто-продвижение: у нас не поток карточек, а сетка,
и «следующая неразмеченная» неоднозначна (вправо по моделям? вниз по файлам?
по фильтру?). Попытка угадать = скачущий фокус и мисклики. Вместо этого скорость
даётся за счёт: hover-клик без открытия деталей, клавиши на припаркованной
цели, фильтр «без отметок» как самособирающаяся очередь (размеченное исчезает
из выборки), агрегат «размечено X из Y» как прогресс. Если юзабилити-замер
(критерий №3) покажет узкое место — вернёмся к авто-продвижению внутри фильтра
«без отметок» как отдельной опции.

### 5.3 Фильтры

Один активный фильтр за раз (радио в menu-dropdown кнопки «Фильтр»).
Семантика попадания по scope определена явно:

| Фильтр | Правило попадания | Источник |
|---|---|---|
| Все | без фильтра (дефолт) | — |
| ✗ Ошибки | цель имеет `verdict=reject` | Phoenix: «фильтр по значению аннотации» — ядро error analysis |
| ? Спорные | `verdict=unsure` | Prodigy flag «разобрать позже» |
| 💬 С комментариями | непустой `comment` | Label Studio — колонка Comments/фильтр |
| ⚪ Без отметок | цель без пометки | «Show only finished tasks» наоборот — очередь неразмеченного |
| ⚡ Расхождения | см. ниже | Consensus-lite: подсветка + фильтр расхождений |

Правила видимости строк:

- **Режим A** (строка = цель-ответ): строка видна, если её пометка подходит
  под фильтр; для ⚪ — если пометки нет.
- **Режим B** (строка содержит ячейки + цель-строку вопроса): для ✗/?/💬
  строка видна, если попадание есть у самой строки или хотя бы у одной её
  ячейки (неподходящие ячейки глушатся); для ⚪ строка видна, пока есть хотя
  бы одна цель без пометки (ячейка или сама строка) — «строка разобрана»
  означает «всё внутри размечено».
- **Пакет** (строка файла содержит ячейки файл×вопрос×модель, ячейки решений
  и цель-файл): те же правила. Пометка уровня файла — попадание для ✗/?/💬
  (строка видна); для ⚪ пометка файла не закрывает неразмеченные ячейки —
  строка видна, пока есть хоть одна ячейка без пометки.
- **⚡ Расхождения**: режим B — существующий критерий `pairsDisagree` по
  строке (тот же, что ставит ⚡). Пакет: группа файл×вопрос расходится, если
  топ-ответы **видимых** моделей (чипсы) расходятся по тому же критерию;
  попадание — все ячейки группы; строка файла видна, если расходится хотя бы
  одна группа. Фильтр недоступен (disabled с пояснением в title) в режиме A
  и при одной видимой модели — расхождение не определено.

Поведение: одиночный список — строки скрываются, в тулбаре счётчик
«показано X из Y» и чип-сброс; батч-таблица — ячейки глушатся (`opacity .35`),
строки файлов без попаданий скрываются, «Итого» остаётся (раздел 4.4).
Фильтр не персистится и сбрасывается при смене страницы/прогоне — это рабочий
инструмент триажа, не состояние анализа.

### 5.4 Показ/скрытие комментариев одной кнопкой

Тоггл 💬 в ревью-тулбаре (4.8): включён — под каждой помеченной строкой и в
дрилдаунах виден текст комментария одной строкой с ellipsis (полный текст —
в поповере по клику на бейдж); выключен — только бейджи `💬n`. Дефолт выключен:
JTBD 13 «не загромождать UI» + паттерн Label Studio «счётчики вместо контента».

### 5.5 Обучение механике: демо-тур и первая подсказка

Контролы разметки скрыты до hover по дизайну (критерий №4 «ненавязчивость») —
побочный эффект: нулевая обнаруживаемость с нуля. Обучение поэтому встроено
в продукт, а не в документацию (JTBD 18).

**Шаг тура.** Новый шаг `HELP_STEPS` сразу после шага `demoRun` (демо-прогон
одиночного режима). Отдельный шаг, а не интеграция в `demoRun`: у того своя
обучающая цель («посмотреть результаты прогона»), два учебных текста в одном
тултипе перегружают; инфраструктура при этом бесплатна — шаг наследует
подложенные демо-результаты (демо-хуки повторно не дёргаются, состояние на
месте), тот же интерактивный backdrop (`help-interactive`) и подсветку
`#results-card`, то есть пользователь может прямо на шаге потыкать пометки
на демо-результатах (разрешено разделом 7). Отдельного шага после `demoBatch`
нет: механика идентична (та же триада на ячейках таблицы), текст одиночного
шага закрывает это одной фразой — тур не раздуваем.

Текст шага (черновик): «Разметка результатов. Наведите курсор на строку —
справа появятся ✓ ✗ ? 💬: верно / ошибка / спорно / комментарий. Те же
вердикты — клавишами 1/2/3, комментарий — 4 или C, отмена — U. В шапке
сверху: счётчики разметки, фильтр (ошибки, без отметок, расхождения) и
кнопка 💬 показа комментариев. В пакете те же пометки ставятся на ячейки
таблицы. Попробуйте прямо сейчас: это демо — пометки ни к чему не обязывают
и исчезнут вместе с демо-данными при выходе из тура».

**Плашка «Поиграть с демо»** не меняется (это навигация, не учебник).
Разметка демо-результатов в свёрнутом виде — часть обучения руками: при
развороте тура шаг реинициализируется и демо-результаты подкладываются
заново (гарды демо-хуков сбрасываются) — пометки, поставленные в свёрнутом
виде, сбрасываются вместе с ними; при выходе из тура — тем более (раздел 7:
пометки живут внутри снапшота результатов, демо-результаты в `tourSnap`
пользователя не входят). Промис «пометки исчезнут» живёт в тексте шага,
а не в плашке.

**Пропустившие тур.** Тур можно навсегда закрыть (флаг `dq-help-seen`), а до
кнопки «?» в тулбаре ещё надо догадаться. Минимальное решение — одноразовая
подсказка при первом реальном (не тур) появлении результатов: маленький
`.popover` у первой строки `#results-list`, две строки («Наведите курсор на
строку результатов — там ✓/✗/? и 💬. Клавиши 1/2/3, отмена — U»), кнопка
«Понятно»; флаг `dq-review-hint-seen` в localStorage (аналог `dq-help-seen`).
Не показывается во время тура (`isHelpOpen()`) и на демо-результатах — там
учит сам тур. Клик вне тоже ставит флаг: одноразовость важнее дочитывания.
Альтернатива «достаточно тура» отклонена: у скрытых до hover контролов
обнаруживаемость нулевая, а тур можно пропустить навсегда.

## 6. Комментарии

### 6.1 Механика

Комментарий живёт в **поповере** (паттерн `.popover`: `position: fixed`,
позиционирование от якоря, закрытие по клику вне — как `batch-model-popover`
и fold-меню). Инлайн-редактор в строке отвергнут: ломает высоту строк,
конфликтует с дрилдауном и hover-зонами. Отличия от базового паттерна,
продиктованные нашими сценариями:

- **z-index 405** (слой dist-tip, оверлея решения, лайтбокса), а не 90:
  поповер должен быть доступен на интерактивных демо-шагах тура (затемнение
  400, подсветка 401) — иначе вердикты на демо кликабельны, а комментарий
  ушёл бы под затемнение, ломая «поиграть с демо»;
- **стек Esc**: поповер обрабатывает `keydown` в capture-фазе с
  `stopImmediatePropagation` и закрывает только себя. Это критично: обработчик
  оверлея решения (`results.js`) закрывает оверлей на любой Esc — без
  потребления поповером Esc закрыл бы и поповер, и оверлей под ним. Остальные
  document-level Esc-обработчики (лайтбокс, превью, fullscreen контекста,
  тур) получают Esc только когда поповер закрыт. Реализация включает аудит
  всех существующих Esc-обработчиков на предмет порядка;
- **close-on-scroll/resize**: поповер `position: fixed` отрывается от якоря
  при скролле — закрывается (с сохранением текста) по `document` scroll в
  capture-фазе и по `resize`, прецедент — fold-меню в `context.js`.

```
клик по 💬 (или клавиша C на активной цели):
                       ┌──────────────────────────────────────────┐
                       │ №2 · b.txt — «Спам?» — Clef 9B           │ ← контекст цели
                       │ [✓] [✗] [?]        вердикт: Ошибка       │
                       │ ┌──────────────────────────────────────┐ │
                       │ │ Ложное срабатывание: вопрос клиента, │ │
                       │ │ а не реклама…                        │ │
                       │ └──────────────────────────────────────┘ │
                       │ local · создано 14:02 · изменено 14:20   │
                       │ [Снять пометку]              [Готово ✓]  │
                       └──────────────────────────────────────────┘
```

- Открытие: клик по 💬 в триаде, клик по бейджу `💬n`, клавиша `C`.
- Сохранение: `Ctrl/Cmd+Enter`, кнопка «Готово», клик вне, Esc — всё сохраняет
  (нет режима «отменить ввод»: пустой текст = нет комментария; дешёвый undo
  покрывает ошибки). Enter внутри textarea — перевод строки (как в ассистенте,
  Shift не требуем).
- Поповер — единый редактор пометки: можно сменить вердикт (та же триада),
  удалить пометку целиком («Снять пометку»), видеть автора и таймстампы.
- В поповере виден контекст цели (файл/вопрос/модель) — Phoenix-принцип
  «аннотация читается вместе с тем, что аннотирует».

### 6.2 Индикация и счётчики

- Бейдж `💬n` у цели (n — число комментариев на цели; в v1 это 0 или 1, но
  бейдж сразу счётчиком — задел под треды, не переделывать UI).
- В тулбаре шапки — суммарный `💬n`; фильтр «с комментариями» (5.3).
- Обязательный комментарий при ✗ (опция Label Studio) **не вводим**: блокирует
  скорость триажа, а JTBD 3 закрывается фильтром и счётчиками.

### 6.3 Resolved-статус — не нужен в v1

Resolved/unresolved (Label Studio) — механика тредов между ревьюером и
аннотатором. У нас один автор, комментарий — заметка к пометке, а не задача;
«закрыть вопрос» = снять или сменить пометку. Вернёмся, если появится
multi-role (раздел 10).

## 7. Жизненный цикл разметки

| Событие | Поведение разметки | Обоснование |
|---|---|---|
| Новый прогон (одиночный) | `state.results` заменяется целиком → пометки сбрасываются вместе с ним. Если пометки были — confirm до запуска: «Новый прогон заменит результаты и сотрёт разметку (N пометок, K комментариев). Сохранить текущие можно через «Сохранить как…». Продолжить?» | Пометка привязана к конкретным ответам (Phoenix: аннотация к span, не «к вопросу вообще»). Молчаливый перенос на новые ответы = ложная разметка. Confirm с числом пометок — защита от потери разбора (JTBD 1–3) |
| Повторный прогон пакета | `runBatch` НЕ заменяет объект результатов, а мутирует `state.batch.results` пофайлово, id файлов стабильны — поэтому пометки сбрасываются **явным кодом в начале `runBatch`**, один раз, после того же confirm (до запуска первого файла). Без явной очистки пометки «переехали» бы на новые ответы. Отмена на середине: пометки уже сброшены (пользователь подтвердил), частично обновлённые результаты остаются — честное состояние; повторный прогон confirm'а не требует (пометок уже нет) | Та же привязка к ответам; явный сброс вместо побочного эффекта замены объекта, которого в пакете нет |
| Правка входных данных без прогона (stale) | Пометки **сохраняются** вместе с результатами; существующая жёлтая плашка «результаты могут быть неактуальны» покрывает и разметку | Результаты на экране те же — разметка валидна. Привязка к снапшотам `state.results.questions` / `state.batch.questions` (3.2), а не к живому редактору, делает правку вопросов безопасной |
| Смена пресета / «Новый» / «Очистить» пакет | Очищается вместе с результатами (`clearSingleResults` / `loadPresetFiles` / `resetBatch` / `clearFiles` дополняются сбросом `marks` / `batch.questions`) — существующие confirm'ы пресета/«Нового» уже предупреждают о замене | Результаты пресета не связаны с прошлым прогоном |
| Импорт файла без результатов | Результаты и разметка очищаются (текущее поведение `clearSingleResults`; для пакета — `loadPresetFiles`) | Нечего размечать |
| Импорт файла с результатами без разметки | Разметка **замещается**, а не мерджится: `restoreSingleResults` ставит `marks` из файла или `[]`; `restoreBatchResults` — `state.batch.marks` из файла (после remap) или `[]`. Иначе пометки прошлого пакета повисли бы на новых id файлов | Файл сессии — полный снимок; молчаливое слияние = чужие пометки на чужих id |
| Импорт файла с результатами и разметкой | Восстанавливается вместе с результатами как актуальная (раздел 8) | JTBD 7, 14 |
| Удаление файла пакета | `removeFile` удаляет результаты файла → тем же изменением удаляются его пометки из `state.batch.marks` | Целевое действие пользователя над тем же объектом |
| Удаление/переименование модели в реестре | Пометки по её ключу становятся сиротами: не рендерятся, не считаются в счётчиках, но в экспорт попадают | Данные не теряем (Phoenix upsert-философия), UI не засоряем |
| Демо-тур | `tourSnap` — явный список полей, а не «state.batch.*»: он дополняется разметкой обоих режимов (одиночная едет внутри deep-copy `state.results` автоматически; пакетная — новым явным полем `batchMarks`, иначе потеряется). `tourDemoExit` восстанавливает пометки вместе с результатами. Демо-результаты стартуют без разметки (`loadPresetFiles`/`applyDemo*` чистят); пометки, поставленные на демо, стираются вместе с демо-результатами при выходе. Разметка демо-результатов — штатная часть обучения (шаг тура о разметке, 5.5) | Симметрия с результатами; persist на время тура на паузе — демо-пометки нигде не оседают. Явное поле, потому что `batchMarks` — sibling результатов, а не их часть |
| Автосейв (persist.js) | Разметка **не** попадает в `dq-workspace` — результаты там тоже не хранятся | Консистентность: персист отвечает за черновик входных данных; результаты+разметка сохраняются осознанным «Сохранить как…» (риск потери при закрытии вкладки тот же, что у результатов сегодня, — принят продуктом) |

## 8. Экспорт/импорт и совместная работа

### 8.1 Формат в файле сессии («Сохранить как…»)

Разметка включается автоматически вместе с результатами (чекбокс «Включить
результаты прогона»): пометки без результатов бессмысленны, отдельный чекбокс
не нужен. В `buildSessionData` добавляется:

```jsonc
{
  // ...существующие поля сессии...
  "results": {
    // ...существующие results/order/runMode/questions/decision/images...
    "marks": [ /* пометки scope=single, полная запись из раздела 3.1 */ ],
    "marks_version": 1
  },
  "batch_results": {
    "files": ["f_a1b2c3", "f_d4e5f6"],   // существующее: id в порядке batch_files
    "questions": [ /* НОВОЕ: снапшот вопросов прогона пакета (с direction) */ ],
    "results": { /* ... */ },
    "durations": { /* ... */ },
    "decision": { /* ... */ },
    "marks": [ /* пометки scope=batch; target.file — СТАРЫЙ id из files */ ],
    "marks_version": 1
  }
}
```

Почему single-пометки внутри `results`, а batch — отдельным полем
`batch_results.marks`: `buildSessionData` отдаёт `state.results` целиком,
поэтому `marks` едет без кода; у пакета `results` — словарь по id файлов,
списку пометок там не место, и ему нужен remap — кладём рядом с `files`,
который remap и определяет. `batch_results.questions` появляется одновременно
(снапшот вопросов прогона, 3.2) — `restoreBatchResults` восстанавливает его
в `state.batch.questions`; у старых файлов без поля — пересчёт из текущих
вопросов, как сейчас (обратная совместимость).

### 8.2 Импорт и remap id файлов пакета

`parseImport` уже возвращает `results` и `batchResults` объектами целиком —
поля `marks`/`questions`/`marks_version` проезжают без изменений парсера.
Работа — в restore-функциях `stale.js`:

- `restoreSingleResults`: принимает `results.marks` (валидация записей:
  известный `verdict`, объект `target`; битые записи пропускаются с
  `console.warn`, без модалки — как и вся защитная обработка импорта).
  Поля нет — `marks = []` (замещение, не мердж — раздел 7).
- `restoreBatchResults`: строит `idMap` из `br.files` (старое поведение) и
  **тем же idMap перекодирует** `target.file` каждой пометки `br.marks`;
  пометки, чей файл не попал в remap, отбрасываются. Поля нет — `marks = []`.
  Снапшот `br.questions` → `state.batch.questions` с валидацией: массив
  объектов-вопросов в формате `normalizeQuestion`, иначе фолбэк на живые
  вопросы (поведение до фичи) — битая структура не должна ронять
  `renderBatchResults`.
- `marks_version > 1` — разметка пропускается, предупреждение в format-banner
  (3.2). `marks_version` отсутствует — читаем как v1 (первая версия формата
  могла бы выйти без поля; читаем щедро).

### 8.3 CSV и JSON-экспорт пакета

Кнопки «Экспорт CSV/JSON» в `#batch-results` — внешний анализ (не реимпорт):

- **CSV** (`buildBatchCsv`): +4 колонки в конец: `отметка`
  (`верно`/`ошибка`/`спорно`/пусто), `комментарий`, `отметка_решения`,
  `комментарий_решения`. Строка CSV уже есть на каждую ячейку
  файл×модель×вопрос — пометки ячеек и решений ложатся естественно. Пометки
  уровня файла/модели в CSV не попадают (нет строки такой гранулярности) —
  они есть в JSON.
- **JSON** (dump рядом): блок `marks` той же схемы, но `target.file`
  заменён на имя файла (как `decisions` в существующем экспорте — по `f.name`)
  и `target.question` дополнен текстом вопроса — файл читается внешними
  инструментами без нашего состояния.

Одиночный режим CSV-экспорта не имеет — там разметка уезжает только в файле
сессии (осознанно: сценарий одиночного режима — совместный разбор файлом,
не табличный анализ).

### 8.4 Сценарий «передал коллеге»

1. П1: разметил прогон → «Файл → Сохранить как…» → чекбокс «Включить
   результаты прогона» → файл `.json` (материалы + вопросы + правила +
   результаты + разметка одним бандлом — паттерн Argilla `to_disk`).
2. П2: «Файл → Открыть…» → результаты и пометки на месте, fingerprint из
   файла, stale нет. П2 может продолжить разметку поверх и пересохранить
   файл обратно.

**Ограничение круговорота (явно):** атрибуции нет — все пометки
`author: "local"`, и клик П2 по чужому вердикту молча перезапишет его
(`updated_at` сменится, исходное значение потеряется). Это осознанное
ограничение v1: «конфликтов авторства нет» ровно потому, что нет атрибуции.
Обходной путь — П2 хранит свою копию файла, сравнение версий внешним diff.
Штамповать автора при импорте (имя файла/машины) не делаем: ложная атрибуция
хуже отсутствующей. Возврат к вопросу — вместе с multi-role (раздел 10).

### 8.5 Целостность

- Файл с разметкой открыт над изменёнными материалами: существующий confirm
  импорта («заменит текущий материал…») + после импорта любая правка включает
  stale-плашку — разметка при этом остаётся (раздел 7).
- Расхождение состава вопросов/файлов файла и текущего UI не вредит: пометки
  ссылаются на снапшоты результатов внутри того же файла, не на живой редактор.

## 9. Интеграция с ассистентом

### 9.1 Что попадает в снапшот

`buildSnapshot()` дополняется полем `reviewMarks` (только размеченное,
компактно — Phoenix-принцип «аннотации в metadata, которые видит оценщик»):

```jsonc
"reviewMarks": {
  "totals": { "accept": 8, "reject": 3, "unsure": 1, "comments": 4 },
  "items": [
    "вопрос №2 «Спам?» × 9B: ✗ «Ложное срабатывание: вопрос клиента, а не реклама»",
    "вопрос №5 «Тон?» × JEV: ✓",
    "решение × 9B: ✗ «FP: порог P(спам) ≥ 90% пропускает вежливую рекламу»",
    "прогон 27B: ? «медленно и шумно на длинных текстах»",
    "файл №3 (b.txt) × вопрос №1 × 9B: ✗ «не заметил вложение»",
    "файл №7 целиком: ✗ «неформат, исключить»",
    "модель 27B по пакету: ? «переоценивает тон»"
  ]
}
```

- **Резолюция ссылок — по снапшотам прогона, не по живому редактору.**
  `target.question` (id) → № вопроса ищется в `state.results.questions`
  (одиночный) / `state.batch.questions` (пакет): снапшот ассистента нумерует
  вопросы по `state.questions`, и после stale-правок номера могут разойтись —
  пометка обязана ссылаться на то, что реально размечалось. `target.file` →
  num по позиции в `state.batch.files` (та же нумерация, что у бейджей `№n`).
  Модель — `modelShortLabel` по ключу.
- **Сироты** (цель не резолвится: модель удалена, id вопроса не найден в
  снапшоте прогона) в `items` не попадают и в `totals` не считаются — totals
  когерентны счётчикам шапки (4.8).
- **stale**: при `resultsStale`/`batch.resultsStale` к блоку добавляется
  `"stale": true`, а в `prompts.py` — уточнение: «при stale номера вопросов и
  файлов в reviewMarks — на момент прогона, текущие вопросы могли измениться».
- Бюджет: ≤ 30 items (приоритет: сначала ✗ и ?, потом с комментариями, потом
  ✓), текст ≤ 1500 символов. Два механических требования к снапшоту:
  (а) в `buildSnapshot` ключ `reviewMarks` ставится ДО `resultsSummary` —
  крайняя хвостовая обрезка `serialize_snapshot` (prompts.py) режет конец
  JSON, и поле после `resultsSummary` съедалось бы первым; (б) в
  `serialize_snapshot` — своя ветка обрезки ПОСЛЕ `resultsSummary` (текущий
  приоритет «тексты batchFiles → context.text → resultsSummary» дополняется
  разметкой как самым ценным: сначала жертвуем сводкой, потом разметкой;
  урезание — items по приоритету, затем укорачивание комментариев).
  Backend-тест рядом с `test_serialize_snapshot_prioritizes_results_over_context`
  (`backend/tests/test_assistant.py`).
- prompts.py — новое правило: «reviewMarks — вердикты и заметки аналитика по
  результатам; учитывай их при анализе и в предложениях, ссылайся по № вопроса
  и № файла; не предлагай правки, противоречащие пометкам, не оспорив их».

### 9.2 Как аналитик ссылается на пометки

- Свободным текстом: «разбери мои ✗ в файле 3» — снапшот даёт ассистенту
  всё нужное (JTBD 8).
- (could, JTBD 16) Кнопка «→ ассистенту» в поповере комментария: вставляет в
  поле ввода панели текст-ссылку `Пометка: файл №3 × вопрос №1 × 9B — ✗ «…»: `
  — курсор в конце, аналитик дописывает вопрос. Humanloop-паттерн «Editor →»
  (перенос контекста в инструмент одним кликом).

### 9.3 Задел на будущее (не v1)

- Ассистент предлагает разметку: записи с `author: "assistant"` в статусе
  pending, приёмка карточкой «Принять/Отклонить» — существующий proposal-
  паттерн ленты. Поля `author` и `criterion` уже в схеме (Phoenix annotator
  kind LLM, Argilla suggestions).
- Корпус ✗-помеченных ячеек как вход для регрессионных прогонов и калибровки
  LLM-судьи (Phoenix «filter → export to dataset», LangSmith Align Evaluator):
  экспорт уже умеет отдавать разметку (8.3) — точка подключения готова.

## 10. Не входит в v1 и почему

| Исключено | Почему | Условие возврата |
|---|---|---|
| Multi-role: права, очереди, раздельные сессии ревьюеров (Label Studio Enterprise, Labelbox workflow, Argilla pending/submitted) | Приложение однопользовательское локальное; передача коллеге — файлом, а не сервером. Поле `author` заложено | Серверный режим или ≥3 разметчика над одним корпусом одновременно |
| Метрики качества по разметке (accuracy прогона против пометок, acceptance-дашборды) | Нужен накопленный объём разметки; считать по 10 пометкам — шум | ≥3 сессии с ≥100 пометок на проект или явный запрос «покажи процент ложных» |
| Golden labels / benchmarks (Labelbox) | Преждевременно: сначала накопить разметку, из неё же вырастут эталоны | Появление регрессионного набора (✗-корпуса) и повторные прогоны против него |
| LLM-as-judge и калибровка судьи на пометках (LangSmith Align Evaluator) | Этап 2 после накопления ✗-примеров; задел — `criterion`/`author` и экспорт 8.3 | ≥50 ✗-пометок с комментариями в одном домене |
| Pairwise-режим (LangSmith PAQ) | Таблица сравнения уже side-by-side; раздельные пометки по моделям закрывают потребность | Запрос на «A/B-слепое» сравнение без имён моделей |
| Серверное хранилище разметки, audit log append-only (Labelbox workflow_history) | Файл сессии + `updated_at` достаточны одиночному циклу; истории правок никто не читает | Multi-user или спор «кто и когда изменил вердикт» |
| Resolved-статус комментариев | Нет тредов и второго ролевого участника (раздел 6.3) | Multi-role ревью |
| Отдельный флаг-закладка (Prodigy `f`) | «? спорно» + фильтр «Спорные» покрывают «разобрать позже» | Пользователи массово ставят ? и просят «ещё одну корзину» |
| Обязательный комментарий при ✗ (опция LS) | Блокирует скорость триажа — главную метрику фичи | Аналит качества корпуса: «✗ без пояснений бесполезны» |
| Авто-продвижение к следующей неразмеченной | Сетка, не поток карточек (раздел 5.2) | Замер критерия №3 покажет узкое место |
| Переназначаемые хоткеи (Prodigy) | Дефолт 1/2/3/4/C/U покрывает; настраивать нечего критичного | Жалобы на коллизию с раскладкой/привычками |
| Эмодзи-реакции, freeform-аннотации, несколько осей рубрики в UI | Избыточно для ✓/✗/? + комментарий; `criterion` ждёт своего часа | Потребность в оси «тип ошибки FP/FN» |
| «Fix & Accept» (Label Studio — поправить аннотацию и принять) | Нечего «чинить»: вывод модели не редактируется в UI — правятся входные данные, вопросы и пороги; цикл «✗ + правка вопроса + перепрогон» закрывает тот же сценарий | Появление редактирования ответов под golden-корпус |
| Массовые действия над отфильтрованной выборкой (Argilla Bulk, Labelbox «Move to task») | Типовой прогон — десятки целей: точечный триаж с хоткеями и фильтрами быстрее, чем выделение-и-действие; массовый вердикт по фильтру — риск расставить пометки неглядя | Типовой пакет ≥ 200 целей или запрос «принять все отфильтрованные» |

## 11. Метрики успеха и риски UX

### 11.1 Как проверим, что разметка быстрая и не загромождает

- **Скорость**: критерии 1–2 проверяются DOM-ассертами (клик по кнопке триады
  или keydown `Digit2` → пометка в state, диалогов не открыто; клик по 💬 →
  фокус в textarea поповера). Отдельный DOM-кейс — русская раскладка
  (`key: "с", code: "KeyC"` открывает поповер). Критерий 3 (90 ячеек ≤ 6 мин)
  — ручной чек-лист юзабилити-прогона: секундомер, прогон с хоткеями против
  прогона мышью; чек-лист фиксируется в реализационной задаче.
- **Ненавязчивость** (критерий 4): строка/ячейка без пометок при отсутствии
  hover не отличается от текущей (ни одного нового видимого элемента в потоке;
  тулбар шапки в нулевом состоянии — одна компактная строка). Проверка глазами
  на ~550 и ~1440 px по Definition of Done; contract-тесты фронтенда на
  состояния «нет пометки / помечено / с комментарием / фильтр» (новые
  поверхности без покрытия роняют contract-тесты — это сигнал дописать их).
- **Отсутствие регрессий жестов**: клик по строке по-прежнему открывает
  дрилдаун; hover — тултип распределения; клик по чипу решения — оверлей;
  Esc закрывает поповер, не трогая оверлей под ним. Покрывается расширением
  существующих тестов `results`/`batch`.

### 11.2 Риски и митигации

| Риск | Митигация |
|---|---|
| Случайный вердикт по hover-триаде (цель мелкая, рядом шеврон) | Цель кнопки ≥ 18 px; триада левее шеврона, не перекрывает его; повторный клик по активному вердикту снимает пометку (toggle); undo `U`/⟲ по последним 10 операциям |
| Хоткеи срабатывают при вводе текста / в русской раскладке | Гард по фокусу (input/textarea/select/CodeMirror/оверлеи/тур/прогон); сопоставление по `e.code` — раскладконезависимо; DOM-кейс RU-раскладки (5.1) |
| Триада конфликтует с dist-tip | Tip — `pointer-events: none`, триада в DOM строки/ячейки; физически не пересекаются |
| Индикация ломает геометрию (кромка сдвигает контент, значок расширяет nowrap-колонку, триаде не к чему якориться) | Кромка — inset box-shadow (не border); значок у ячейки — absolute-оверлей в углу, не в потоке; `position: relative` на `.res-row`/`.res-cell`/`th` добавляется в CSS этой фичей (4.1); визуальная проверка 550/1440 |
| Esc закрывает оверлей под поповером | Поповер потребляет Esc в capture-фазе с `stopImmediatePropagation`; аудит document-level Esc-обработчиков при реализации (6.1) |
| Поповер отрывается от якоря при скролле | Close-on-scroll/resize с сохранением текста (прецедент fold-меню, 6.1) |
| Поповер под затемнением демо-тура | z-index 405 — слой интерактивных демо-областей (6.1) |
| Перерендер стирает hover/открытый дрилдаун при смене пометки | Точечное обновление DOM пометки, без полного `renderResults()`; существующий инвариант «не рендерить результаты по поллингу models» сохраняется |
| Потеря разметки при перепрогоне | Confirm с числом пометок и подсказкой «Сохранить как…»; в пакете — явный сброс в начале `runBatch` (раздел 7) |
| Потеря разметки при закрытии вкладки | Тот же статус-кво, что у результатов (persist их не покрывает); счётчик пометок в шапке сам по себе напоминание сохранить файл |
| Фильтр скрывает строки — «потерял контекст» | Счётчик «показано X из Y» + чип активного фильтра с ✕; в таблице ячейки глушатся, а не исчезают — геометрия сетки сохраняется |
| Пометки-сироты (модель удалена из реестра) | Не рендерятся, не считаются, но экспортируются; данных не теряем |
| Рост DOM-слушателей на больших таблицах (30×N ячеек) | Делегирование: один document-обработчик keydown; hover-триада создаётся лениво на первый hover по ячейке либо единый floating-элемент, переставляемый за курсором (реализационный выбор; концептуально — один overlay-контрол на всех) |
